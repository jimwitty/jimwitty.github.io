## 一、全局地图：Windows 组件与驱动的位置

Windows 操作系统横跨用户模式与内核模式两层。驱动不是独立王国：内核模式驱动本身就是**执行体（Executive）的一部分**——执行体是那组管理 I/O、PnP、内存、进程与线程、安全等的内核模式组件的统称。驱动的工作方式是双向的：

- **向下调用**：驱动调用各内核组件导出的例程干活。例如创建设备对象要调 I/O 管理器导出的 `IoCreateDevice`。
- **向上被调用**：驱动必须实现一组系统规定的**标准驱动例程（Standard Driver Routines）**，由操作系统在需要时回调——驱动的"入口"不是 main，而是这组被系统点名的回调函数。

文字版结构示意（自上而下）：

```
用户模式：  应用程序 / Win32 子系统 / 用户模式驱动（如打印驱动、UMDF 驱动）
            ── 系统服务接口（句柄、NtXxx/ZwXxx）──
内核模式：  执行体（Executive，位于 ntoskrnl.exe）
              ├─ I/O 管理器 ── 内含两个子组件：PnP 管理器、电源管理器
              ├─ 对象管理器        ├─ 内存管理器
              ├─ 进程和线程管理器  ├─ 配置管理器（注册表）
              ├─ 安全参考监视器    ├─ 内核事务管理器（KTM）
              └─ 内核（Kernel 本体：线程调度、中断分发等最底层机制）
            各类库：执行体支持库(Ex) / 运行时库 RTL(Rtl) / 安全字符串(Rtl) /
                    DMA 库 / HAL 库(Hal) / CLFS(Clfs) / WMI 库(Wmi)
            驱动程序（.sys）：分层叠在设备之上，夹在执行体与硬件之间
硬件抽象层：HAL —— 屏蔽主板/芯片组级差异
硬件：      总线（PCI/USB…）与设备
```

两个定位细节值得先记住：① 执行体组件都在 `ntoskrnl.exe` 里，但**驱动和 HAL 不属于执行体层**；② PnP 管理器和电源管理器在组织上是 **I/O 管理器的子组件**，不是与 I/O 管理器平级的独立部门——后面学 IRP 时会看到，PnP/电源请求也是装在 IRP 里下发的，这正是组织关系的体现。

## 二、核心要点（先记结论）

1. **驱动分两种执行环境**：用户模式驱动跑在用户态（典型如 Vista 起的打印驱动），崩溃只拖垮当前进程；内核模式驱动跑在内核态、作为执行体的一部分，一个野指针就可能蓝屏整机。本指南讲的是后者。
2. **内核驱动天生是分层的**：一个请求从应用下来，依次穿过最高层、中间层、最低层驱动组成的**驱动堆栈（driver stack）**，结构差异不大、功能差异巨大——越往下越贴近硬件。
3. **IRP 是唯一的"官方语言"**：I/O 管理器、PnP 管理器、电源管理器都用 I/O 请求包（IRP）与驱动通信；一个 IRP 含固定头（原始请求信息 + I/O 状态块）和**每层驱动各一份的 I/O 堆栈位置**，因此同一张 IRP 可以被整条堆栈逐层复用、接力处理。
4. **驱动没有"自己的进程"**：驱动例程通常运行在**任意线程上下文**中——借的是恰好触发它的那个线程。只有最高层驱动可以假设自己运行在发起 I/O 的线程上下文里；中低层驱动永远不能做此假设。
5. **一切皆可被打断**：任何线程可被更高优先级线程抢占；任何例程（包括 ISR）在某个 IRQL 上运行时，都可被更高 IRQL 的中断打断。运行在某 IRQL 上时，该处理器会屏蔽同级及更低 IRQL 的中断向量。由此推出 ISR 必须极短：保存状态、排队一个 DPC、立刻退出，重活留到 DISPATCH_LEVEL 的 DPC 里做。
6. **同步基线是自旋锁 + IRQL**：多处理器平台上所有 CPU 共享内存、都能接中断，驱动必须同步一切共享数据。在 DISPATCH_LEVEL 及以上只能用自旋锁；自旋锁带有一个绑定的 IRQL，获取锁时升到该 IRQL，从而在单处理器上也靠"屏蔽同级中断"防住重入死锁。
7. **系统是"基于对象"而非"面向对象"**：每个执行体组件定义自己的对象类型并导出操作例程；任何组件都**不能直接摸**别的组件的对象内部，只能调它导出的支持例程。很多系统对象是**不透明（opaque）**的——驱动只能通过例程操作，永远不要直接访问其内部结构（系统可以随时改内部布局，这是可移植性的根基）。
8. **例程命名是一张地图**：内核支持例程的名字形如 `前缀 + 操作 + 对象`，前缀标识导出它的组件：`Io`（I/O 管理器）、`Ob`（对象管理器）、`Mm`（内存管理器）、`Ps`（进程/线程管理器）、`Po`（电源管理器）、`Cm`（配置管理器）、`Se`（安全参考监视器）、`Ke`（内核）、`Ex`（执行体支持库）、`Rtl`（运行时/安全字符串）。但有两个例外要记牢：**PnP 管理器没有自己的前缀**（没有 "Pp" 例程，它借道 I/O 体系工作）；**RTL 与安全字符串库都以 `Rtl` 开头，却是两个不同的库**。
9. **I/O 是异步优先的**：请求方发出 I/O 后可以继续执行；驱动不必按收到顺序处理 IRP，可以重排、拆分大传输、并行重叠处理，也不必把一个 IRP 处理完才碰下一个。驱动通过注册 **IoCompletion 例程**在下层完成时被回调，通过设备扩展（device extension）保存进行中操作的状态。
10. **"管理器 vs 库"的分工**：管理器是拥有某种系统资源并对外提供服务接口的组件（对象、内存、I/O、注册表、安全……）；库是供驱动直接链接调用的工具例程集合（内核机制、执行体通用服务、RTL 工具、安全字符串、DMA、HAL、CLFS、WMI）。前者是"部门"，后者是"工具箱"。

## 三、关键知识点详解

### 3.1 驱动类型：先按"在哪运行"分，再按"在栈中哪层"分

**第一刀：用户模式 vs 内核模式。**
- 用户模式驱动（如打印驱动）在用户态运行，通常充当 Win32 应用与内核驱动/系统组件之间的接口层。代价是多一次模式切换，收益是崩溃半径小。
- 内核模式驱动在内核态运行，是执行体的一部分。所有内核驱动都要提供一组系统定义的**标准驱动例程**——驱动之间的差异主要在这组例程的实现内容，而不是结构。
- 有一部分内核驱动同时是 **WDM 驱动**：遵循 Windows Driver Model，必须支持 PnP 和电源管理。（注：本指南的 WDM 章节会细讲；现代新驱动官方更推荐 KMDF，但 KMDF 并不取代 WDM，理解 WDM 仍是前提。）

**第二刀：内核驱动在堆栈中的三层。** 同一个设备的驱动们竖直叠成一摞（驱动堆栈），按位置分三类：

- **最高层驱动（highest-level）**：典型是文件系统驱动（FSD），如 NTFS、FAT、CDFS。它们最贴近应用语义（"读文件偏移 X 的 N 字节"），但**永远依赖下层驱动**把语义翻译成具体设备操作。
- **中间层驱动（intermediate）**：同样依赖下层支持，再细分为三种：
  - **功能驱动（function driver）**：真正操纵某个具体外设的驱动，处理对该设备的读写，是设备的主驱动；
  - **过滤驱动（filter driver）**：插在功能驱动之上或之下，拦截/修改经过的请求（加密、监控、兼容性修补都爱用这一层——逆向时最常打交道的也是它）；
  - **软件总线驱动（software bus driver）**：自己呈现出一组"子设备"，供更高层驱动挂载，典型是多功能适配器（一块板卡上有多种异构设备）的驱动。
  - 此外，导出类/微类（class/miniclass）接口的系统类驱动，本质也是一对中间层驱动：类驱动 + 厂商微驱动组合起来等价于一个功能驱动或软件总线驱动。
- **最低层驱动（lowest-level）**：直接控制 I/O 总线（如 PCI 总线驱动），**不依赖任何下层驱动**。它们与 PnP 管理器协作，为总线上所有子设备配置硬件资源（设备内存映射、IRQ 等）；历史上由 HAL 承担的一部分总线功能在 Windows 2000 后被总线驱动接管。另外，直接控制某个物理设备的旧式（legacy）驱动也属于最低层。

一个具体的堆栈例子（指南原文）：打开操纵杆 → joystick 驱动 → USB 集线器驱动 → USB 主控制器驱动 → PCI 总线驱动，IRP 在这条栈里逐层传递。**关键推论**：栈中任何一层不及时、正确地处理并传递 IRP，整条栈都会出问题甚至崩溃。

### 3.2 设计目标逐条解读（7 条）

这 7 条不是口号，每一条都对应一组硬性编程纪律：

1. **可移植（Portable）**——同一份源码换平台重新编译就能跑。纪律：用 C 写（不用汇编）、只通过 WDK 提供的接口与头文件与系统交互（主头文件 `Wdm.h`/`Ntddk.h`）、不依赖尺寸/布局可变的数据类型、不调用带状态的或系统已有替代品的标准 C 运行时函数、平台相关定义隔离在 `#ifdef` 内。**为什么能成立**：因为系统组件彼此只通过导出例程通信（见"基于对象"），实现换血、接口不变，调用方就不用改。
2. **可配置（Configurable）**——设备硬件资源（I/O 端口、IRQ 等）可被系统动态指派，驱动里**不许硬编码**资源值，也不许轮询设备去猜资源。PnP 管理器维护设备树，并为每个设备保存两份清单：能用的资源 / 实际指派的资源，随插拔动态重排。同样，"可配置"还要求驱动不假设栈的上下邻居是谁——同一个磁盘驱动要能同时伺候多个文件系统、容错（镜像/条带）中间驱动。
3. **永远可抢占、永远可中断（Always Preemptible and Always Interruptible）**——调度权永远在系统手里。线程按内核的优先级方案运行，普通线程时间片轮转，实时优先级线程也只是"跑到完成或被更高实时优先级抢占"（Windows 并非硬实时系统）。代码当前运行的 IRQL 决定了它在中断维度的"地位"：PASSIVE_LEVEL（线程通常在此级，不屏蔽任何中断）< APC_LEVEL < DISPATCH_LEVEL < 设备 IRQL（DIRQL）< 系统关键中断（时钟、总线错误等占最高级）。**推论**：在高 IRQL 上停留越久，系统延迟越差，所以高 IRQL 例程必须短；很多支持例程只能在 PASSIVE_LEVEL 调用（因为它们是可分页代码或要访问可分页数据），调用前先确认自己所处的 IRQL，是驱动编程的日常动作。
4. **多处理器安全（Multiprocessor-Safe）**——目标平台是 SMP：所有 CPU 对等、共享内存、每个 CPU 都能接中断。单处理器上"天然串行"的操作，在 SMP 上真的会并行：一个例程处理新请求的同一瞬间，另一个例程可能正在另一颗 CPU 上和设备对话。纪律：凡驱动例程间共享的数据、凡物理设备本身，访问前必须同步。工具分工：能等待的场景用内核分发器对象（事件、互斥体、信号量、定时器、线程）；DISPATCH_LEVEL 及 DIRQL 场景**只能用自旋锁**。自旋锁的两条内核策略——同一时刻只有一个持有者；获取自旋锁必须在该锁绑定的 IRQL 上——本质上是把"中断屏蔽"和"互斥"焊在了一起。
5. **基于对象（Object-Based）**——系统资源统一抽象为对象：文件对象表示"应用与设备的连接"，设备对象表示逻辑/虚拟/物理设备，驱动对象表示驱动的加载映像，这些都由 I/O 管理器定义。组件之间只通过对方导出的支持例程操作对象；对象对外部可以是不透明的。**对逆向者的翻译**：你在 WinDbg 里看到的 `_FILE_OBJECT`、`_DEVICE_OBJECT`、`_DRIVER_OBJECT`、`_EPROCESS`，全是这套对象体系的实例；句柄表里存的也是对象引用。
6. **包驱动 I/O 与可复用 IRP（Packet-Driven I/O with Reusable IRPs）**——I/O 管理器的流水线是：接收请求 → 造 IRP → 路由到合适的驱动 → 跟踪直到完成 → 把状态回给请求方。IRP 的结构（固定头 + 每驱动一份堆栈位置）使它天生为"接力"设计：每层驱动只看自己那份堆栈位置里的参数干活，干完把 IRP 往下传，或者自己再造/复用一张 IRP 发给更低层。**这是整个 Windows I/O 体系的中枢概念，后面第 6、7 批会整整两批讲它。**
7. **支持异步 I/O（Supporting Asynchronous I/O）**——请求方不等结果就能继续跑，这是系统吞吐的关键。代价是复杂度全部转移给驱动：处理顺序不可假设、完成通知靠回调（IoCompletion 例程）、中间状态要自己找地方存（设备扩展就是为此设的"每设备行李箱"）。可以说，Windows 驱动编程的大部分"难"，难在这条和第 3、4 条的叠加。

**附：示例驱动与 Surface 最佳实践（本批扫读即可）**。WDK 自带示例（装完在 `src\general` 下，GitHub 上也维护）：通用骨架类的 toaster（WDM 示例套件）、IOCTL 示例、obcallback（进程保护回调示例）、regfltr（注册表过滤）、tracedrv（WPP 跟踪）等，是后面各批的现成对照代码。Surface 团队最佳实践是一份"常见翻车清单"，与本批概念直接相关的几条：IOCTL 缓冲区不校验长度就用；在分发例程里无期限等待；不开 Driver Verifier 测试；不把可分页代码标为可分页、在内核栈上放大结构体；用全局变量存每设备状态（应放设备/对象上下文）；持有锁时调用其他驱动（死锁头号来源）；该用系统同步原语却自己用 interlocked 操作拼锁。这些条目现在当"气味清单"记住，后续批次会逐条落到机制上。

### 3.3 九大管理器逐个职责

> 通用规则：与某管理器直接打交道的例程带它的前缀。驱动与每个管理器的典型接触场景一并给出。

**① 对象管理器（Object Manager，前缀 `Ob`）**——全系统对象的"户籍科"。在内核里，文件、设备、同步机制、注册表键……一切资源都表示为对象；对象 = 头（名称、类型、安全等元信息）+ 体（各类型自有数据），系统有 25 种以上对象类型（文件、设备、线程、进程、事件、互斥体、信号量、注册表键、作业、节、访问令牌、符号链接……）。对象管理器的五大职责：管对象的创建与销毁；维护对象命名空间数据库（即对象目录树）；跟踪每个进程占用的资源；跟踪对象的访问权以提供安全；管理对象生命周期、在引用归零时自动销毁回收。**驱动接触场景**：你创建的每个设备对象都登记在它的命名空间里（`\Device\…`、`\DosDevices\…` 符号链接）；安全/监控类驱动还会用 `ObRegisterCallbacks` 在进程句柄被打开/复制时拦截——示例驱动 obcallback 演示的正是这个。

**② 内存管理器（Memory Manager，前缀 `Mm`）**——管物理内存（RAM）的总账房。职责是虚拟内存的动态分配与回收，并支撑内存映射文件、共享内存、写时复制（copy-on-write）等概念。**驱动接触场景**：分配池内存背后的分页/非分页规则、把物理地址映射为虚拟地址（`MmGetPhysicalAddress` 是其典型例程）、处理用户缓冲区时锁定页面（MDL）等，都归它管。第 4 批会系统展开，本批先建立"内存种类与可分页性由它说了算"的概念。

**③ 进程和线程管理器（Process and Thread Manager，前缀 `Ps`）**——管"谁在运行"。进程是正在运行的程序实例（有 ID），线程是进程内真正被调度执行的实体（有 ID），一个进程可以有多个线程；它负责所有线程的执行调度衔接。**驱动接触场景**：`PsCreateSystemThread` 建系统线程；注册进程/线程创建通知与镜像加载通知回调（`PsSetCreateProcessNotifyRoutineEx` 等）是 EDR/安全驱动的标配眼睛。文档对这类通知回调有一组专门纪律：回调要短小、不要在回调里调用户态服务验证、不要做注册表调用、不要做阻塞/IPC 调用、不要与其他线程同步（易重入死锁）、慢活儿丢给系统工作线程——这组"不许"本身就是理解通知回调执行环境（时机敏感、上下文特殊）的最好教材。另注意 Win10 起的子系统进程（WSL）也是它管辖的变体。

**④ I/O 管理器（I/O Manager，前缀 `Io`）**——驱动的"总机 + 邮局"，本批分量最重的一个。它管理应用与设备驱动接口之间的通信：设备速度与系统速度不匹配，所以通信主要靠 IRP 这种"数据包"完成——与网络包、窗口消息包是同类设计。它定义了驱动要实现的标准例程集合，维护 IRP 的创建、路由、跟踪与完成，并提供分层堆栈模型让多个驱动协作完成一次 I/O。**两个子组件**：PnP 管理器与电源管理器挂在它名下。**驱动接触场景**：几乎全部——`IoCreateDevice` 造设备对象、`IoCallDriver` 把 IRP 递给下一层、完成例程、取消逻辑……驱动的一生都在和它打交道。它也是从逆向视角看驱动时最先要盯住的组件：一个驱动导出了哪些分发例程、怎么处理 IRP，基本决定了它的行为轮廓。

**⑤ PnP 管理器（Plug and Play Manager，无前缀）**——管"设备来了/走了，系统怎么办"。PnP 是硬件技术 + 软件技术的组合，使 PC 能在设备接入时自动识别、配置几乎无需用户干预（如插入 U 盘自动挂载）。它在组织上是 I/O 管理器的子系统；**没有直接以它命名的例程前缀**，驱动与它的互动主要通过 PnP 类 IRP（`IRP_MJ_PNP` 及一堆次要功能码）和通知机制完成，资源（IRQ、内存窗口等）的仲裁也由它与总线驱动协作完成。**驱动接触场景**：WDM 驱动必须实现 `AddDevice` 并处理启动/停止/移除设备的 PnP IRP——第 10 批的主题。

**⑥ 电源管理器（Power Manager，前缀 `Po`）**——管全机与单设备的电源状态有序变迁（工作/睡眠/休眠/关机）。它与策略管理器协作：收集电源状态变更请求、决定各设备应按什么顺序变迁、再用**电源 IRP** 通知相应驱动执行（驱动还可能要继续通知自己的子设备）。驱动需要能感知的信息包括：系统活跃度、电量、关机/睡眠/休眠请求、用户按电源键、控制面板的电源策略（如电量 10% 自动关机）。**驱动接触场景**：处理 `IRP_MJ_POWER`，以及 `PoSetPowerState`/`PoCallDriver` 这类调用；写得不好的电源处理是蓝屏 0x9F（DRIVER_POWER_STATE_FAILURE）的经典来源。第 11 批展开。

**⑦ 配置管理器（Configuration Manager，前缀 `Cm`）**——管注册表。它是 INI 文件时代的继承者：注册表统一存放硬件与软件的持久化配置。驱动想知道某个注册表数据何时变化时，可以在指定数据上注册回调（`CmRegisterCallback` 是其典型例程），数据一变回调就被触发。**驱动接触场景**：读自己的参数键、监控注册表（自保护/行为监控驱动常用注册表回调做拦截，即所谓 registry filtering）。第 12 批会回到这块。

**⑧ 内核事务管理器（Kernel Transaction Manager，KTM）**——把"多步读写要么全成、要么全回滚"的事务语义带进内核。多个数据存储上的读写需要原子性时，把操作组成一个事务：全部成功才提交（commit），中途失败就回滚（rollback）到原始状态。它是用户态事务型 NTFS（TxF）的平台基础。**驱动接触场景**：普通设备驱动很少直接用它；文件系统与需要事务日志的组件才会打交道，属于"知道它存在、知道它解决什么问题"即可的管理器。

**⑨ 安全参考监视器（Security Reference Monitor，前缀 `Se`）**——访问控制的裁决者。任何动作发生前，系统必须确认它不违反安全策略；Windows 用访问控制列表（ACL）决定各对象的安全属性，安全参考监视器提供让驱动参与访问控制的例程（如 `SeAccessCheck` 执行一次访问检查）。**驱动接触场景**：创建设备对象时给它设安全描述符（SDDL）决定"谁能打开这个设备"；在 IOCTL 处理里判断调用方权限；以及理解为什么对象管理器查安全要来问它。注意分工：对象管理器负责"跟踪访问权"（记账），安全参考监视器负责"按 ACL 做判定"（裁决）——第 5 批的主角。

### 3.4 库类组件速览

库不拥有资源、不做裁决，它们是给驱动（及其他内核组件）直接调用的例程集合：

| 库 | 前缀 | 内容与要点 |
|---|---|---|
| **内核库（Kernel Library）** | `Ke` | 内核本体提供的最底层机制：线程调度、硬件中断路由等"其他一切都依赖之"的核心功能。设计要求是**快而简单**。如 `KeGetCurrentThread`。文档特意注明：现在的 Windows 内核**不是微内核**，别套微内核概念。 |
| **执行体支持库（Executive Support Library）** | `Ex` | 执行体各管理器之外的通用服务集合（对象、内存、进程线程、I/O、配置管理等服务的通用接口层），如池分配、ERESOURCE、rundown 保护等都常从这里出。如 `ExGetCurrentResourceThread`。 |
| **运行时库（Run-Time Library, RTL）** | `Rtl` | 各内核组件共用的普通工具例程：字符串、注册表辅助（如 `RtlCheckRegistryKey`）、链表、Unicode 转换等。注意内核里只能用内核版 `RtlXxx`，不能调用户模式的 `RtlXxx`。 |
| **安全字符串库（Safe String Library）** | 同为 `Rtl` | 专治字符串类安全漏洞（溢出、未终止）的一组带长度校验的字符串函数。**与 RTL 同前缀、不同库**——本批最容易记混的一对。写驱动应默认用安全字符串函数处理外部输入。 |
| **DMA 库（DMA Library）** | （经 I/O 体系的适配器对象接口） | 设备绕过 CPU 直接读写内存（DMA）的支持：适配器对象、映射寄存器、散点/聚集等机制的例程。文档特别提醒别与 "Device Memory Access"（读写 I/O 端口与寄存器的一组宏）混淆——第 9 批细讲。 |
| **HAL 库（HAL Library）** | `Hal` | 硬件抽象层：夹在硬件与系统其余部分之间，屏蔽主板/中断控制器等底层差异，本身实现为一个 DLL。官方**不鼓励**自写 HAL；驱动需要硬件级访问时用它提供的例程。 |
| **CLFS 库（Common Log File System）** | `Clfs` | 通用日志文件系统：为系统文件提供事务型日志（日志序列号、编组区、重启动记录等），与事务型文件系统/KTM 一族关系密切。普通驱动极少直接用。 |
| **WMI 库（WMI Library）** | `Wmi` | 让驱动把自己的状态、统计、事件暴露给 Windows 管理基础设施（WMI）的机制；WDM 驱动按规范应实现 WMI 支持以便"可被系统管理"。**与 WMI 的通信也是走 IRP 的**（`IRP_MJ_SYSTEM_CONTROL`）——又一次印证 IRP 的中枢地位。第 12 批细讲。 |

一句话记忆法：**管理器管"东西"（对象、内存、请求、配置、安全判定），库管"动作模板"（调度原语、字符串、DMA 套路、日志格式）**。逆向读导入表时，前缀就是第一层分组依据。

## 四、解读：结合你的背景看这一批

**1. 驱动活在什么执行环境里？** 用一张对照表压缩用户态直觉的失效点：

| 维度 | 用户态程序 | 内核驱动 |
|---|---|---|
| 进程/线程 | 有自己的进程、主线程，身份明确 | 无进程无私有线程，代码被"寄生"在任意线程上下文中执行 |
| 崩溃后果 | 进程退出 | 整机 bug check（蓝屏） |
| 可用 API | Win32/CRT，文档齐全、容错好 | 只能用 WDK 导出的支持例程，且多数带 IRQL 前置条件 |
| 内存 | 私有虚拟地址空间，缺页随便用 | 与所有内核组件共享地址空间；分页内存的使用受 IRQL 严厉限制 |
| 并发模型 | 自己决定线程模型 | 被动响应：被回调、被中断、被抢占是常态 |
| 生命周期 | main 进入、退出即结束 | 被加载、被点名（回调）、被卸载，全程听系统安排 |

从逆向转到驱动视角，最重要的心态切换是：**驱动不是"程序"，而是一组挂在系统事件上的反应代码**。你分析一个 .sys 时问的"它什么时候、在什么上下文、被谁调用"，正是这批概念里"标准例程 + 任意线程上下文 + IRQL"的具体化。

**2. 本批概念与常见分析对象的对应关系：**

- **对象目录 / 句柄表**：对象管理器的命名空间就是 WinObj 里看到的 `\Device`、`\DosDevices`、`\BaseNamedObjects` 那棵树；进程句柄表里每一项都是"某进程持有的一个对象引用 + 已授予访问权"。分析驱动通信时，从 `\DosDevices\Xxx` 符号链找到设备对象，是定位 IOCTL 入口的标准动作。
- **IRP 流向**：`!irp`、`!devstack`、IRP 跟踪在 WinDbg 里看的就是本批说的"固定头 + 每层一份堆栈位置"在逐层接力；一个请求在哪一层被挂起、被改参数、被完成，都对应本批的堆栈模型。第 6、7 批会把 IRP 拆开细看，本批先立住"包驱动 + 可复用"的心智模型。
- **过滤驱动层**：中间层过滤驱动是监控、EDR、加固类软件的标准落点——你在样本里看到某个 .sys 既不碰硬件又拦截一切 I/O，它在地图上的坐标就是"filter driver"，其行为逻辑（先看、改、再往下传 IRP）由本批的分层模型定义。
- **通知回调群**：`Ps`（进程/线程/镜像）、`Cm`（注册表）、`Ob`（句柄操作）三组回调是安全驱动的"传感器套餐"，全部出自本批的管理器地图；分析一个 EDR 驱动时，先查它注册了哪几路回调，就能勾勒它的监控面。
- **IRQL 与上下文**：逆向时看到驱动在分发例程里直接访问用户态地址、或在高 IRQL 路径上调可分页函数，往往就是 bug/漏洞点；判断依据正是本批的"任意线程上下文 + IRQL 纪律"。

**3. 为什么微软要把系统切成"管理器 + 库"？** 表面原因是模块化，深层原因是**可移植与可替换**：对象不透明 + 只认导出例程，意味着任何组件的内部实现可以整体重写而不波及调用方。这也解释了逆向中的一条经验：未文档化结构（如 `_EPROCESS` 内部偏移）跨版本漂移是常态，而文档化例程接口几十年稳定——依赖前者的工具（包括很多 hook/监控手法）注定要逐版本维护，依赖后者的则长寿。

## 五、易混点与自查

### 易混点辨析

1. **"基于对象（object-based）" ≠ "面向对象（object-oriented）"**：指南特意声明 Windows 不是经典 C++ 意义的面向对象系统。对象 = 带头信息的受管数据集合 + 只经导出例程操作；没有继承/多态那一套。看到 opaque（不透明）对象更要克制：不要因为逆向时见过它的内部结构，就在驱动代码里直接访问——那是未文档化依赖，换版本就碎。
2. **功能驱动 vs 过滤驱动 vs 总线驱动（WDM 三分类）≠ 最高层/中间层/最低层（堆栈位置三分类）**：前者按"角色"分，后者按"位置"分，是两把不同的尺子。功能/过滤驱动通常位于中间层，但"中间层"里还包含软件总线驱动和类驱动；最低层则主要是硬件总线驱动。混用两套术语是读驱动文档时最常见的迷路来源。
3. **PnP 管理器与电源管理器的"归属"**：两者都是 I/O 管理器的子组件，但只有电源管理器有自己的例程前缀（`Po`），PnP 没有（没有 `PpXxx`）——它通过 IRP 与通知机制工作。别因为没有前缀就以为 PnP 不重要：WDM 驱动合规与否，一大半看 PnP 处理。
4. **RTL 库 vs 安全字符串库**：都用 `Rtl` 前缀，指南明确说它们**不是同一个库**。RTL 是通用工具集，安全字符串库是专为字符串安全设计的带校验函数集；看到 `RtlStringCchCopyW` 这类名字要知道它出自后者。
5. **执行体（Executive）≠ 内核（Kernel）**：狭义的"内核"（`Ke`）只是执行体里的一个组件，负责调度与中断等最底层机制；对象、内存、I/O 等管理器与它平级同属执行体。口语里"进了内核"指内核模式这个大环境，别把 `KeXxx` 例程误当成"全部内核功能"的代表。
6. **DMA 库 ≠ Device Memory Access**：前者是"设备与内存直连传输"的整套机制（适配器对象、映射寄存器……）；后者只是读写 I/O 端口/寄存器的一组宏。指南专门点名防混。

### 自查问题（只给问题，答案请学完后自答）

1. 拿起任意一个你分析过的 .sys：用本批的地图，它属于哪一层（最高/中间/最低）？在 WDM 角色分类里它算功能、过滤还是总线驱动？你的判断依据是什么？
2. 为什么只有最高层驱动可以假设自己运行在发起 I/O 的线程上下文中？这个假设一旦被中低层驱动误用，会具体坏掉什么？
3. 自旋锁为什么要绑定一个 IRQL？如果允许在任意 IRQL 获取自旋锁，单处理器和多处理器上分别可能出现什么死锁形态？
4. IRP 里为什么要给"每个驱动一份 I/O 堆栈位置"，而不是一份全局参数区大家共用？这与"可复用 IRP"是什么关系？
5. 给定例程名 `PoCallDriver`、`CmRegisterCallbackEx`、`ObReferenceObjectByHandle`、`SeAccessCheck`、`MmProbeAndLockPages`：分别指出导出组件、它操作的对象类型、以及驱动最可能在什么场景下调用它。（下一批起会陆续验证你的答案。）
