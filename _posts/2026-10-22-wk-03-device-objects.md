## 一、本批地图

### 1. 一个典型设备堆栈（自下而上）与每层设备对象的创建者

```
        用户态应用 / 上层内核组件
                  │  IRP 永远先送到堆栈顶
                  ▼
   ┌─────────────────────────────────────┐
   │ 上层筛选 DO (filter DO)              │ ← 上层筛选驱动在 AddDevice 中建（IoCreateDevice）
   ├─────────────────────────────────────┤
   │ 功能设备对象 FDO                     │ ← 功能驱动在 AddDevice 中建（IoCreateDevice）
   ├─────────────────────────────────────┤
   │ 下层筛选 DO (filter DO，可有多个)    │ ← 下层筛选驱动在 AddDevice 中建
   ├─────────────────────────────────────┤
   │ 总线筛选 DO (bus filter DO，可选)    │ ← 总线筛选驱动在 AddDevice 中建
   ├─────────────────────────────────────┤
   │ 物理设备对象 PDO                     │ ← 总线驱动在响应 IRP_MN_QUERY_DEVICE_RELATIONS
   │                                        (BusRelations) 枚举子设备时建；永远位于栈底；
   │                                        是堆栈中唯一被命名的对象（系统自动生成名）
   └─────────────────────────────────────┘
        总线（PCI / USB / i8042…）
```

要点：三类设备对象**都是同一个结构 DEVICE_OBJECT**，区别只在"谁建的、代表谁看设备"。堆栈是 devnode 的一部分；PnP 管理器另外在 devnode 里维护设备是否已启动、谁注册了变更通知等信息（`!devnode` 可看）。原始模式（raw mode）设备是例外：堆栈里只有 PDO 和零个或多个总线筛选 DO，没有 FDO 和普通筛选 DO。

文档的走查例子（USB 摇杆）：根总线枚举出 PCI 总线（PDO+FDO）→ PCI 驱动枚举出 USB 主控制器（PDO+FDO，由 class/miniclass 驱动对充当功能驱动）→ USB 主控枚举出 Hub（PDO+FDO）→ Hub 枚举出 HID 摇杆（PDO + 下层筛选 DO + FDO + 上层筛选 DO）。注意**一个总线驱动横跨多个堆栈**：它既是自家控制器那个堆栈里的功能驱动（建 FDO），又是子设备堆栈里的总线驱动（建 PDO）。

### 2. 命名空间：从用户态路径到设备对象

```
用户态：CreateFile("\\\\.\\DosDeviceName", ...)
              │   \\.\ 是 Win32 侧进入 \DosDevices（即 \??）命名空间的入口
              ▼
对象管理器命名空间
   \??（即 \DosDevices，每会话视图）
      ├─ COM1 ──符号链接──► \Device\Serial0
      ├─ C:   ──符号链接──► \Device\HarddiskVolumeX
      └─ Global\...（全局视图的别名入口）
   \Device
      ├─ \Device\000000xx   ← PDO 的自动生成名（WDM 堆栈的命名锚点）
      └─ \Device\DeviceName ← 非 WDM 驱动手工命名的设备对象
              │   对命名对象的打开请求，被自动导向该对象所在堆栈的栈顶
              ▼
        堆栈顶设备对象的驱动 DispatchCreate
```

要点：**NT 设备名**是对象在 `\Device` 目录里的真名；**MS-DOS 设备名**是 `\DosDevices`（`\??`）目录里的一个符号链接对象，指向 NT 设备名——它存在的唯一理由是兼容 DOS/Win32 路径习惯（`COM1`、`C:`）。WDM 驱动通常不建符号链接，改用**设备接口**（IoRegisterDeviceInterface 注册 GUID 接口，本质上是系统替你管理的一组指向 PDO 的符号链接）对外暴露设备。

## 二、核心要点

1. **设备对象是设备在内核中的"户籍与收件地址"**：操作系统用 DEVICE_OBJECT 表示设备，所有针对设备的操作都以它为目标；没建设备对象的驱动收不到任何给该设备的 IRP。纯软件驱动（不碰硬件）同样必须建设备对象——它代表的是"操作的逻辑目标"。

2. **三类设备对象是同一结构、三种角色**：PDO 由总线驱动建、永远在栈底，代表"总线眼中的这个设备"，同时也是 PnP/电源/I/O 管理器眼中的设备本体；FDO 由功能驱动建，代表设备的功能面；filter DO 由各类筛选驱动建。各有各自的 device extension。

3. **堆栈按固定顺序自下而上长出来**：总线驱动响应 IRP_MN_QUERY_DEVICE_RELATIONS（BusRelations）时建 PDO → 总线筛选 → 下层筛选 → 功能驱动建 FDO → 上层筛选，每一步都是 PnP 管理器确保驱动已加载后调用其 AddDevice、由驱动 IoCreateDevice + IoAttachDeviceToDeviceStack 挂到当前栈顶。PnP 与电源 IRP 必须一路下传到 PDO，任何一层不得私自"吞掉"。

4. **DeviceExtension 是驱动的"每设备全局变量区"**：由 IoCreateDevice/IoCreateDeviceSecure 在创建时按驱动给定的尺寸从非分页池分配、清零，与设备对象同生共死。驱动跑在任意线程上下文里，没有线程局部状态可依赖，设备状态、内核对象（定时器/DPC/中断对象指针）、下层设备对象指针几乎全存这里。

5. **WDM 的命名规则是反直觉的：只有 PDO 被命名，且名字是系统生成的**：总线驱动建 PDO 时带 FILE_AUTOGENERATED_DEVICE_NAME 特征，系统自动生成 `\Device\000000xx` 式的名字；FDO 与 filter DO **不许命名**——给它们命名会绕过 PnP 管理器的安全安排。非 WDM 驱动才需要自己给设备对象起 `\Device\Xxx` 的名（且至少要有一个命名对象，否则用户态够不着）。

6. **一个堆栈只许有一个命名对象，因为安全检查只认命名对象**：对命名对象的任何打开请求都会被自动导向栈顶；系统按"被命名的那个对象"的安全描述符做访问检查。若同栈两个对象各有名字、各有不同强度的安全描述符，攻击者可以冲着弱的那个名字发请求、却打到强的那个对象上——所以"一栈多名"是明确禁止的反模式。

7. **MS-DOS 设备名分本地与全局两套，且本地遮蔽全局**：全局 `\DosDevices` 系统级可见；每个登录会话（XP 起以 AuthenticationID 区分；Win2000 是终端服务会话）有自己的本地 `\DosDevices`。对象管理器查名时先本地、后全局，同名时本地赢——这就是为什么 A 用户映射的 X: 盘对 B 用户和系统服务不可见。驱动要建全局符号链接，必须在系统线程上下文（如 DriverEntry）里建，或显式写 `\DosDevices\Global\Xxx`。

8. **IoCreateDevice 与 IoCreateDeviceSecure 的分工由"谁需要给安全描述符"决定**：WDM 功能/筛选驱动一律用 IoCreateDevice（不命名、走 PnP 默认安全）；总线驱动建可 raw-mode 的 PDO 必须用 IoCreateDeviceSecure，需要比总线默认更严的安全描述符时也用它；非 WDM 驱动建命名对象用 IoCreateDeviceSecure。用 Secure 版时 DeviceClassGuid 必须用自创的新 GUID，套用现有设备类 GUID 会污染那个类的安全设置与兼容性。

9. **设备对象的四类属性——类型、特征、独占、安全描述符——都可在创建时给默认值、且注册表设置覆盖之**：INF 在安装时（设备级 DDInstall.HW 或类级 ClassInstall32 的 AddReg，用 DeviceType / DeviceCharacteristics / Exclusive / Security 四个关键字），或安装后由管理员用户态程序经 SetupDiGet/SetDeviceRegistryProperty（SPDRP_*）修改，都会覆盖驱动创建时的取值。这意味着：驱动代码里写的属性不是最终裁决，部署配置能改。

10. **特征标志分两种作用域：单对象级与整栈级**：FILE_DEVICE_SECURE_OPEN、FILE_REMOVABLE_MEDIA、FILE_FLOPPY_DISKETTE、FILE_READ_ONLY_DEVICE、FILE_WRITE_ONCE_MEDIA 属于整栈级——只要在注册表或任一 FDO/filter DO 上设置，PnP 管理器就把它同步到全栈每个设备对象；FILE_AUTOGENERATED_DEVICE_NAME 只对单个对象（PDO）有意义。绝大多数驱动实际只设一个特征：FILE_DEVICE_SECURE_OPEN。

11. **FILE_DEVICE_SECURE_OPEN 是命名空间安全的总闸**：它保证对设备命名空间内**任何**打开请求（包括 `\Device\X\任意后缀路径` 这种打开）都套用同一套安全设置。没有它，I/O 管理器只校验设备名本身那一级的访问权，尾随名字（trailing name）部分的安全语义会不一致——这是路径型攻击的经典缝隙（详解见三之 5）。

12. **独占（Exclusive）是个"按名字"的单句柄语义，且 WDM 下只能由 INF 设置**：独占开启后，同一命名对象同时只许打开一个句柄（同一句柄内多线程重叠 I/O 不受限）。WDM 堆栈里被命名的是 PDO、而 PDO 是总线驱动替功能驱动建的，所以功能驱动自己调 IoCreateDevice 时给 FDO 设 Exclusive **毫无作用**，必须在类或设备的 INF 里经 AddReg 设置。非堆叠的非 WDM 驱动和 raw-mode 设备则可用 IoCreateDeviceSecure 自行设置。

13. **初始化设备对象时有几件"挂栈即自动、手工要补"的事**：IoAttachDeviceToDeviceStack 会自动把上层设备对象的 StackSize 设为"下层 StackSize + 1"、AlignmentRequirement 设为下层的值；但 DO_BUFFERED_IO / DO_DIRECT_IO 标志要驱动自己在每个设备对象上设（中间层必须与下层保持一致），DO_DEVICE_INITIALIZING 必须由功能/筛选驱动亲手清除（第 2 批已提），可移动介质的 DO_VERIFY_VOLUME、电源相关的 DO_POWER_INRUSH / DO_POWER_PAGABLE 按设备情况补设。

14. **邻居的设备对象是"只读展品"**：上层驱动可以读下层设备对象（典型是读 StackSize 来给自建 IRP 定层数），但**永远不许写**下层设备对象（唯一例外：文件系统对下层可移动介质驱动的 DO_VERIFY_VOLUME 标志位）；**永远不许访问下层的 device extension**——两个驱动之间没有安全的扩展同步办法，这种后门通信会让两驱动无法独立升级、中间插不进新筛选层。驱动间通信只许走 IRP + IoCallDriver。

## 三、关键知识点详解

### 1. 三类设备对象与堆栈构成

**PDO（Physical Device Object）**。创建者是父总线驱动，时机是它响应 PnP 管理器的 IRP_MN_QUERY_DEVICE_RELATIONS（BusRelations）枚举子设备时——只有"自上次查询以来新出现在总线上的设备"才新建 PDO。PDO 有三重身份：（a）对总线驱动，它是"我枚举到的这个孩子"；（b）对 PnP/电源/I/O 管理器等系统组件，它是这个设备的官方代表；（c）对整个堆栈，它是栈底锚点和唯一命名对象。注意"设备"会嵌套：SCSI 适配器插在 PCI 总线上，PCI 驱动为它建 PDO；而 SCSI 适配器自己的堆栈里，它的功能驱动建 FDO——同一个物理物在父堆栈里是"子设备 PDO"，在自家堆栈里是"总线控制器 FDO 所代表的设备"。

**FDO（Functional Device Object）**。创建者是功能驱动，时机是 PnP 管理器在确定功能驱动后调用其 AddDevice。FDO 代表设备的功能面——读写、IOCTL、电源策略等实际"业务"都在这一层落实。文档特别提醒一类瘦身形态：class/miniclass、port/miniport 驱动对合起来才是一个功能驱动、只建**一个** FDO（第 2 批已述）。

**Filter DO**。按位置分三种：总线筛选 DO（挂在 PDO 之上、FDO 与下层筛选之下，例：ACPI 筛选）、下层筛选 DO（FDO 之下，改硬件呈现行为）、上层筛选 DO（FDO 之上，做增值处理）。每一类都遵循同一规则：PnP 管理器先于它下面的层加载它、调 AddDevice，它判断"这个设备与我有关"才建 DO 并挂栈，无关就什么都不建地返回成功（第 2 批已述失败的代价）。

**堆栈的几个结构性事实**：
- 所有设备（含总线适配器、非总线设备）都有 PDO + FDO；raw mode 是唯一的"只有 PDO"形态（外加可选总线筛选 DO）。
- IRP 永远发给栈顶对象；堆栈用"命名对象的名字"来标识（或用符号链接、设备接口这样的别名）。
- 设备对象由对象管理器管理，与其他内核对象同样可命名、可被打开句柄——第 1 批"基于对象"在这里具体化了。
- minidriver 型驱动（有 class/port 驱动罩着的）和 NDIS 这类子系统驱动是例外：设备对象由 class/port 驱动或子系统代建，mini 驱动只收被转发的请求。

### 2. 创建、初始化与设备扩展

**IoCreateDevice / IoCreateDeviceSecure 的入参就是设备对象的"出生配置"**：device extension 大小；DeviceType 常量；一个或多个按位或的 DeviceCharacteristics；Exclusive 布尔（WDM 驱动必须传 FALSE，独占改走 INF，见核心要点 12）；所属 DRIVER_OBJECT 指针（AddDevice 的入参或 DriverEntry 里拿到）；可选的 DeviceName（WDM 非总线驱动不传）。创建成功后，I/O 管理器分配设备对象及全部附属结构，device extension 清零，存于非分页池。

**按角色的创建路线**（文档明确给出）：
- WDM 功能/筛选驱动：IoCreateDevice，一般在 AddDevice 里调（个别如磁盘驱动要在 Dispatch 例程里响应布局 IOCTL 时建，属例外）。
- WDM 总线驱动建 PDO：设备可 raw-mode → 必须 IoCreateDeviceSecure；不可 raw-mode → 两者皆可，总线默认安全够用用 IoCreateDevice，想更严用 IoCreateDeviceSecure 指定安全描述符。
- 非 WDM 驱动：未命名对象用 IoCreateDevice，命名对象用 IoCreateDeviceSecure；未命名对象用户态打不开，所以至少建一个命名对象。

**初始化清单（IoCreateDevice 返回后、挂栈前后）**：
- **StackSize**：新建时为 1；IoAttachDeviceToDeviceStack 自动设为下层值+1。个别设备类型文档可能要求更大，按设备类文档办——它决定了发给本对象的 IRP 预留多少层 I/O 堆栈位置。
- **AlignmentRequirement**：新建时为"处理器缓存行大小−1"（为直接 I/O 缓冲对齐兜底）。最低层物理驱动要把本设备对齐要求−1 后与现值取大；走 IoAttachDevice*/IoGetDeviceObjectPointer 挂到下层之上的高层驱动，此字段会被自动设为下层的值；总则：高层驱动不要擅自改它。
- **数据传输方式标志**：中间层与最低层驱动在每个设备对象上设 DO_BUFFERED_IO 或 DO_DIRECT_IO 之一——注意这不是每对象独立选择，中间层必须与下层一致，因为这个标志决定 I/O 管理器今后如何把用户缓冲区递给整条链。
- **其他 Flags**：可移动介质 DO_VERIFY_VOLUME、需要涌入电源的设备 DO_POWER_INRUSH、不在分页路径上的设备 DO_POWER_PAGABLE；功能/筛选驱动必须清除 DO_DEVICE_INITIALIZING（设备从"初始化中"转为"可被 I/O 管理器投递请求"，时机与含义第 2 批已述）。
- **扩展内对象的初始化时机**：能熬过 PnP start/stop 的对象与数据在 AddDevice 里初始化；依赖 START_DEVICE 才下发的资源信息、或 stop/restart 时会变的，推迟到处理 IRP_MN_START_DEVICE 时初始化。

**DeviceExtension 的规划**。它的内容与布局完全由驱动自定义，是大多数中间层与最低层驱动**最重要**的数据结构，常存：设备状态机状态；驱动用到的内核对象本体或指针（KTIMER、KDPC、自旋锁；有 ISR 的驱动必存中断对象指针，一 ISR 管多设备或多 ISR 时还要存中断自旋锁）；自家设备对象指针、**下层设备对象指针**（IoCallDriver 下传时要用，就是 AddDevice 里 IoAttachDeviceToDeviceStack 的返回值存这里）；设备的资源列表副本等。两个"邻居礼仪"再次强调（见核心要点 14）：扩展是私有领地，上层连看都不许看；要传数据，走 IRP。

### 3. 命名体系与符号链接

**NT 设备名**。形如 `\Device\DeviceName`，是设备对象在对象管理器 `\Device` 目录里的名字。对 WDM，这个体系被系统接管成统一方案：PDO 由系统自动命名（总线驱动只管在创建时带上 FILE_AUTOGENERATED_DEVICE_NAME），FDO 与筛选 DO 不命名——理由除了防撞名，更重要的是**安全检查锚点的唯一性**（核心要点 6）。非 WDM 驱动则必须自己在建对象时把名字作为 DeviceName 参数传入 IoCreateDeviceSecure，至少建一个命名对象到 `\Device` 下才收得到请求。

**打开请求的落点规则**：对某个命名对象的打开，自动送达该对象**所在堆栈的栈顶**——名字只是堆栈的门牌号，接待的永远是栈顶那一层。这解释了一个常见困惑：你打开的是 PDO 的名字，第一手处理 Create 的却是上层筛选驱动。

**MS-DOS 设备名与符号链接**。`\DosDevices\COM1` 这类名字本身是对象管理器里的一个 SymbolicLink 对象，由 IoCreateSymbolicLink（或 IoCreateUnprotectedSymbolicLink）创建，目标指向 NT 设备名。用户态用 `\\.\` 前缀进入这套命名空间（`CreateFile("\\\\.\\COM1")`），用户态程序也能用 DefineDosDevice 自建这类链接。只有设备必须拥有众所周知的 DOS 名（如 COM1）时才需要手工建；WDM 的正道是设备接口。

**本地与全局 `\DosDevices`（`\??`）**。系统维护一个全局目录加每会话一个本地目录：
- XP 起，本地上下文按**登录会话**划分（以令牌的 AuthenticationID 标识）；Win2000 按终端服务会话（SessionId）划分，且新会话启动时把全局目录**拷贝**一份作本地目录、此后全局变更不再同步；XP 起改为**查找顺序**语义：先本地后全局、本地同名遮蔽全局。
- 系统线程与 LocalSystem 身份的线程**不在**任何本地上下文里，它们就在全局上下文中。
- 每个线程有"当前 DosDevices 上下文"，且可随生命期变化——于是同一个驱动例程在不同调用者线程里执行时，建出的符号链接可能落进不同会话的本地目录。这是"在 Dispatch 里建符号链接，链接却只有某个用户看得见"这类怪象的根源。
- 驱动要确保建到全局：或在必定运行于系统线程上下文的例程（如 DriverEntry）里建，或直接用 `\DosDevices\Global\DosDeviceName` 路径（注意 `\DosDevices\Global` 在不支持本地/全局区分的老平台不存在，文档给了 IoIsWdmVersionAvailable 判断的兼容写法）。
- 反过来也可以利用本地性：在响应某会话线程发来的 IOCTL 时建符号链接，它自然落进那个会话的本地目录，实现"每用户一份设备名"。

### 4. 属性：类型、特征与独占

**DeviceType（DEVICE_OBJECT.DeviceType）**。表示底层硬件的种类，取值是系统定义的 FILE_DEVICE_* 常量（Ntddk.h / Wdm.h）：FILE_DEVICE_DISK(0x7) 覆盖磁盘分区及一切"看起来像磁盘"的对象、FILE_DEVICE_KEYBOARD(0xB)、FILE_DEVICE_NETWORK(0x12)、FILE_DEVICE_UNKNOWN(0x22) 等。规则：0–32767 为微软保留，必须用系统常量对应已有类型；中间层驱动一般沿用底层设备的类型（如容错磁盘驱动 ftdisk 建的对象仍是 FILE_DEVICE_DISK，不为镜像集另立新类型）；硬件对不上任何已定义类型时，用 FILE_DEVICE_UNKNOWN 或 32768–65535 区间的自定义值——这个区间是第三方的安全区，不会与微软将来新增的常量撞车。

**Characteristics（DEVICE_OBJECT.Characteristics）**。标志位集合。按作用域分两类：
- **整栈级**（FILE_DEVICE_SECURE_OPEN、FILE_FLOPPY_DISKETTE、FILE_READ_ONLY_DEVICE、FILE_REMOVABLE_MEDIA、FILE_WRITE_ONCE_MEDIA）：在任一 FDO/filter DO 上设置或在注册表设置，PnP 管理器都会把它传播到全栈（含 raw-mode 时的 PDO）。注册表值的优先级：**设备级设置 > 设备类级设置 > 0**。
- **单对象级**（如 FILE_AUTOGENERATED_DEVICE_NAME，仅用于 PDO）：只影响本对象，创建时指定。
大多数驱动实际只设 FILE_DEVICE_SECURE_OPEN 一个（见下节）。

**Exclusive（独占）**。语义是 I/O 管理器按"名字"执行的单打开限制：同一命名对象同时仅一个句柄；独占只限制**句柄数**，不限制单句柄上的多线程重叠 I/O。两个容易误判的边界（原文明确）：
- 独占是对"名字本身"执行的，不看尾随名：对 `\Device\DeviceName\File1` 的打开与对 `\Device\DeviceName\File2` 的打开算同一次独占占用。
- 相对打开（relative open，基于已有句柄再打开）不走这套强制；若堆栈里出现两个命名对象（明确不推荐），I/O 管理器会**每个名字各放一个句柄**，独占的整体性要驱动自己在 Dispatch 里兜底。

**注册表设置属性的位置与方式**。安装时：设备级在 INF 的 DDInstall.HW 段的 AddReg 里写，类级在 ClassInstall32 段的 AddReg 里写，关键字就是 DeviceType / DeviceCharacteristics / Exclusive / Security 四个。安装后：管理员权限的用户态程序可用 SetupDiGetDeviceRegistryProperty / SetupDiSetDeviceRegistryProperty（SPDRP_DEVTYPE / SPDRP_CHARACTERISTICS / SPDRP_EXCLUSIVE / SPDRP_SECURITY（二进制 SECURITY_DESCRIPTOR）/ SPDRP_SECURITY_SDS（SDDL 字符串）），类级则用 SetupDiGet/SetClassRegistryProperty。**注册表值覆盖创建时值**——审计时看到的生效属性，应以"创建参数 + INF/注册表覆盖"的合成结果为准（对照 `!devobj` 输出的 Characteristics/SecurityDescriptor 字段才是最终态）。

### 5. 命名与访问的安全边界

这一节把前面几处散落的安全规则收成一张图，因为它们共同决定了"用户态进程打开一个设备时，到底谁被检查、检查什么"：

1. **检查锚点唯一化**：系统只对堆栈中被命名的对象（WDM 下即 PDO）的安全描述符做访问检查，且打开被自动导向栈顶。因此安全描述符的"挂载点"与请求的"入口点"是分离的：SDDL 写在 PDO 上，生效在全栈。一栈多名会制造出"从弱 SD 的名字进、打到强 SD 的对象"的绕行通道，文档明文禁止。

2. **命名本身即攻击面，所以"只在必要时命名"**：官方重要提示原文——仅在必要时（遗留应用按名打开、非 PnP/控制设备对象）才命名设备对象。PnP 驱动给 FDO 命名会"绕过 PnP 管理器的安全特性"（创建小节原文），因为命名对象脱离了设备接口 + PDO 安全描述符这套统一安排，成为一条不受 INF/类安全策略覆盖的旁路。WDF 驱动也不需要靠命名来建符号链接。

3. **IoCreateDeviceSecure 的正确用法**：用于需要自定义安全描述符的命名对象（及 raw-mode PDO 等场景）。两个纪律：（a）必须传**自建的新类 GUID**作 DeviceClassGuid，套用既有类 GUID 会把你的安全设置写进别人的类、或被别人的类设置污染；（b）SDDL 的内容设计（哪些主体能开、能读写还是只能读）属于第 5 批"安全性"章的 Controlling Device Access / SDDL for Device Objects，本批只需记住"Secure 版 = 命名 + 自带 SDDL + 自建类 GUID"这一组绑定关系。

4. **FILE_DEVICE_SECURE_OPEN 与尾随名（trailing name）**：设备对象可以像目录一样被"带路径打开"——`\Device\X\SomePath`，尾随部分由驱动的 DispatchCreate 自行解释（有的驱动用它做子对象寻址）。风险在于：若不设 FILE_DEVICE_SECURE_OPEN，对尾随路径打开的访问检查可能只验到设备名一级；设了它，I/O 管理器保证**进入该设备命名空间的任何打开请求都套用相同的安全设置**（原文："ensures that the same security settings are applied to any open request into the device's namespace"）。独占语义同样是"按名字整体"执行的（核心要点 12 的第一条边界与此呼应：File1/File2 共用同一独占额度）。更细的命名空间访问控制（Controlling Device Namespace Access、FILE_DEVICE_SECURE_OPEN 如何影响 IRP_MJ_CREATE 中的 FileName 检查）是安全章的内容，第 5 批展开；本批记住结论：**不设 SECURE_OPEN 的命名设备，其 Create 路径解析就是审计重点**。

5. **谁有权改属性，谁就有权改安全姿态**：注册表里的 Security/DeviceCharacteristics/Exclusive 覆盖创建值，而写这些键走的是设备安装基础设施（管理员或安装程序）。换言之，一个驱动的实际暴露面不只取决于 .sys 二进制，还取决于 INF 与后续 SetupDi* 调用——做驱动安全评估时，INF 与二进制要一起看。

## 四、解读（结合逆向 / 取证 / 攻防背景）

**在 WinDbg 里读懂一台真实机器的设备森林。** 本批概念与调试命令是一一对应的：`!devstack <devobj>` 自下而上列出一个堆栈的全部设备对象及所属驱动——你应当能立刻标注哪层是 PDO（最下、属于总线驱动）、哪层是 FDO、哪些是 filter DO；`!devobj <devobj>` 给出单个对象的 DeviceType、Characteristics、Flags、AttachedDevice（栈中上一层）、设备名等字段，正好用来核对本批的属性体系；`!devnode` 看 devnode 层面（设备是否 started、驱动列表）；在对象管理器命名空间里浏览（WinObj 或 `!object \Device`、`!object \??`）则能把"名字 → 符号链接 → 设备对象 → 堆栈"这条链走通。逆向一个陌生驱动时，**先 `!object \??` 找它建的符号链接、再顺藤摸到设备对象和堆栈**，是定位其用户态可达入口的标准起手式。

**符号链接是 IOCTL 入口的路标，也是历史最悠久的滥用面。** 大量自研/老旧驱动（尤其非 WDM 风格、控制设备对象风格的）走"\Device\Xxx 命名 + \DosDevices\Xxx 符号链接 + CreateFile 打开 + DeviceIoControl 发命令"的老路。站在攻击面角度，本批给出三条直接可用的审计直觉：（1）凡是驱动**自己命名**的对象，先查它有没有配套的 SDDL（IoCreateDeviceSecure）——用裸 IoCreateDevice 建命名对象意味着安全描述符走了默认/类默认，历史上多次出现"任何用户可打开并发送 IOCTL"的提权问题；（2）凡是**不设 FILE_DEVICE_SECURE_OPEN** 的命名设备，去看它的 DispatchCreate 是否校验 FileObject->FileName 是否为空——不校验尾随名，`\Device\X\任意路径` 就可能被当作合法打开甚至被用来绕开预期的访问路径（第 2 批 Create 小节的 FileName 校验在此接上了）；（3）符号链接若用 IoCreateUnprotectedSymbolicLink 建在全局命名空间、或驱动在任意线程上下文里随手建链接，要留意**链接抢占/遮蔽**：本地 DosDevices 遮蔽全局的语义本是为多用户隔离设计的，反过来低权限会话也能在自己的本地命名空间里遮蔽名字，影响同会话内更高权限进程的打开目标解析——分析"某服务打开设备却连到了奇怪对象"类问题时，这是排查清单上的一项。

**FILE_DEVICE_SECURE_OPEN 对路径穿越类问题的影响（点到为止）。** 它的本质是把"命名空间内一切打开"收敛到同一套安全检查之下：没有它，设备名那一级的 SD 检查通过之后，尾随路径如何解释、是否再做权限判断，全凭驱动 Create 例程自觉。设了它，至少"谁有资格进入这个命名空间"这一关是统一且由 I/O 管理器强制的；至于进入之后尾随名指向的子资源各自该有什么权限，仍需要驱动在 Create 里逐项处理（安全章 Controlling Device Namespace Access 会把这套规则讲透，是第 5 批的内容）。所以审计结论的措辞应当分层：没设 SECURE_OPEN 是**姿态缺陷**（高风险信号），是否构成可利用漏洞还要看 Create 的尾随名处理与 IOCTL 的访问检查。

**"读邻居对象、禁写邻居扩展"在逆向中的回响。** 文档禁令（核心要点 14）解释了两个常见现象：其一，正规驱动间协作只能走 IRP，所以抓 IRP 流向（IRP 追踪、栈上各层 Dispatch 的断点）就是理解驱动协作的正道；其一，凡是你看到某驱动直接读写**别的驱动**的 device extension 或设备对象字段，那不是正常设计，而是 hook/作弊/rootkit 式的带外通信——这正是 EDR 与反作弊在设备堆栈层面找异常的一个模式：堆栈构成可枚举、归属可核对，任何"不在册"的对象或字段篡改都会在这张图上露馅。同理，filter DO 的位置即权力位置：上层筛选 DO 能看到 FDO 收到的一切请求，分析数据窃取/键盘记录类样本时，键盘堆栈上方多出来的那个 filter DO 往往就是答案。

## 五、易混点与自查

### 易混概念辨析

1. **设备对象 ≠ 设备，设备堆栈 ≠ 驱动堆栈的口语混用**：一个物理设备对应一摞设备对象（每层驱动一个）；"驱动堆栈"口语里常指这摞对象及其驱动的集合，而 devnode 还额外包含 PnP 状态信息。说"请求发给设备"时，精确说法是"发给堆栈顶部的设备对象"。

2. **PDO 的"F"与 FDO 的"P"**：PDO 是 Physical（物理），由**总线驱动**建、在栈底；FDO 是 Functional（功能），由**功能驱动**建、在 PDO 之上。新手最常记反创建者——口诀：**枚举者建 PDO（看得见硬件的总线驱动），干活者建 FDO**。

3. **NT 设备名 vs MS-DOS 设备名 vs 设备接口**：NT 设备名是 `\Device` 下的真名（内核对象名）；MS-DOS 设备名是 `\DosDevices` 下指向真名的符号链接（兼容层别名）；设备接口是按 GUID 注册的能力标识，系统内部同样用符号链接实现，但链接由系统按接口类统一管理、名字含 GUID 与引用计数语义。三者不是同一层东西：真名是本体、DOS 名是手工别名、接口是托管别名。

4. **IoCreateDeviceSecure 的"Secure"≠ 自动安全**：它只是允许你**自带 SDDL 与类 GUID**，SDDL 写得过宽照样不安全；而且给它套既有类 GUID 会反过来破坏那个类的安全设置。用错的 Secure 比不用更危险。

5. **Exclusive 是按"名字"的，不是按"设备对象"的**：I/O 管理器在名字解析层执行独占，不理会尾随名；且 WDM 栈里给 FDO 设 Exclusive 无效——生效点是被命名的 PDO，而 PDO 的这个属性只能经 INF 注入。看到驱动代码里给 FDO 传 Exclusive=TRUE，先别急着下结论，要去翻 INF。

6. **本地 `\DosDevices` 与全局 `\DosDevices` 不是两份注册表式的配置，而是同一命名空间的两个视图域**：查找先本地后全局、同名本地遮蔽全局；Win2000 是"会话启动时拷贝快照"、XP 起是"实时分层查找"——同一段老代码在两个系统上的符号链接可见性问题，根源可能就在这里。

### 自查问题（只给问题，自行回笔记核对）

1. 一个 USB 键盘的设备堆栈里，从栈底到栈顶依次有哪些设备对象？分别由哪类驱动、在什么时机（哪个例程响应什么请求）创建？为什么说"总线驱动横跨多个堆栈"？
2. WDM 驱动为什么不该给自己的 FDO 命名？如果一个堆栈里出现两个命名对象且安全描述符强度不同，会出现什么具体的绕行情形？
3. 用户态执行 `CreateFile("\\\\.\\MyDev")` 时，`MyDev` 这个名字经历了哪几层解析（\??、符号链接、\Device）才落到某个设备对象？最终第一个收到 IRP_MJ_CREATE 的为什么是栈顶驱动而不是被命名的 PDO 的驱动？
4. 某驱动在 DispatchDeviceControl 里用 IoCreateSymbolicLink 建了个符号链接，结果只有当前登录用户能看到、系统服务看不到——用本批的哪个机制解释？要让它全局可见有哪两种改法？
5. 审计一个驱动时，你在 INF 里看到 AddReg 写了 `DeviceCharacteristics` 与 `Exclusive`，在 .sys 里看到它用 IoCreateDeviceSecure 建了命名对象并自带 SDDL——这个设备的最终生效属性由哪几方合成？哪一份说了算？你会优先检查哪两个点来判断它是否存在"任意用户可打开设备发 IOCTL"的风险？
