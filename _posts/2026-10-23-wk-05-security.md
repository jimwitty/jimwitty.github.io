## 一、本批地图：一次打开设备请求的安全裁决链

用户态调用 `CreateFile` 打开设备，到 IRP_MJ_CREATE 落进驱动的 DispatchCreate 例程，中间要过五道关。**关键事实：驱动的 Create 例程拿到的，是已经被系统裁决过的结果，而不是原始请求。**逐道看责任方：

```
用户态进程
CreateFile("\\\\.\\MyDevice\\任意尾随名", DesiredAccess = GENERIC_READ|GENERIC_WRITE,...)
│
▼
——责任方：对象管理器 + I/O 管理器
\\.\ → \??（\DosDevices）下的符号链接 → NT 设备名 \Device\MyDevice
路径被拆成两段：「设备对象名」 + 「尾随名 FileName」
（如 \Device\MyDevice\任意尾随名；尾随名为空 = 打开设备本身）
│
▼
——责任方：I/O 管理器 / PnP 管理器（事前配置）
设备堆栈的访问检查只认「被命名的那个设备对象」的安全描述符；
这份 SD 的来源按优先级取（见详解一）：
设备级注册表设置 > 设备类（setup class）级注册表设置 > 按 PDO 的
DeviceType + Characteristics 生成的默认值
打开请求被导向堆栈顶部，但安全检查按被命名对象的 SD 做。
│
▼
——责任方：安全参考监视器（SRM）+ 对象管理器
拿调用线程令牌（token）中的 SID 集合，对照 DACL 中的 ACE 逐条比对：
调用方请求的 DesiredAccess（通用权限先按对象类型映射成具体权限）
是否被 DACL 允许？有显式 Deny 或没有 Allow 覆盖 → STATUS_ACCESS_DENIED，
IRP 根本到不了驱动。
│
▼
——责任方：取决于 FILE_DEVICE_SECURE_OPEN
尾随名为空 → 裁决结束，打开的是设备本身。
尾随名非空（打开的是"设备命名空间内的名字"）：
· 设了 FILE_DEVICE_SECURE_OPEN → 系统把第 3 道的同一份 SD 检查
同样套用到这次带尾随名的打开上，裁决口径统一。
· 没设 → 系统设备对象的 ACL，是否允许完全由驱动的
DispatchCreate 自己决定（多数驱动根本没写这个检查！
这就是尾随名绕过的缝，见详解二）。
│
▼
——责任方：驱动自己
IRP 的 Parameters.Create.SecurityContext → IO_SECURITY_CONTEXT，
其中 DesiredAccess 记录了调用方请求（且已通过裁决）的访问掩码；
FileObject->FileName 还带着尾随名。
驱动在这里做的是「业务层决定」：接受/拒绝、为这个句柄分配上下文、
独占设备的二次确认——而不是重做一遍系统 ACL（当然可以加码自查）。
│
▼
打开成功 → 句柄诞生；后续 Read/Write/DeviceControl 沿这个句柄进来，
，后续请求默认不再逐条查 ACL。
```

这张图的推论比细节更重要：**设备安全 = 第 2 道的 SD 写了什么 × 第 4 道的缝堵没堵。**驱动作者没写一行安全代码，不等于"没有安全设置"，而是等于"接受了系统默认的那套相当宽松的设置"（见核心要点 2）。

## 二、核心要点

1. **设备访问由安全描述符（SD）裁决，不由驱动代码裁决**。谁能打开设备，是对象上的 SD（及其中的 DACL）在打开路径上被安全参考监视器执行检查的结果；驱动的 DispatchCreate 收到请求时，ACL 检查已经做完了。驱动代码能做的是加码（自查调用方、拒绝尾随名），不能（也不应该）替代这套机制。

2. **WDM 驱动的 SD 是 PnP 管理器"事后刷上去"的，代码里的取值只是候选之一**。AddDevice 里 IoCreateDevice 建出设备对象后，PnP 管理器按"设备级注册表 > 设备类级注册表 > 按 PDO 的类型/特征生成的默认 SD"的顺序确定最终 SD 并应用到**整个设备堆栈的每个对象**。所以审计生效权限永远要看 INF/注册表的合成结果（第 3 批已点过，本批给出完整顺序）。

3. **默认 SD 比大多数人以为的宽得多**。对多数设备类型与特征组合，默认 SD 给管理员 GENERIC_ALL，给"其他所有人"GENERIC_READ | GENERIC_WRITE | GENERIC_EXECUTE。换句话说，一个什么安全配置都没写的 WDM 驱动，其设备默认对任何登录用户可读写——这是理解 BYOVD 生态的起点：很多老驱动不是"被攻破"，是"从出厂起大门就开着"。

4. **Raw mode 是唯一的例外，总线驱动必须自己供 SD**。设备以 raw mode 工作时 PnP 管理器定不了 SD，总线驱动必须用 IoCreateDeviceSecure 为 PDO 指定 SD；非 raw 时也可以主动供一份更严的，但注册表设置会覆盖它——"代码是下限建议，注册表是最终裁决"。

5. **非 WDM（legacy）驱动没有任何"系统代管"，必须自带默认 SD + 自有类 GUID**。用 IoCreateDeviceSecure 创建命名设备对象，同时给出默认 SD（SDDL 子集）和一个自己生成的、独一无二的类 GUID；系统再拿注册表中该 GUID 类的安全设置覆盖默认值。套用别人的类 GUID 等于和别人共用一份注册表安全配置，会互相污染（和第 3 批 IoCreateDeviceSecure 的 GUID 纪律是同一条）。

6. **每个设备对象都自带一个"命名空间"，尾随名打开默认不在系统 ACL 的管辖内**。`\Device\X\Foo` 这种"设备名 + 斜杠 + 名字"的打开，语义是"打开设备命名空间内的一个'文件'"（对文件系统就是真文件，对普通设备则是驱动自定义的概念）。系统默认**只**对设备本身的那次打开查 ACL，带尾随名的打开查不查、怎么查，默认完全甩给驱动。

7. **FILE_DEVICE_SECURE_OPEN 是把"设备本身的 SD"扩展到"整个命名空间"的开关**。设了它，命名空间内一切名字的打开都套用设备对象的同一份 SD，口径统一；它是设备特征（Characteristics）之一，可在创建时设、WDM 还可在注册表里设；且它在**堆栈顶部**被检查，所以 filter DO 挂栈后必须把下一层设备对象的 Characteristics 抄过来，否则这个特征在栈顶就"消失"了。

8. **不支持命名空间的驱动只有两条合规路线**。要么设 SECURE_OPEN（然后把任何带尾随名的打开都当作打开设备本身处理）；要么在 DispatchCreate 里检查 `IrpSp->FileObject->FileName`，长度非零就失败。**独占（exclusive）设备必须走第二条**——因为独占语义是"同一个命名对象同时只有一个句柄"，若带尾随名的打开被当作设备打开放行，就等于绕着独占的账面另开了一扇门。

9. **SDDL 是 SD 的文本形态，设备对象只认其中一个子集**。形态是 `"D:P"` + 一串 `(A;;Access;;;SID)` 形式的 ACE：Access 可写十六进制掩码或双字母代码（GA/GR/GW/GX 是 generic，RC/SD/WD/WO 是标准权限）；SID 用双字母缩写（SY 系统、BA 管理员、WD World、AU 已认证用户、RC 受限代码等）。INF 里可以写完整 SDDL，但 IoCreateDeviceSecure 只接受文档定义的子集；用 SDDL 时驱动要链接 Wdmsec.lib。预置串（Wdmsec.h）从 KERNEL_ONLY（用户态谁都打不开）到 SYS_ALL_ADM_RWX_WORLD_R（人人可读）构成一条现成的"松紧刻度尺"。

10. **通用权限（generic）在打开时按对象类型映射成具体权限（specific），裁决只认映射后的集合**。GENERIC_READ 对文件意味着 FILE_READ_DATA + FILE_READ_ATTRIBUTES，对注册表键意味着 KEY_QUERY_VALUE + KEY_ENUMERATE_SUB_KEYS，对设备则映射为该设备类型对应的读集合。写驱动时要明白：SDDL 里写 GR 放行的是"这一整组具体权限"，不是一个抽象的"读"。

11. **安全描述符里驱动只需关心 DACL；特权是另一本账，别和 ACL 混**。SD 由 DACL（谁能对这个对象做什么）与 SACL（哪些操作要记审计日志）组成，DACL 的每条 ACE = SID + 访问掩码 + Allow/Deny。特权（privilege）则附着在**进程/令牌**上而非对象上（如 SeBackupPrivilege、SeLoadDriverPrivilege 的概念位置），只有少数例程会检查特权，绝大多数系统例程根本不查——"调用方是管理员"与"调用方持有某特权"与"调用方过了 DACL"是三件不同的事。

12. **打开是一次性裁决，句柄是裁决结果的载体**。打开成功后，句柄的已授予访问就是上限；后续的读写与 IOCTL 默认沿这个句柄进来、不再逐操作重查设备 ACL。这意味着：真正的安全边界在 Create 那一瞬，DeviceControl 里若有"这个控制码只该管理员用"的细分需求，必须驱动自己按控制码再做调用方校验（如检查 SecurityContext 或线程令牌），系统不会替它按 IOCTL 分级。

## 三、关键知识点详解

### 详解一：设备访问由谁决定——SD 的三层来源与默认值的真相

原文 Controlling Device Access 一节按驱动类型分三种情形，合起来是一张完整的"谁说了算"表：

**（1）WDM 驱动（一般情形）：PnP 管理器代管。**时序是：PnP 管理器调 AddDevice → 驱动 IoCreateDevice 建对象并挂栈 → **PnP 管理器随后更新这个新设备对象的 SD**。取值顺序：

1. 注册表里有该**设备级**的安全设置 → 用它，且应用到堆栈的每一个对象；
2. 否则，注册表里有该**设备类（setup class）级**的安全设置 → 用它，同样全栈应用；
3. 否则，不动每个对象的默认 SD，此时全栈的默认 SD 由 **PDO 的 DeviceType 与 Characteristics 决定**。

第 3 条的默认值就是核心要点 3 说的那份：对多数类型/特征，管理员 GENERIC_ALL、其他所有人 GENERIC_READ|GENERIC_WRITE|GENERIC_EXECUTE。注意它宽松的原因：这套默认值要照顾"设备就是给应用用的"这个一般预期，收紧是个别驱动自己的事——**默认值的设计目标是可用性，不是最小权限**。注册表设置的具体落点（INF 的 AddReg 写 DeviceType/DeviceCharacteristics/Exclusive/Security 等）在第 3 批已讲，本批的衔接点是：注册表不是"建议"，它在优先级链的顶端，压过一切代码内取值。

**（2）WDM 总线驱动：raw mode 必须自供。**如果子设备能以 raw mode（无功能驱动直接操作）工作，PnP 管理器无法为其 PDO 定 SD，总线驱动**必须**用 IoCreateDeviceSecure 建 PDO 并附 SD。非 raw 的情形可以不供（走上面的代管流程），也可以主动供一份更严的作为"地板"，但注册表设置仍能覆盖它。

**（3）非 WDM 驱动：全自理。**没有 PnP 代管，必须用 IoCreateDeviceSecure 建命名对象、给默认 SDDL、给自有类 GUID（GuidGen 生成、独一无二）；系统用注册表中该类 GUID 对应的安全设置覆盖默认 SD。后果是：legacy 驱动的设备权限 = 作者写的 SDDL 子集 × 安装后注册表状态，两处都查不到"收紧"的动作，就等于作者把权限设计完全交给了默认值与运气。

**一个容易被漏掉的推论**：既然 WDM 的 SD 在 AddDevice 返回后才被 PnP 刷定，驱动在 IoCreateDevice 那一瞬写的任何"安全意图"（除 raw/legacy 路径的 Secure 版）都不构成保障；反过来，**攻击面评估时看到驱动代码里没有任何安全调用，不能推出"它没有 SD"——它有一份系统给的、通常很宽的 SD**。

### 详解二：命名空间访问与尾随名——FILE_DEVICE_SECURE_OPEN 补的是哪条缝

**命名空间是什么**。在 WDM 里每个设备对象都关联一个命名空间：以设备名为前缀的一切路径。`\Device\DeviceName\FileName` 就是"设备 DeviceName 的命名空间内的名字 FileName"。文件系统驱动里 FileName 是磁盘上的真文件；对普通设备驱动，"命名空间内的文件"这个概念由驱动自行定义——而**绝大多数设备驱动根本不支持命名空间**，它们只认"打开设备本身"（尾随名为空）这一种打开。

**缝在哪里**。打开请求进来时，系统按被命名对象的 SD 做访问检查——但原文明确写道：**默认情况下，命名空间内名字的打开请求，其安全检查完全留给驱动，操作系统不查设备对象的 ACL**。也就是说：

- 打开 `\Device\X`（无尾随名）：系统查 SD，没权限直接拒绝，驱动无感。
- 打开 `\Device\X\随便什么`（有尾随名）：系统把 IRP 交给驱动的 DispatchCreate，**查不查由驱动**。

而现实中大量驱动的 DispatchCreate 是无条件 `return STATUS_SUCCESS` 的——它假设"能进到我这里的都是过了检查的"。于是同一个设备出现两副面孔：正门有门禁，尾随名这条"侧门"无人值守。历史上不少驱动的提权/绕过正是从这里进的：正路打开被 SD 拦，拼一个尾随名进去，Create 照样成功，DeviceControl 全套功能到手。

**两种堵法（原文给的标准答案）**：

| 情形 | 方法一 | 方法二 |
|---|---|---|
| 不支持命名空间 | 设 FILE_DEVICE_SECURE_OPEN，把任何命名空间打开都当作打开设备本身，一份 SD 管到底 | DispatchCreate 检查 FileObject->FileName，长度非零即失败（**独占设备必须用这条**） |
| 支持命名空间 | 设 FILE_DEVICE_SECURE_OPEN，让命名空间与设备共用同一套安全设置（驱动负责实现命名空间语义） | 在 DispatchCreate 里按名字自查 ACL——但原文仍建议设 SECURE_OPEN，除非命名空间内的打开**有意**要比设备本身更弱的安全设置 |

**一个实现细节（栈顶检查）**：SECURE_OPEN 是在**堆栈顶部**被检查的特征。filter 驱动 attach 后成为新的栈顶，它的设备对象若不抄下层对象的 Characteristics，SECURE_OPEN 在栈顶就不存在了——所以 filter 的 AddDevice/attach 路径必须在挂栈后把下一层设备对象的 Characteristics 成员复制到自己的设备对象上。这条在第 3 批"特征是整栈级"的语境里提过，本批给出它在安全上的具体后果：**一个粗心的 filter 能把下层辛苦设好的命名空间保护整层摘掉**。

### 详解三：SDDL 实务——读懂并写对设备对象的权限串

**形态**。设备对象的 SDDL 串形如 `"D:P(A;;GA;;;SY)(A;;GR;;;WD)"`：
- `D:` 表示后面是 DACL；`P` 是保护标志（protected，阻止父级 ACL 继承覆盖——设备对象上这是常态写法）；
- 每条 ACE 是 `(A;;Access;;;SID)`：第一个 `A` = ACCESS_ALLOWED_ACE（本子集只用 Allow 型），Access 段是允许的访问掩码，SID 段是这条 ACE 作用的主体。注意原文的子集里没有 Deny 型 ACE 的写法——设备对象的权限设计靠"只给需要的人写 Allow"，而不是"给所有人再 Deny 个别人"。

**Access 的两种写法**。可以写十六进制 `0x...` 掩码，也可以用双字母代码拼接：

- Generic：`GA` = GENERIC_ALL、`GR` = GENERIC_READ、`GW` = GENERIC_WRITE、`GX` = GENERIC_EXECUTE；
- 标准（specific/standard）：`RC` = READ_CONTROL、`SD` = DELETE、`WD` = WRITE_DAC、`WO` = WRITE_OWNER。

原文特别提醒：**GENERIC_ALL 把上面两张表的所有权利打包全给，包括改 ACL 的 WRITE_DAC**——给 BA 写 GA 是"管理员完全控制"的常态，但给任何非管理主体写 GA 都等于把设备连同它的权限配置一起送出去了。

**常用 SID 缩写**（设备场景高频的那批）：`SY` LocalSystem（操作系统自身，含其用户态组件）、`LS` 本地服务、`NS` 网络服务、`BA` 内置管理员组、`BU` 内置用户组、`BG` 来宾组、`AU` 已认证用户、`AN` 匿名登录、`IU` 交互登录用户、`NU` 网络登录用户、`WD` World（XP 起不含匿名会话）、`RC` 受限代码（Restricted Code）、`UD` 用户模式驱动（UMDF，Win8 起）。

其中 `RC` 的语义值得单独记：它不是一个独立人群，而是给"不受信任代码"加的**双重检查**——带 RC 的令牌要同时通过普通 SID 列表和受限 SID 列表两轮校验；且任何用了 RC 的 ACL 必须同时写 WD。预置串里 RES_R 与不带 RES 的版本的区别就在于多了一条 `(A;;GR;;;RC)`：前者连"以受限方式运行的代码"也能读，后者不能。

**预置串速查（Wdmsec.h，从严到宽）**：

| 常量 | SDDL | 语义 |
|---|---|---|
| SDDL_DEVOBJ_KERNEL_ONLY | `D:P`（空 DACL） | 用户态谁都打不开（含以 System 运行的用户态进程）；只有内核态可达。典型用法：总线驱动先用它建 PDO，等 INF 再放宽；或 legacy 驱动先锁死，等自己的服务在运行时用 SetFileSecurity 设最终 SD——"默认从严、按需放松" |
| SDDL_DEVOBJ_SYS_ALL | `D:P(A;;GA;;;SY)` | 在 KERNEL_ONLY 基础上，允许以 System 身份运行的**用户态**代码任意访问 |
| SDDL_DEVOBJ_SYS_ALL_ADM_ALL | `D:P(A;;GA;;;SY)(A;;GA;;;BA)` | System + 管理员完全控制，其他人一律拒绝 |
| SDDL_DEVOBJ_SYS_ALL_ADM_RWX_WORLD_R | `D:P(A;;GA;;;SY)(A;;GRGWGX;;;BA)(A;;GR;;;WD)` | System 完全控制；管理员可读写执行但**没有 WRITE_DAC**（想改 ACL 须先夺取所有权）；World 只读；受限代码不可达；原文还注：未给普通用户 traversal 权限，对带命名空间的设备可能不合适 |
| SDDL_DEVOBJ_SYS_ALL_ADM_RWX_WORLD_R_RES_R | 上串 + `(A;;GR;;;RC)` | 在上者基础上再允许受限代码只读 |

这五个串都是现成的模板，自定义时在它们基础上增删 ACE 即可。另外两个原文纪律：这些预置串**不带继承修饰符，只适用于设备对象**，不要拿去描述文件或注册表键；INF 里能写完整 SDDL，而 IoCreateDeviceSecure 只吃子集——同一份权限设计走代码路径时要确认没用上子集之外的语法。

### 详解四：访问权限映射——generic 是"宏"，specific 才是裁决单位

打开对象时调用方在请求里给出 DesiredAccess（第 1 批/第 4 批语境里它出现在 IRP_MJ_CREATE 的 IO_SECURITY_CONTEXT 里），系统做访问检查时比对的是**具体权限集合**。权限分三层：

- **标准权限（standard rights）**：对一切对象类型通用，如 DELETE（删除对象）、READ_CONTROL（读 SD）、WRITE_DAC（改 DACL）、WRITE_OWNER（改所有者）、SYNCHRONIZE。SDDL 代码 RC/SD/WD/WO 对应的就是这一层的一部分。
- **对象特定权限（specific rights）**：随对象类型而变。文件/设备这一类有 FILE_READ_DATA、FILE_WRITE_DATA、FILE_READ_ATTRIBUTES 等；注册表键有 KEY_QUERY_VALUE、KEY_ENUMERATE_SUB_KEYS。两个对象可能都有"读"的概念，但具体权限集合完全不同。
- **通用权限（generic rights）**：GENERIC_READ / GENERIC_WRITE / GENERIC_EXECUTE / GENERIC_ALL，是与对象类型无关的"宏"。系统按该对象类型的 **generic mapping** 把它们展开：GENERIC_READ 对文件展开为 FILE_READ_DATA | FILE_READ_ATTRIBUTES（再加标准权限里的 READ_CONTROL 等），对键展开为 KEY_QUERY_VALUE | KEY_ENUMERATE_SUB_KEYS……，裁决拿展开后的集合逐位核对 DACL。

对驱动工作的两条实际含义：
1. **写 SD 时的宽窄要按展开后算账**。给 WD 写一条 GR，在设备上等于放行"读数据 + 读属性 + 读控制信息"这一整组；若设计意图只是"允许读某个状态"，GR 可能已经给多了，但不用 GR 就得逐位写十六进制掩码——可读性与精确性的取舍点在这里。
2. **Create 例程里读到的 DesiredAccess 是调用方"请求且被允许"的掩码**。驱动若要做句柄级的细分（例如"这个句柄打开时只申请了读，后续不许拿它发写类 IOCTL"），依据就在 SecurityContext 里，而不是靠猜调用方身份。

### 详解五：安全描述符与裁决流程——SD 长什么样、检查在哪发生

每个内核对象都挂一份安全描述符，内核里用不透明的 SECURITY_DESCRIPTOR 表示。它由四部分构成：头部控制信息、Owner SID、**DACL**、**SACL**。

- **DACL（自主访问控制列表）**：决定"谁能对这个对象做什么"，由一串 ACE 组成，每条 ACE 三要素：适用的 SID、一组访问权限、Allow 还是 Deny。打开路径上的裁决就是把令牌中的 SID 集合与调用方请求的访问掩码，拿去和 DACL 做匹配——请求的每一位权限都必须被某条 Allow ACE 覆盖且不被 Deny 截断，才算通过。
- **SACL（系统访问控制列表）**：决定"哪些操作要写审计日志"，与放行与否无关。原文明确：驱动开发者通常只关心 DACL，SACL 是 SDK/审计层面的事。

裁决的执行者是**安全参考监视器（Security Reference Monitor）**配合对象管理器：对象管理器负责在按名打开的路径上找到对象并触发检查，SRM 提供 SeAccessCheck 这类裁决例程。放在本批地图里就是第 2、3 道关——**发生在 IRP 生成之前**，驱动不在这条路径上，它的 Create 例程被调用这个事实本身，就意味着裁决已通过（或走的是内核句柄/系统线程等绕过检查的路径，第 4 批 OBJ_KERNEL_HANDLE / OBJ_FORCE_ACCESS_CHECK 的讨论与此呼应：内核模式打开默认信任，强制核验要显式要求）。

还有一层要分清：SD 是**对象级**的配置，它管的是"打开"这个动作。对象打开之后各具体操作（哪个 IOCTL 能调、参数合不合法）不在 SD 的射程内——这是详解六与解读部分"驱动自查"存在的理由。

### 详解六：特权在驱动路径上的位置——少数例程的入场券检查

特权与 ACL 是两套正交的机制：**ACL 挂在对象上，特权挂在进程（令牌）上**。特权是"这个进程被授予的系统级能力"，如 SeBackupPrivilege（绕过文件 ACL 做备份读）、SeRestorePrivilege、SeLoadDriverPrivilege（加载驱动）、SeDebugPrivilege 等。

原文 Privileges 一节给了三条关键事实：

1. **只有极少数例程会检查特权**："Most system routines do not perform any privilege checks."驱动不能假设"我调的系统例程会替我把调用方资格筛一遍"。
2. 原文表格举的例子是：SeManageVolumePrivilege 之于 ZwSetInformationFile（设 FileValidDataLengthInformation 时）、SeTakeOwnershipPrivilege 与 SeSecurityPrivilege 之于 SeAccessCheck（分别对应"夺取所有权"路径与"访问 SACL"路径——即想读/改审计设置本身就需要 SeSecurityPrivilege）。
3. **执行上下文决定检查结果**：同一个驱动例程，若运行在系统进程上下文里，操作总是成功；若运行在某个用户进程上下文里且该进程没有所需特权，操作就可能失败。这与第 1 批的"任意线程上下文"直接咬合——**驱动以谁的身份在跑，决定了它此刻的特权面貌**；把需要特权的操作放在用户请求线程里同步执行，就可能出现"管理员的服务能用、普通用户的客户端就失败"的间歇性怪象，反之若驱动拿系统线程代办，又等于把特权借给了所有能触发它的人。

所以在驱动威胁模型里特权的正确位置是：它不是设备访问的第二道门（那道门是 SD），而是**个别敏感系统操作**的额外入场券；审计时只在看到 SeAccessCheck、文件信息设置等少数调用点时才需要问"这里查的是哪个特权、调用上下文是谁"。

## 四、解读：站在审计与逆向的一侧看这一章

**（1）审计一个驱动的设备攻击面，按这个顺序查。**本批的裁决链反过来就是一份检查单：
1. **先看 INF**：有没有 DeviceCharacteristics（含 SECURE_OPEN 位）、Security（设备级 SDDL）、类级 SDDL；没有就等于接受默认宽 SD（要点 3）——这一步不用碰二进制就能定性大半。
2. **再看设备命名与符号链接**：建的是命名设备还是注册设备接口？符号链接建在全局 `\DosDevices` 还是会话本地？名字是否可预测、是否可能被抢先注册（见下条）。
3. **查 SECURE_OPEN**：设备特征里有没有这一位；若有 filter，filter 有没有抄下层 Characteristics。
4. **读 DispatchCreate**：有没有查 FileName 长度（尾随名）、有没有按 DesiredAccess 做句柄分级、exclusive 设备走没走"尾随名即失败"路线。
5. **最后读 DispatchDeviceControl**：有没有对敏感控制码再做调用方校验（令牌/特权/句柄已授予访问）——因为 SD 只守打开那一瞬，IOCTL 的粗细粒度全靠这里（第 7 批会系统展开 IOCTL，本批先立这个意识）。

**（2）过宽 SDDL 是 BYOVD 与 IOCTL 提权生态的"入口条件"。**Bring Your Own Vulnerable Driver 的链条是：攻击者先要有办法**打开**那个有缺陷的驱动设备，才能发恶意 IOCTL。若设备 SD 只允许管理员，普通用户连第一步都迈不过去，这个驱动对低权限攻击者就没有价值。正因为默认 SD 给 Everyone 读写执行、且海量老驱动从未在 INF 里收紧，攻击面才成立。换句话说：**"这个驱动有没有漏洞"和"这个驱动的门开着没有"是两个独立的问题，后者由本批这套机制决定，且后者才是它进入利用生态的门票**。

**（3）命名空间与命名本身也是攻击面：抢注与劫持。**设备名与符号链接活在同一个对象命名空间里，先到先得。若驱动的设备名/符号链接名固定可预测、且驱动以"名字已存在就失败/或默默复用"的态度处理，低权限方在本会话命名空间内抢先建一个同名对象（尤其是**本地** `\DosDevices` 遮蔽全局的那一层，第 3 批讲过本地优先），就可能让受害进程打开到假对象，或让真驱动加载失败。防御侧的对应动作都在前面批次里：用设备接口（GUID 注册、无固定名）代替全局符号链接、符号链接只在系统上下文建全局版、Create 里对尾随名与 FileName 保持警惕。本批补的是裁决视角：**命名空间解析（第 1 道关）本身没有"这个名字是不是该驱动建的"这种真实性校验**，系统只认"名字指向的对象 + 对象上的 SD"。

**（4）给做加固的读者的落点。**收紧一个现役驱动的设备权限，改动面比想象中小且都在本批射程内：INF 里补设备级 SDDL（或注册表覆盖）、补 SECURE_OPEN 特征、Create 里加尾随名拒绝——三件都不动功能代码。但顺序不能错：先确认没有合法客户端依赖"Everyone 可读"或依赖尾随名打开（老软件的怪用法在第 6 批兼容性话题里是常客），否则加固即断供——这正是这套机制二十多年默认宽松、且没人敢一刀收紧的现实原因。

## 五、易混点辨析

1. **"驱动没写安全代码" ≠ "设备没有访问控制"，也不等于"设备安全"。**WDM 设备永远有一份生效 SD：不是 INF 写的，就是类里继承的，再不然是按类型/特征生成的宽默认值。没写代码的真实含义是"作者把权限设计外包给了默认值"。

2. **SECURE_OPEN 管的是命名空间，不是设备本身。**设备本身的打开（无尾随名）无论设不设这一位都查 SD；这位管的是"设备名后面的那截路径"。把它理解成"打开设备时更严格"是错位的——严格的对象不同。

3. **IoCreateDeviceSecure 的"Secure" ≠ 自动安全。**它只是"允许在创建时附带 SD 与类 GUID"的入口；附的 SD 写得宽（比如给 WD 以 GA），结果比默认还糟。且 WDM 功能/筛选驱动的 SD 终将被 PnP/注册表流程接管，Secure 版的主战场是总线驱动的 raw PDO 与非 WDM 驱动。

4. **GENERIC_ALL 写在 SDDL 里和调用方"请求 GENERIC_ALL"是两回事。**前者是 DACL 中一条 ACE 的授予内容（包含 WRITE_DAC 在内的全集）；后者是打开时 DesiredAccess 的请求值，要先经 generic mapping 展开、再与 DACL 核对才知道成不成立。另注意：管理员拿到 GA 的 ACE，也推不出"任何管理员进程打开都会成功"——令牌是否完整性受限、是否被过滤，与本章的静态 SD 是另一层话题。

5. **特权检查与 ACL 检查不是一前一后的两道门，而是两条不相干的线。**ACL 检查在按名打开对象的路径上由系统统一执行；特权检查只在个别例程内部按需发生（且多数例程根本不查）。"我是管理员进程"既不保证过某个收紧过的设备 DACL，也不等于持有 SeLoadDriverPrivilege 等具体特权。

6. **DACL 里的"没有 Allow"就是拒绝，不需要显式 Deny。**设备 SDDL 子集连 Deny ACE 的写法都没有，权限模型是默认拒绝 + 白名单放行；读 INF 时看到 DACL 里只有一两条 ACE，先问"没被列出的人是什么下场"——答案是打不开，而不是"没限制"。

## 六、自查问题（只给问题，自行回原文核对）

1. 一个 WDM 功能驱动在 AddDevice 里用 IoCreateDevice 建了未命名 FDO，INF 里什么安全设置都没写。请完整说出它最终生效的 SD 是由谁、在什么时机、按什么顺序定下来的，以及一个普通登录用户能不能打开这个设备、能拿到哪些访问。
2. 同一设备，攻击者直接打开 `\Device\X` 被拒绝，改打开 `\Device\X\foo` 却成功进了 DispatchCreate 并拿到句柄。这中间哪道关没有生效？驱动方有哪两种标准修法？如果这是个 exclusive 设备，修法为什么只剩一种？
3. 读这条 SDDL：`D:P(A;;GA;;;SY)(A;;GRGWGX;;;BA)(A;;GR;;;WD)`。逐条说出每个主体的权限；管理员与 World 的关键差别在哪一位上？把它与 Wdmsec.h 里的哪个预置串对照，差了什么？
4. 一个 filter 驱动正确地给自己的 filter DO 设了和下层一样的 SD 思路，却被发现把下层的命名空间保护弄丢了。可能漏了哪一步？这一步为什么必须在 attach 之后做？
5. 驱动的 DispatchDeviceControl 里有个控制码能物理读写任意磁盘扇区，作者说"没关系，设备只有管理员能打开"。请用本批的机制逐条检验这句话：设备 SD 在哪配的、默认值是什么、尾随名路径查不查、打开后系统还替他按 IOCTL 分不分级——哪几处假设站不住？
