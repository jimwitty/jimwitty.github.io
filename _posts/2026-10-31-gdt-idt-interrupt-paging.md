这四个词是 x86 电脑（我们平时用的 Windows、Linux 电脑）开机后最先立起来的四套规矩。它们听着吓人，其实各自只管一件很朴素的事。本文不假设你懂操作系统，只要你会用电脑，就能一路读下来；但该有的细节一个不少，读完你应该能自己画出"一个内存地址是怎么被翻译的""一次按键是怎么变成屏幕上字符的"。

## 先用一座大楼把四个角色认全

把电脑想象成一座大楼：

- **内存**是大楼里一排排真实的储物柜，每个柜子有真实编号。柜子的真实编号，就叫**物理地址（physical address）**。
- 程序手里拿的地址不是柜子编号，而是一张**取件码**——它以为自己在用"第 12345678 号柜子"，其实那只是个虚拟号码。这个虚拟号码叫**线性地址（linear address，也叫虚拟地址）**。
- **页表（page table）**是前台的**登记簿**：负责把取件码翻译成真实柜子编号。没有登记簿，你拿着取件码永远找不到柜子。
- **GDT（全局描述符表，Global Descriptor Table）**是大楼的**分区与门禁总表**：规定整座楼划成哪几个区（代码区、数据区、内核区、用户区），每个区从哪到哪、谁能进、能干什么。
- **IDT（中断描述符表，Interrupt Descriptor Table）**是大楼贴在墙上的**应急电话簿**：火警按几号键、电梯故障打哪个电话、有人晕倒找谁——每种突发情况对应一个编号和一个处理人。
- **中断处理（interrupt handling）**就是**突发情况发生时的整套反应流程**：警报响起、正在办的事先停下、现场封存、专人处理、处理完回到刚才停下的地方继续——办事的人甚至不知道中间出过事。

四者的关系一句话：**GDT 和页表管"平时怎么访问内存"，IDT 和中断处理管"出事时怎么办"；而页表出事时（要找的页不存在），恰恰要靠 IDT 叫人来处理——四套规矩在这里咬合。**

下面逐个拆开讲，每个都按同一节奏：它是什么、为什么非有它不可、它长什么样、实际运转时一步一步发生了什么。

## 一、GDT：大楼的分区与门禁总表

### 1. 先说为什么会有"段"这个东西

最早的 x86 处理器（8086，1978 年）有个先天不足：它内部算地址的零件是 16 位的，一次最多表示 65536（64KB）个地址，可它又想用上 1MB 内存。工程师的凑合办法是**两个数拼一个地址**：地址 = 段值 × 16 + 偏移。好比快递地址写"第 5 区 + 区内的 320 号"，区号和门牌合起来才是完整地址。这里的"段"就是"区"。

到了 80286、80386，电脑开始要跑多任务、要讲安全：程序 A 不能乱翻程序 B 的内存，用户程序不能碰内核的地盘。光有"区号"不够了，每个区必须配一张**身份证**，写明：

- 这个区**从哪开始**（基址，base）
- 这个区**有多长**（界限，limit）
- 这个区**是干什么的**（是代码还是数据，能不能读、能不能写、能不能执行）
- **什么级别的人能进**（特权级，DPL，0~3 级，0 最高——内核是 0 级，用户程序是 3 级）

这张身份证就叫**段描述符（segment descriptor）**，8 个字节。把全系统所有段的身份证装订成一本册子，就是 **GDT**。

### 2. 程序怎么"出示"自己要去哪个区

程序不能直接说区的名字，它手里攥着一个 16 位的小牌子，叫**段选择子（segment selector）**，平时就放在 CS、DS、SS 这些段寄存器里。牌子拆开是三段：

```
 15                              3   2    1  0
 ┌────────────────────────────────┬───┬──────┐
 │           索引（第几号描述符）    │TI │ RPL  │
 └────────────────────────────────┴───┴──────┘
```

- **索引（13 位）**：要查 GDT 里的第几号身份证。13 位最多 8192 号，所以 GDT 最多 8192 个描述符。
- **TI（1 位）**：查的是 GDT（0）还是另一本小册子 LDT（1）。LDT 是给单个程序开小灶用的，现代操作系统基本不用它，知道有这回事即可。
- **RPL（2 位）**：出示牌子的人自报的级别，用来和门禁比对。

CPU 还有一个专门的寄存器 **GDTR**，记着两件事：GDT 放在内存的哪个地址、多长。开机时操作系统用一条 `lgdt` 指令把自己编好的 GDT 交给 CPU，从此查表有了依据。

### 3. 一次完整的"进区"过程

当程序往段寄存器里装一个新选择子时（比如执行一条跳转指令切换代码段），CPU 会：

1. 按索引去 GDT 里取出对应描述符；
2. 检查：这个段存在吗？来的人级别够吗（比如 3 级的用户程序想进 0 级的内核代码段，直接拒绝）？要干的事允许吗（往代码段里写数据？不行）；
3. 全部通过后，把描述符里的基址、界限、权限**抄进段寄存器内部的隐藏部分**（叫描述符缓存）。

第 3 步是个关键细节：**查表只在"换段"的那一瞬间发生**。之后成千上万次访问内存，CPU 都直接用缓存好的基址和界限，不再翻 GDT。所以 GDT 平时几乎不被读到，它是"立规矩"的，不是"每次都查"的。

任何一步检查不过关，CPU 当场触发一个叫**通用保护异常（#GP，13 号）**的警报（怎么处理警报，第三部分讲 IDT 时再说）——Windows 上老式的"此程序执行了非法操作"、Linux 上的段错误，很多就是这么来的。

### 4. 现代操作系统里 GDT 的真实地位

说个反直觉的事实：**现代 Windows、Linux 几乎把"段"架空了**。它们的办法是：代码段、数据段的描述符一律填"基址 = 0、界限 = 拉满整个 4GB（64 位下更甚）"，等于全楼不设分区墙，所有人共用同一片平坦地址——这叫**平坦模型（flat model）**。程序之间的隔离改由页表负责（第二部分的主角）。

那 GDT 能删掉吗？**不能，有三样东西还离不开它：**

1. **特权级切换的栈**：用户程序陷入内核时要换一根"内核专用栈"，栈的位置记在一个叫 **TSS（任务状态段，Task State Segment）**的结构里，而 TSS 的描述符就挂在 GDT 里。没有 GDT，中断一来连栈都不知道换到哪去。
2. **每个 CPU 一张 GDT**：64 位系统里每个处理器核心有自己的 GDT，里面还放着各自的 TSS 等私有条目。
3. **第 0 号描述符永远是空的**：这是故意的——谁要是误用了一个空的段选择子，CPU 立刻报错，而不是稀里糊涂访问到什么东西。

一句话总结 GDT：**它是开机时立下的"分区与门禁章程"，平时被架空，但章程本身和藏在里面的 TSS 永远删不掉。**

## 二、页表：取件码翻译成真实柜子编号的登记簿

这是四个机制里最重要、也最值得一步步走一遍的一个。

### 1. 为什么需要翻译这一层

设想没有页表，程序直接使用物理地址，会有三个灾难：

- **没有隔离**：任何程序都能读写任何内存，包括内核和其他程序——一个程序崩溃拖垮全系统，病毒更是畅通无阻。
- **内存没法拼凑**：程序需要一整块连续的 500MB，可内存里只剩一堆碎片，加起来够、连起来不够——直接失败。
- **装不下就没办法**：物理内存 8GB，想同时跑总量 12GB 的程序？无解。

页表的解法是**中间加一层翻译**：内存被切成大小统一的块，每块 4096 字节（4KB），叫**页（page）**；物理内存那边的块叫**页框（page frame）**。程序的线性地址先按页查登记簿，翻译成页框编号，再拼上页内位置，得到物理地址。这一层翻译一加，三个灾难同时化解：

- 每个程序有**自己的一本登记簿**，只能翻译到分给它的页框——隔离天然成立；
- 程序眼里连续的一大片地址，背后可以是**任意散落的页框**——碎片不再是问题；
- 暂时不用的页可以**先搬到硬盘上**、登记簿里记一笔"不在内存"，要用时再搬回来——这就是虚拟内存能"以小装大"的原理。

### 2. 登记簿为什么是"两级"的

32 位地址一共有 2³² = 40 多亿个字节，按 4KB 一页，有 1,048,576 页。如果用一本扁平登记簿，每页一条记录、每条 4 字节，这本书本身就要 **4MB，而且每个程序一本、必须常驻内存**。十个程序就是 40MB 净浪费，何况大多数程序根本用不满地址空间，簿子里绝大部分条目是空的。

于是登记簿做成**两级**，结构像查字典先查部首、再查页码：

- **页目录（Page Directory）**：第一级，共 1024 条记录（叫 PDE，页目录项），每条指向一本小册子。
- **页表（Page Table）**：第二级，每本 1024 条记录（叫 PTE，页表项），每条指向一个真实页框。

好处是：**小册子按需才建**。一个只用了几十 MB 的程序，可能只需要几本小册子，登记簿总共花几十 KB 而不是 4MB。大片没用到的地址范围，在页目录里一条"空"记录就打发了，连小册子都不用印。

配套地，线性地址这 32 位也被切成三段，正好对应"查哪本簿、查第几条、页内第几字节"：

```
 31                22 21                12 11                 0
 ┌───────────────────┬───────────────────┬────────────────────┐
 │   页目录索引(10位)  │    页表索引(10位)   │    页内偏移(12位)     │
 │   第几本小册子      │    小册子第几条     │   页框内第几个字节    │
 └───────────────────┴───────────────────┴────────────────────┘
```

页内偏移为什么是 12 位？因为一页 4096 = 2¹² 个字节，正好 12 位数得完。剩下 20 位平分给两级索引，各 10 位、每级 1024 条，严丝合缝。

还有一个关键角色：**CR3 寄存器**。它存着"当前正在用的那本页目录放在物理内存的哪个地址"。每个程序一本页目录，操作系统切换程序时就换 CR3——换簿子只需要改一个寄存器，这是整个虚拟内存机制的枢纽。

### 3. 一步一步走完一次翻译（真实数字）

假设 CPU 要访问线性地址 **0x12345678**，当前 CR3 = **0x0001F000**（页目录放在物理地址 0x1F000 处）。翻译全程不需要软件参与，是 CPU 内部的硬件零件（叫页表遍历器）自动走的：

**第 0 步：拆地址。**
0x12345678 按 10/10/12 拆开：
- 页目录索引 = 72（0x48）
- 页表索引 = 837（0x345）
- 页内偏移 = 0x678

**第 1 步：查页目录。**
页目录在 0x1F000，第 72 条记录的地址 = 0x1F000 + 72×4 = **0x0001F120**。从这里读出 PDE = **0x000AB007**。
解读这条记录：低 12 位是标志——最后一位（P，Present）= 1，表示"这本小册子存在"；倒数第二位（R/W）= 1 可写；倒数第三位（U/S）= 1 表示用户程序可访问。高 20 位 0x000AB 是小册子的存放地址，即**页表在物理内存 0x000AB000 处**。
（如果 P = 0，翻译当场中止，CPU 触发**缺页异常**——别急，第三、四部分会讲它怎么被处理。）

**第 2 步：查页表。**
页表在 0xAB000，第 837 条记录的地址 = 0xAB000 + 837×4 = **0x000ABD14**。读出 PTE = **0x00C35067**。同样解读：P = 1 页在内存里，高 20 位 0x00C35 是**真实页框编号**，即数据真正躺在物理内存 0x00C35000 开始的那一页里。

**第 3 步：拼地址。**
物理地址 = 页框地址 + 页内偏移（偏移全程不翻译、原样带过来）= 0x00C35000 + 0x678 = **0x00C35678**。

翻译完成。CPU 拿着 0x00C35678 去访问真实内存，整个过程程序毫无感知。

回头看这个例子里藏着的两个设计：

- **每一级都要过安检**：不光查"在不在"，还要查权限（只读页想写？用户程序想碰内核页？任一级不过关，翻译立即中止并触发异常）。隔离就是靠这道逐级安检实现的。
- **翻译的代价不小**：走完两级要多读两次内存（读 PDE、读 PTE），加上真正访问那一次，一次访存变三次。64 位系统是四级页表（下面讲），更要多读四次。CPU 怎么受得了？靠下一小节的缓存。

### 4. TLB：翻译结果的速查小抄

**TLB（Translation Lookaside Buffer，旁路翻译缓存）**是 CPU 内部的一小块高速缓存，专门存"最近翻译过的：线性页号 → 物理页框"的对应关系。每次访存先查小抄：

- **命中**（绝大多数情况，命中率通常 99% 以上）：直接用，不查登记簿，零额外开销；
- **未命中**：才老老实实走一遍上面三步查表，顺便把结果记进小抄。

代价是：操作系统改动了页表（比如把某页搬到硬盘），必须记得通知 CPU 把小抄里对应的旧记录作废（叫刷 TLB），否则 CPU 会按旧地址找错柜子。切换程序、换 CR3 的时候，小抄里的记录原则上也要大批作废——为什么要作废、有没有办法免掉，值得单独一小节讲清楚（见下一节）。

### 5. PCID：给小抄的每条记录盖一个"哪家的"印章

先说"换 CR3 就大批作废"这条老规矩是怎么来的。小抄上记的是"线性地址 → 物理地址"，可同一个线性地址在不同程序里指的是完全不同的物理页（每个程序一本登记簿）。切换程序时若保留旧记录，新程序拿自己的线性地址来查，可能撞上旧程序留下的同号记录，直接找到**别人的柜子**——数据串门，绝不能发生。所以老 CPU 的规矩简单粗暴：**操作系统一写 CR3（换登记簿），小抄里非全局的记录整本作废**，这就叫"全刷"。

代价随之而来：被换上来的程序每次都从一本空小抄开始，它接下来访问的每一页全是"未命中"，每页都要老老实实走完四级查表（平白多读四次内存），跑上好一阵小抄才重新焐热。系统里程序一多、切换一勤——服务器上尤其如此——大量时间就耗在反复重建小抄上。CPU 厂商先打了个补丁：页表记录里设一个"全局"标志，标了全局的记录（主要是内核的页，所有程序共用同一份）在全刷时豁免。但用户程序自己的页没法标全局（标了真会串门），冷启动之苦依旧。

**PCID（Process-Context Identifier，进程上下文标识符）**是后来的正解，Intel 在 2010 年的 Westmere 一代 CPU 引入，此后成为标配。思路一句话：**给小抄里的每条记录多记一栏——"这是几号程序的"。**

- **编号从哪来**：操作系统给每个程序（准确说每个地址空间）发一个编号，12 位，一共能发 4096 个。这个编号存放的位置很巧：就住在 CR3 的最低 12 位里——页表基址按 4KB 对齐，低 12 位天然空闲，正好借来装编号（又是"借闲置字段"的老套路）。启用它要先在 CR4 里打开一个开关位（PCIDE 位）。
- **记录怎么打标记**：CPU 把一次翻译结果记进小抄时，把当前 CR3 里带着的编号一并记下。从此查小抄变成**双条件命中**：地址对得上、编号也对得上，才算数。
- **切换时发生什么**：操作系统写新 CR3 时，可以在值里附带一个"不要作废"的标记（CR3 值的最高位）。CPU 看到它，就把小抄原样保留——旧程序的记录留着也无妨，编号对不上，新程序永远查不到它们头上。更妙的是**切回来**：甲程序被换下去又换回来，只要它的记录还没被挤掉（小抄容量有限，记录之间会互相挤占，挤掉的只能重查），开局就是热的。冷启动之苦，大减。
- **编号不够用怎么办**：同时活跃的程序可能超过 4096 个，操作系统就要回收编号改发他人。回收前必须先把小抄里打着这个编号的旧记录定向清除，否则新主人会撞上旧主人的记录。为此 CPU 专门备了一条新指令（INVPCID），能按编号精准作废：只刷某一号的、或者某一号里某一页的，不动其他人。
- **它后来还救过急**：2018 年 Meltdown 漏洞的软件修复方案，要求把内核的登记簿和用户的登记簿彻底分开，程序每次进出内核都要换一次 CR3。若没有 PCID，每次系统调用都会伴随一次全刷，性能惨不忍睹；有了编号标记，两套登记簿的记录能在同一本小抄里和平共处、互不干扰，这套修复方案才变得"用得起"。

一句话收束：全刷是"换访客就撕掉整本小抄"；PCID 是"每条记录盖上房号印章，换访客时谁的记录都不撕，查的时候地址和印章双对上才放行"。

### 6. 两个变体：大页与 64 位四级页表

**大页**：页目录记录里有个 PS（Page Size）标志，置上它，这条记录就不指向小册子了，直接指向一个 **4MB 的大页框**，线性地址剩下的 22 位全是页内偏移。翻译一步到位。适合内核自己、显存这类"大块、整齐"的内存，省查表、省小抄。

**64 位**：地址变长后，两级不够分，变成**四级**：48 位有效地址按 9/9/9/9/12 切分——四级索引各 9 位（每级 512 条）、偏移 12 位。走查过程和两级版**完全一样**，只是登记簿多套了两层：CR3 → 四级簿 → 三级簿 → 二级簿 → 页表 → 页框。为什么每级变 9 位？因为 64 位系统里每条记录占 8 字节，一页 4KB 正好装 512 条——严丝合缝，还是同一个设计逻辑。现在还有 57 位地址的五级页表，同理多一层而已，不必被层数吓住：**层数只是簿子的套娃深度，翻译的动作永远是"按索引查一条、拿到下一本簿的地址"重复而已。**

## 三、IDT：出事时照着打的应急电话簿

### 1. 为什么需要一张"突发情况对照表"

电脑运行中随时可能出状况：

- 程序算了个除以零；
- 程序访问的页不在内存里（上一节说的缺页）；
- 键盘被按了一下，键盘控制器喊 CPU 来取数据；
- 网卡收到一个数据包；
- 时钟芯片定时敲一下，提醒操作系统"该换个程序运行了"。

这些事统称**中断与异常事件**。每种事件该由哪段代码处理，必须有一张权威对照表，否则 CPU 撞上事件只能干瞪眼。这张表就是 IDT：**256 个表项，编号 0~255，编号叫向量（vector）**。操作系统开机时把 256 个格子逐一填好：每格写明"这种事件的处理程序在代码段的哪个位置、用什么规矩进门"。CPU 里同样有个寄存器 **IDTR** 记着 IDT 的地址和长度，用 `lidt` 指令装入——和 GDTR 之于 GDT 正好一对。

向量号的分配有历史规矩：

| 向量范围 | 用途 | 例子 |
|---|---|---|
| 0~31 | CPU 异常（Intel 钦定，不许挪用） | 0 除零、8 双重故障、13 通用保护、14 缺页 |
| 32~255 | 外部中断与软件中断（操作系统自由分配） | 键盘、网卡、时钟各占一格；老传统里 0x80（128）曾被 Linux 用作"敲门进内核"的系统调用门 |

### 2. 每一格里写的是什么：门

IDT 的表项叫**门描述符（gate descriptor）**，核心信息三样：

- **处理程序的地址**：在哪个代码段、偏移多少——出事时 CPU 就跳去那里；
- **门的种类**，重点是两种：
  - **中断门（interrupt gate）**：一进门**自动关中断**（把 IF 标志清零）。意思是"处理急事期间别再被别的普通中断打断"，适合硬件中断处理。
  - **陷阱门（trap gate）**：进门**不关中断**，处理期间还能响应别的中断，适合异常处理这类可能耗时的事。
- **门禁级别（DPL）**：只管一件事——**软件主动敲门时**谁有资格。比如用户程序执行 `int 3`（断点）是调试的正当需求，所以 3 号门的 DPL = 3、谁都能敲；而硬件事件是 CPU 自己照表办事，根本不看 DPL——设备敲门不讲级别，天经地义。

### 3. GDT 和 IDT 放一起看就清楚了

| | GDT | IDT |
|---|---|---|
| 记着什么的表 | 段的身份证（分区与门禁） | 事件的处理人（应急电话） |
| 表项叫 | 段描述符 | 门描述符 |
| 谁来查 | 装段寄存器时、特权切换时 | 每次中断/异常发生时 |
| 地址寄存器 | GDTR | IDTR |
| 装载指令 | `lgdt` | `lidt` |
| 表项数量 | 最多 8192 | 固定 256 |

两本表都是开机时操作系统立下的规矩，立完之后 CPU 就靠它们自动运转。

## 四、中断处理：一次"出事"的完整旅程

先把三个容易混的词分清，它们是亲兄弟：

- **中断（interrupt）**：来自 CPU **外部**的事件——设备干完活了、来数据了、时钟到点了。特点是**异步**：和正在执行的程序没关系，随时可能响，与程序的进度无关。
- **异常（exception）**：CPU **自己执行指令时**出的状况——除零、访问的页不在、权限不够、执行了非法指令。特点是**同步**：哪条指令闯的祸，警报就精确地在哪条指令处响起。
- **软件中断**：程序**故意**执行 `int n` 指令敲门，是主动求见（老式系统调用、调试断点走这条路）。现代系统调用改用更快的专用指令，但机制上是同一家人。

三者从"查 IDT"开始走同一条处理通道。下面以最典型的**键盘中断**为例，一步不漏地走完整个流程：

### 第 1 步：设备举手，调度员排队

你按下一个键，键盘控制器把扫描码准备好，通过一根中断线向 CPU 喊话。喊话不是直达的——中间有个调度员叫**中断控制器**（现代电脑是 APIC 体系：设备先报给 I/O APIC，它再转给某个 CPU 核心的 Local APIC）。多个设备同时举手时，调度员按优先级排队，把最急的那个先递给 CPU，并附上它的**向量号**（比如键盘占 33 号）。

### 第 2 步：CPU 在指令的缝隙里响应

CPU 不会把一条指令执行一半就跑开。它先把**当前这条指令完整执行完**，在两条指令的缝隙里检查：有没有待处理的中断？我现在的"请勿打扰"开关（**IF 标志**）开着吗？

- IF = 1：接受中断，进入下一步；
- IF = 0：普通中断先排队等着（操作系统在极短的临界区里会关一下 IF，保护要紧数据改到一半不被打断）；
- 例外是 **NMI（不可屏蔽中断）**：不管 IF，立刻处理——它只留给内存校验错、硬件故障这类"天塌下来"的事。

### 第 3 步：硬件自动封存现场（这一步不用写代码，CPU 全包）

跳去处理程序之前，CPU 硬件自动完成三件事，分毫不差：

1. **换栈（如果需要）**：如果被打断的是 3 级用户程序、处理程序是 0 级内核，直接在用户程序的栈上处理太危险（那根栈不可信、还可能不够大）。CPU 从 **TSS**（还记得吗，它的描述符挂在 GDT 里）中取出内核栈的地址，先换到内核栈，并把用户栈的地址（SS、ESP）压进新栈存好。
2. **压栈存现场**：依次把 **EFLAGS**（一堆状态开关，含 IF）、**CS、EIP**（正执行到哪条指令）压进栈。某些异常还会多压一个**错误码**，写明出事的原因细节（比如缺页异常的错误码会说：是读还是写、是页不存在还是权限问题）。
3. **查电话簿跳过去**：拿向量号查 IDT 第 33 号门，取出处理程序地址，装进 CS、EIP——下一拍，CPU 已经在执行内核的键盘中断处理程序了。如果查的是**中断门**，硬件顺手把 IF 清零：处理急事期间，普通中断暂时别来添乱。

现场被封存成的样子（内核栈上，从栈顶往下）：

```
        ┌─────────────┐ ← 栈顶（处理程序进来时，栈指针就停在这里）
        │  (错误码)    │  仅部分异常有：写明出事的原因细节
        ├─────────────┤
        │     EIP     │  被打断的指令位置（回去的路标）
        ├─────────────┤
        │     CS      │  被打断的代码段
        ├─────────────┤
        │   EFLAGS    │  被打断那一刻的开关状态
        ├─────────────┤
        │  ESP / SS   │  仅特权级切换时有：原来的用户栈地址
        └─────────────┘
```

### 第 4 步：处理程序干活

硬件的活到此为止，剩下是软件（操作系统和驱动）的事，套路固定：

1. 先把其余通用寄存器也压栈保存（硬件只存了最关键的几个，处理程序要动用其他寄存器，得先把人家的东西放好）；
2. 干正事：键盘驱动从控制器读出扫描码，翻译成字符，放进输入缓冲区，唤醒正在等键盘输入的程序；
3. 干完给中断控制器回一个 **EOI（中断结束通知）**："这单处理完了，可以派下一单。"**忘了发 EOI 是新手驱动的经典 bug**——控制器以为你还忙着，之后同类中断再也不派，键盘就此"失灵"。

### 第 5 步：一条 iret，时光倒流

处理程序最后执行 **`iret`** 指令。它是唯一能把第 3 步存的东西**整套弹回去**的指令：EIP、CS、EFLAGS 一次性恢复（若当初换了栈，连 SS、ESP 也换回去）。CPU 回到被打断的那条指令的下一条，继续执行——**被打断的程序完全不知道中间发生过什么**，就像电话铃响时你按了暂停，接完电话按继续，电影一帧不差。

整个过程有多快？从按键到处理完是**微秒级**。而时钟中断用的是同一套流程，只是频率高得多：它每秒响上百到上千次，操作系统在它的处理程序里记账、决定"下一个该轮到哪个程序上 CPU"——你感觉到的"很多程序同时在跑"，就是靠这铃声一次次把 CPU 从一个程序手里转交给另一个。独占着 CPU 死循环的程序也逃不过：它关不掉时钟的铃，铃一响，控制权就回到操作系统手里。

## 五、四个机制合演一遍：一次缺页的全过程

最后把四个主角拉到同一个场景里，看它们如何配合。场景：你双击打开一个大程序，CPU 要执行它的一段代码，发现那页还躺在硬盘上没装进内存。

1. **页表环节**：CPU 执行到这条指令，照例先查页表翻译地址——查到 PTE 时发现 **P 位 = 0**："这一页不在内存里。"翻译中止。
2. **异常环节**：CPU 当场触发 **14 号异常（缺页，#PF）**，把出错的地址放进一个专用寄存器（CR2），错误码写明"读操作、页不存在、用户态"。
3. **IDT 环节**：CPU 拿 14 去查 IDT，14 号格子里是内核缺页处理程序的地址（陷阱门，进门不关中断）。执行第 3 步那套封存现场的动作后，跳进处理程序。
4. **处理环节**：内核一看 CR2 和错误码就明白了：这不是程序出错，是它要的页还在硬盘上。于是安排把这一页从硬盘读进一个空页框，回来把 PTE 填好、P 位置 1，`iret` 返回。
5. **重演环节**：CPU 回到那条没执行成的指令，**重新执行**它。这次查页表一路绿灯，翻译成功，程序像什么都没发生过一样继续跑。整个过程你唯一的感觉是：程序启动时顿了一下。

注意第 5 步的妙处：能"重新执行"，靠的是异常发生时那条指令**还没有产生任何副作用**，现场存得干干净净。这也是异常处理敢于"假装无事发生"的底气。

反过来，如果查表发现的是"权限不够"而不是"页不在"，内核处理完的结论就不是补页，而是终止程序——同样的入口，不同的裁决。Windows 的"内存不能为 read"弹窗、Linux 的段错误（Segmentation fault），大多就是这条链走到了裁决那一步。

## 追问补记一：为什么每个 CPU 一张 GDT？TSS 为什么在 GDT 里？（2026-10-31）

**先纠正一个前提**：GDTR 是每颗 CPU 各自的一个寄存器，架构上根本不存在"全系统共用一张 GDT"这个概念，只有"每颗 CPU 的 GDTR 指向哪张表"。多颗 CPU 的 GDTR 指向同一张物理表是允许的，但 Windows 不这样做，因为表里有几格天生是每 CPU 不同的（WRK 源码 KE/I386/KERNLINI.C 的注释原话："each processor has its own IDT, GDT, and TSS as well as PCR!"）。

**必须每 CPU 不同的格子（32 位 Windows，WRK 实表，共 11 项）：**

| 选择子 | 项 | 基址指向哪 | 每 CPU 不同？ |
|---|---|---|---|
| 0x00 | 空描述符 | — | 同 |
| 0x08 | 内核代码段 R0 Code | 0，界限 4GB，DPL 0 | 同 |
| 0x10 | 内核数据段 R0 Data | 0，界限 4GB，DPL 0 | 同 |
| 0x18 | 用户代码段 R3 Code | 0，界限 4GB，DPL 3 | 同 |
| 0x20 | 用户数据段 R3 Data | 0，界限 4GB，DPL 3 | 同 |
| 0x28 | 主 TSS 描述符 | **本 CPU 的 TSS 本体地址** | **不同** |
| 0x30 | PCR 段（内核态 FS） | **本 CPU 的 KPCR 地址** | **不同** |
| 0x38 | TEB 段（用户态 FS） | 当前线程 TEB，**随线程切换改写** | **不同** |
| 0x40 | VDM 平铺段 | 遗产项 | 同 |
| 0x48 | LDT 描述符 | 当前进程 LDT（多为空） | 随进程变 |
| 0x50 | 双重故障 TSS 描述符 | **本 CPU 的 DF 专用 TSS** | **不同** |
| 0x58 | NMI TSS 描述符 | **本 CPU 的 NMI 专用 TSS** | **不同** |

结论：GDT 是"九成相同、一成私有"。整表只有 88 字节，实现上干脆每 CPU 整表复制一份模板，再把私有格填上本 CPU 的地址。

**为什么 TSS 必须每 CPU 一份**：TSS（任务状态段）是一块内存结构，装着本 CPU 的应急资料，最重要的是 SS0/ESP0（进内核要换的内核栈地址）、64 位下的 IST 专用栈、I/O 权限位图。两颗 CPU 若共用一份 TSS，各自的内核栈地址会互相覆盖——中断在 A 核进来却换上 B 核的栈，当场灾难。

**"TSS 在 GDT 里"的准确含义**：TSS 本体不在 GDT 里；GDT 里是 TSS 的描述符（基址 = TSS 本体的线性地址、类型 = TSS）。CPU 找任何东西都只走"选择子→查 GDT→描述符"这一条路，找 TSS 也不例外。GDT 是通讯录，TSS 是通讯录里登记的地址对应的人——人不住在通讯录里。

**描述符如何对应到物理内存**：描述符存的是线性基址。例：内核执行 FS:[0]，FS 装着选择子 0x30，查本 CPU GDT 第 6 格得基址 = 本 CPU 的 KPCR 线性地址，线性地址 = 基址 + 0，再经页表（CR3 走查）译到物理页，读到的第一个字段就是 PCR 的自引用指针——内核借此知道"我在哪颗 CPU 上"。用户程序走数据段 0x23 时基址为 0，线性地址就是偏移本身，翻译全靠页表，这就是"段被架空"的具体含义。GDT 表本体也是内存：每 CPU 一小块内核非分页内存，GDTR 指向它。

## 追问补记二：每次线程切换，GDT 的 TEB 描述符真的都在变吗？不能靠 CR3 区分吗？（2026-10-31）

**结论先行：描述符一直在变——每次线程切换都被改写。CR3 解决的是另一件事，两者不互相替代。**

先纠一个前提：线程没有各自的地址空间——同一进程的全部线程共享一个地址空间（一本页目录、一个 CR3）。每线程独有的是 TEB（在进程用户空间里划出的一块不重叠区域，各线程线性地址不同）、用户栈、内核栈。

提问者的推理对一半：**跨进程**切换时 CR3 确实换了，同一线性地址落到不同物理页；两个不同进程的线程，TEB 甚至可能位于同一线性地址、纯靠 CR3 区分。但**同进程线程切换是决定性反例**：CR3 根本不变（同一本页目录），而两个线程的 TEB 在同一地址空间里线性地址不同。FS 必须从甲线程的 TEB 转指乙线程的 TEB——描述符里存的是线性地址，CR3 帮不上忙，唯一办法是改写描述符基址。

源码实证（WRK，`KE/I386/CTXSWAP.ASM:571-580`，就在线程切换函数 SwapContext 本体里）：

```
; Set the TEB descriptor to point to the thread TEB and set the TEB address
        mov     eax, [esi]+ThTeb        ; get user TEB address
        mov     [ebx]+PcTeb, eax        ; set user TEB address
        mov     [ecx]+(KGDT_R3_TEB+KgdtBaseLow), ax
        mov     [ecx]+(KGDT_R3_TEB+KgdtBaseMid), al
        mov     [ecx]+(KGDT_R3_TEB+KgdtBaseHi), ah
```

每次切换，它把新线程的 TEB 地址拆成三段（基址在描述符里被拆成 BaseLow/BaseMid/BaseHi 三个碎片存放，是 286 时代的历史格式），写进本 CPU 的 GDT。变的是基址，界限与类型不动；FS 里的选择子永远是 0x38|3，变的只是它背后的基址。

配套细节：改了内存中的描述符，CPU 段寄存器内部的描述符缓存不会自动刷新；所以返回用户态的路上要按陷阱帧里存的 KGDT_R3_TEB|3 重新装载 FS，新基址才生效——"改表 + 重装 FS"是一套连贯动作，这也是它必须由切换路径亲自做的原因。成本就是往本 CPU 的 GDT 里写几个字节，可忽略；且因 GDT 每 CPU 一份，改写只影响本 CPU——这正是补记一里"每 CPU 一张 GDT"的第三个理由的实证。

64 位分叉：64 位线程的 FS 基址不走描述符，改走 MSR（IA32_FS_BASE），切换时直接写 MSR——形式变了，"每次切换都要更新 FS 指向"没变。GDT 里为 WOW64 的 32 位线程保留了兼容模式 TEB 描述符（KGDT64_R3_CMTEB），仍靠改写它；顺带一瞥：AMD64 初始化时把处理器编号编码进该描述符的界限字段（`KE/AMD64/ALLPROC.C:352-354`），是给兼容模式代码读当前处理器号用的小把戏。

一句话收束：**CR3 管"进程之间同名地址不同家"，TEB 基址改写管"同一个家里每个线程各有各的房间"——两把钥匙开两把锁。**

## 追问补记三：FS 到底怎么"重新装载"？64 位 MSR 怎么找到 TEB？处理器编号怎么编进界限还不坏事？（2026-10-31）

### 1. FS 重装的实证：一条 pop fs / mov fs 指令

"装载段寄存器"是一个具体的硬件动作：执行 `mov fs, 选择子` 或 `pop fs` 的那一拍，CPU 拿选择子的索引去本 CPU 的 GDT 里把描述符读出来，做类型/级别/存在性检查，然后把基址、界限、属性抄进 FS 在 CPU 内部的隐藏缓存——此后所有 FS: 访问都用这份缓存，直到下一次装载。改 GDT 内存不影响已装载的缓存，这就是为什么"改完基址必须重装"。

WRK 出口路径有两处实证：

- 全恢复出口 EXIT_ALL（`KE/I386/KIMACRO.INC`）：把栈指针挪到陷阱帧的 SegFs 字段处，执行一条 **`pop fs`**——把帧里存的选择子（常数 KGDT_R3_TEB|3，即 0x3B）弹进 FS，触发上述整套查表+抄缓存。注意 EXIT_ALL 先判断 SegCs 是不是内核代码段：返回内核态就整段跳过段寄存器恢复，FS 保持指着 PCR 不动。
- 快速出口（如 `KE/I386/TRAP.ASM` 中的一条返回路径）：`mov edx, KGDT_R3_TEB OR RPL_MASK` 之后 **`mov fs, dx`**，紧接着 iretd。

关键分工：**陷阱帧里存的是常数"第几格"（0x3B），GDT 格子里存的是"哪个 TEB"（基址）**。线程切换只改格子，成千上万份陷阱帧一份都不用动。时序上，切换回来的线程是在内核里"活过来"继续往外退的，退到出口例行执行 pop fs 时才完成重装——重装不是为切换特设的步骤，是每次回用户态的例行动作；切换只是赶在例行重装之前把格子改了。若省了重装，FS 缓存里仍是上一个线程的 TEB 基址，用户代码会读写别人的 TEB，数据错乱兼信息泄漏，所以这步是硬性的。

### 2. 64 位：MSR 的值就是基址本体，不查任何表

x86-64 给 FS、GS 各配了一个 MSR（型号专用寄存器）：IA32_FS_BASE（0xC0000100）、IA32_GS_BASE（0xC0000101），另有 IA32_KERNEL_GS_BASE（0xC0000102）供 swapgs 交换用。64 位模式下，带 FS:/GS: 前缀的访存，地址生成部件直接算 **线性地址 = MSR 里的基址 + 偏移**——基址就躺在 CPU 内部的寄存器里，不查 GDT、不读内存、不存在"装载/刷新缓存"这个环节；内核用 WRMSR 指令写入即刻生效。FS/GS 在 64 位模式下也不做界限检查。其后仍走页表翻译到物理页，与 32 位无异。

补正一句 Windows 的具体分工（上一条补记说得不够准）：64 位 Windows 里担纲指 TEB 的是 **GS**——用户态 GS→本线程 TEB、内核态 GS→本 CPU 的 KPCR，进内核时 swapgs 指令把 IA32_GS_BASE 与 IA32_KERNEL_GS_BASE 整对交换，出内核再换回。FS 的 MSR 机制与 GS 完全相同，只是 Windows 把这个角色分给了 GS；32 位（WOW64）线程跑在兼容模式下，FS 仍走 GDT 描述符（KGDT64_R3_CMTEB），与补记二所述一致。

### 3. 处理器编号编进界限：占高位、借闲置字段

源码（`KE/AMD64/ALLPROC.C:352-354`）：描述符的界限字段共 20 位（LimitLow 16 位 + LimitHigh 4 位）。编号被塞进**最高 6 位**：LimitHigh = Number >> 2，LimitLow 的第 15–14 位 = Number & 3；**低 14 位原样保留**。

- **长度确实变了，而且只会变得很大**：编号占的是最高位，它的最小单位（2¹⁴）就等于整个低位部分的最大值。所以编完的界限 = 编号 × 2¹⁴ + 低位余数，动辄一万多起步（页粒度下还要再放大 4096 倍）；而经这个段访问 TEB 的偏移永远只有几 KB，永远碰不到界限。0 号 CPU 时编号位为 0，界限就等于保留的低位——即这个描述符出厂界限的主体。
- **为什么敢借**：界限检查只在"拿这个段访存"时拿偏移比大小，它在平坦模型时代早已不是真正的隔离防线——真正的隔离是页表（TEB 之外的页映射与权限由页表说了算）。界限字段对这个段而言是闲置字段，借来当数据通道没有功能损失。
- **怎么读回**：`lsl`（Load Segment Limit，装载段界限）指令可以无特权地读出一个描述符的界限——用户态代码执行 lsl 读回这个数，再右移还原出编号。于是 WOW64 的 32 位代码不经过任何系统调用就能知道"我在几号 CPU 上"，这就是这条编码通道存在的目的：收发两端分别是内核初始化时的写入和用户态的 lsl 读取。

## 追问补记四：嵌套页表是什么？为什么虚拟机需要第二套页表？（2026-10-31）

**先和"多级页表"划清界限**：多级页表是"一本登记簿分册装订"（一维，是深度）；嵌套页表是"两套登记簿互相套住"（二维，是又加了一个翻译维度）。后者是虚拟化特有的东西。

**它要解决什么问题**：虚拟机里的客户操作系统以为自己独占一台真机器，照常维护自己的页表，把客户虚拟地址（GVA）翻译成它以为的"物理地址"（GPA）。但 GPA 是假的——那台"机器"并不存在，客户的内存是宿主机上的一堆散页。于是必须有第二套页表，由虚拟机监控器（Hypervisor）维护，把 GPA 再翻译成真正的宿主物理地址（HPA）。每次访存实际上是两段翻译接力：GVA →（客户页表）→ GPA →（宿主页表）→ HPA。

**硬件支持之前靠"影子页表"**：监控器在幕后把两段翻译预先合成一套 GVA→HPA 的表让 CPU 直接用，但必须拦截客户对页表的一切修改、CR3 的一切切换去同步合成表，开销和复杂度都极高。

**硬件嵌套页表**（Intel 叫 EPT 扩展页表，2008 年 Nehalem；AMD 叫 NPT 嵌套页表，2007 年 Barcelona 先行）：CPU 的查表硬件亲自走两套表。机制是"二维走查"：读客户页表的每一级条目之前，那个条目所在的 GPA 要先过一遍宿主页表找到 HPA，才能把条目读出来——等于查一本簿子的每一页，都得先用另一本簿子定位那一页存在哪。代价可算：客户四级 × 每级"宿主四级查表 + 读条目 1 次"，再加数据页本身的一次宿主翻译，最坏光翻译就要读约 24 次内存（不带任何缓存时）。所以虚拟化下 TLB 和各级走查缓存比裸机还要命门；宿主侧用 2MB 大页能砍掉一半以上的宿主查表步数，是云厂商的常规操作。

**其他规则**：两级权限取交集——任一级说不许，整体就不许，宿主随时能单方面收紧。缺页分两种：客户自己的页表说"不在"，是客户操作系统自己的缺页异常、自己处理，监控器不管；宿主页表说"这个 GPA 根本没给过你/被宿主换出了"，叫 EPT 违例，触发 VM 退出（控制权交回监控器的一种事件），由监控器善后。TLB 方面有 VPID（Intel）/ASID（AMD）给每个虚拟机的记录打编号——正是上一节 PCID 思路在虚拟机维度的翻版：切虚拟机也不全刷。

**为什么它重要**：嵌套页表把页表相关的拦截几乎清零，是硬件虚拟化从"能用"变"好用"的分水岭，现代云计算的地基之一。再往上还有"虚拟机里套虚拟机"，走查变三维，代价继续乘上去——原理不变，仍是每多一层房东，就多一整套簿子要查。

## 追问补记五：现代系统调用的专用指令有哪些、怎么执行？时钟中断是几号？还有比它优先级更高的吗？（2026-10-31）

### 1. 专用指令：两组半

`int n` 慢在它什么都管：查 IDT 门、硬件压栈五件（SS/ESP/EFLAGS/CS/EIP）、经 TSS 换内核栈，一趟下来大量访存。专用指令的思路反过来——什么都不保存，只把几个寄存器一换就跳进内核，记账的活全留给软件手工做。具体有两组：

- **SYSENTER / SYSEXIT**（Intel，Pentium II 起，32 位时代的主力）：入口三要素预先写在三个 MSR 里——IA32_SYSENTER_CS（0x174，内核代码段选择子）、IA32_SYSENTER_ESP（0x175，内核栈指针）、IA32_SYSENTER_EIP（0x176，内核入口地址）。执行 SYSENTER 时 CPU 只做：段寄存器换成 MSR 里的值、ESP 换成 MSR 里的值、EIP 跳到 MSR 里的地址。**不压栈、不保存返回地址、不存 EFLAGS**。连锁后果：① 返回地址和用户栈指针靠软件约定传递（ntdll 的桩先把 ESP 放进 EDX 再执行 SYSENTER；返回时 SYSEXIT 从 ECX 取用户 EIP、从 EDX 取用户 ESP 跳回去）；② SYSENTER_ESP 是"每 CPU 一个"的固定值、装不下"当前线程的"内核栈，所以 Windows 的入口代码（KiFastCallEntry）先落在本 CPU 的 DPC 栈上，再照 TSS 里的 ESP0 二次跳板到本线程的内核栈，并手工把陷阱帧伪造出来（WRK `KE/I386/TRAP.ASM:1136` 起）。
- **SYSCALL / SYSRET**（AMD 发明，64 位时代的正主，Intel 在 64 位上跟进）：三个关键 MSR——IA32_LSTAR（0xC0000082）存 64 位内核入口地址（Windows 里就是 KiSystemCall64，`KE/AMD64/TRAP.ASM:1682`）；IA32_STAR（0xC0000081）打包存内核与用户的代码/栈段选择子；IA32_FMASK（0xC0000084）是"进门要清掉哪些标志位"的掩码（Windows 用它清 IF 等）。执行 SYSCALL 时：**RCX ← 返回地址 RIP、R11 ← RFLAGS**（存在寄存器里，还是不压栈）、RIP 换 LSTAR、段换 STAR、RFLAGS 按 FMASK 掩一遍、CPL 变 0。注意它**连栈都不换**——RSP 还指着用户栈，所以内核入口第一件事就是 swapgs 找到本 CPU 的账本、再手工把 RSP 换成本线程的内核栈。一个著名连锁细节：SYSCALL 把 RCX 占作返回地址，所以 64 位系统调用约定里第一个参数改放 **R10**（Windows、Linux 皆然）——不是谁拍脑袋定的，是被这条指令逼的。历史坑：2012 年 CVE-2012-0217，Intel 实现的 SYSRET 在返回地址非规范时会在内核态带着用户栈触发异常，多家系统经虚拟化中招，后来靠软件规避。
- 半组：Linux 32 位长期用 `int 0x80`，Windows 的 `int 2Eh` 是 XP 之前的正门；`int 3`（断点）至今现役，原因在它的编码只有一个字节（0xCC），能盖住任意指令的第一个字节下断。

### 2. 时钟中断几号——分三层答

- **IRQ 编号**：老 PC 上定时器芯片（PIT）接在中断控制器的 **IRQ0**，这是最经典的答案。
- **中断向量**：进保护模式后 IRQ 被重映射避开 0–31 号异常区，PIC 时代时钟是 **0x20** 号向量；APIC 时代节拍改由每 CPU 的本地 APIC 定时器产生，向量由操作系统自选——**Windows 选 0xD1**（这是 HAL 的选择、不是架构钦定；Linux 选 0xEC）。顺带分清：主板上还有个 RTC 实时时钟芯片走 IRQ8，那是"日历时钟"，不是操作系统节拍的主时钟。
- **IRQL 佐证**（WRK 头文件 `INC/I386.H`、`INC/AMD64.H`）：时钟运行在 CLOCK_LEVEL——32 位是 28，64 位是 13；64 位上向量优先级类恰与 IRQL 对齐，0xD1 正落在第 13 类，互为印证。

### 3. 有没有比时钟优先级更高的——有，而且时钟在两个时代的排位还不一样

在操作系统的 IRQL 优先级表内（数值越大越高）：32 位上时钟（28）之上还有 **IPI_LEVEL 29**（核间中断，别的 CPU 喊你办事，如 TLB 击落，必须能打断节拍处理以便全机协调）和 **POWER_LEVEL 30**（电源故障）；之下紧挨着 PROFILE_LEVEL 27（性能剖析定时器）和全部设备中断。64 位表压缩成 16 级：时钟 13 之上是 IPI/POWER 的 14，以及**剖析定时器 PROFILE_LEVEL 直接顶到 15**、与 HIGH_LEVEL 同级（`INC/AMD64.H:350-354` 实测如此）。表外还有两位不参赛的选手：**NMI（不可屏蔽中断）**不走这套仲裁，硬件上压过一切可屏蔽中断；**SMI（系统管理中断）**更在 OS 的视野之外，连 NMI 都压得住。对照史：PIC 年代 IRQ0 是中断控制器上物理优先级最高的输入，时钟曾是外部中断之王；到了 APIC 时代，它退居第二梯队——上面让给了"多核协调"和"保命"这两类事。

## 追问补记六：调度器没在跑，中断处理凭什么能"唤醒"进程？EOI 到底怎么发、为什么 iret 不能代劳？（2026-10-31）

### 1. 唤醒 ≠ 切换：调度器不是一个人，不需要"在场"

误解的根源在把调度器想成一个需要正在运行的独立实体。它不是——调度器是**一套数据结构（等待队列、就绪队列）加一组随时可被任何内核代码调用的函数**，更像一块公告板系统，而不是值班员。"唤醒"拆开就是纯数据操作：把线程从等待队列摘下、状态改成就绪、写进就绪队列。任何在内核里跑的代码走到"公告板"前改一下名单，唤醒就完成了，不需要谁批准。

键盘这条链的真实分工（按 IRQL 划界）：

- **ISR（DIRQL，很高）**：只能干粗活——从键盘控制器读走扫描码、存进驱动的缓冲区、排一个 DPC 就撤。它不能直接碰调度队列：在那么高的级别上动调度数据既违反锁的规矩，也没法处理唤醒引发的连锁反应。
- **DPC（DISPATCH_LEVEL）**：干细活——翻译扫描码、把字符送进输入队列、满足那个正挂起等待的读请求，调用内核的"满足等待"例程：等待线程被摘下等待链、放上就绪队列。**唤醒到此完成，全程没有"调度器在运行"这回事，只有调度的数据结构被修改。**
- **切换（让它真跑起来）是第三步，发生在最近的检查点**：中断/DPC 退出路径在收尾时发现"就绪队列里有个比当前线程更该跑的"，就把人选记进本 CPU 账本（NextThread）并请求一次调度，在 IRQL 降下来、执行 iret 回家之前，借这股正在退出的执行流顺手完成换栈（SwapContext）。被唤醒的线程就这样"凭空"开跑——它需要的不是调度器在场，而是**名字上了名单 + 每个出口都会瞥一眼名单的规矩**。Linux 骨架相同：唤醒函数改状态、入队，并给当前线程贴一张"需要重调度"的便签，从中断返回的路径负责检查便签并执行切换。

### 2. EOI：写给另一个器件的结单，必须显式发

**EOI（End Of Interrupt，中断结束通知）不是 CPU 的事，是中断控制器的事**——CPU 和控制器是两个独立单位。控制器把一个中断递给 CPU 时，会在自己的账本上把这一路标成"处理中"（in-service），并在此期间扣住同级和更低优先级的中断不再递送。EOI 就是那句"这一单结了，擦掉处理中标记，可以递下一件"。

**怎么发——确实就是几条指令，本质是一次写寄存器：**

- 8259A PIC 时代：往 PIC 的命令端口写命令字 0x20，两条指令：`mov al, 20h` / `out 20h, al`（从片级联时还要给从片端口 0xA0、主片各写一次）。
- APIC 时代：往本地 APIC 的 EOI 寄存器写 0——它是内存映射寄存器，地址在 0xFEE000B0，一条 `mov` 内存写即可；x2APIC 模式改走 WRMSR 写 MSR 0x80B。
- 真实系统里驱动不用自己写：Windows 的中断退出路径统一调 HAL 的 HalEndSystemInterrupt（WRK 的 `KE/I386/CLOCKINT.ASM`、`INTSUP.ASM`、`TRAP.ASM` 都声明导入了它），由 HAL 按本机控制器型号选写法。这正是 HAL 存在的理由之一：跟具体芯片打交道的脏活被隔离在这一层里。

**为什么 iret 代劳不了，四条：**

1. **对象不同**：iret 只负责恢复 CPU 自己的寄存器现场（栈上五件），它的语义里没有"通知外部器件"这一项；CPU 甚至不知道系统装的是哪种控制器、几个、如何级联。
2. **场合分不清**：iret 还用于异常返回和系统调用返回——异常是 CPU 内部产生的，控制器账本上根本没有这一笔，乱发 EOI 会擦掉别人正在处理中的标记，把账做乱；伪中断（APIC 的 0xFF 向量）更明确规定**不许**发 EOI，因为硬件压根没置处理中位。
3. **时机是政策不是定式**：有的系统提前发 EOI 以允许同级中断嵌套、换响应速度；有的拖到最后发以防重入冲爆内核栈。这种取舍只有操作系统懂，写死在指令里就没得选。
4. **漏发的死相可验证**：不发 EOI，那一路（APIC 下是整个优先级类及以下）会被控制器永远扣住——键盘第一下有反应、之后全哑，就是这个故障的典型长相。

一句话收束：**iret 是 CPU 跟自己交账（"我回去了"），EOI 是操作系统跟控制器交账（"你那一单结了"）——两个账本、两家单位，合并不了。**

## 追问补记七：TSS 里怎么会有 ESP0？还有 ESP1、ESP2 吗？RFLAGS 和 EFLAGS 什么关系？（2026-10-31）

### 1. 先把本体和描述符再分清一次

GDT 里的是 **TSS 描述符**（一个指针条目）；**TSS 本体**是内存里一块定格式的结构体（一张状态登记表），CPU 靠 TR（任务寄存器，开机时装载一次）随时找得到它。本体里装什么：其原始设计是装一整个任务的全部现场（通用寄存器、段寄存器、CR3 等），供 286/386 时代的"硬件任务切换"使用；现代操作系统嫌它慢，早已不用硬件切换，于是本体里大部分字段荒废，**活着的主要是三对栈指针**——这就引出 ESP0 的来历。

### 2. ESP0/SS0 是什么：是的，真有 ESP1、ESP2

TSS 开头排着三对字段：**(SS0, ESP0)、(SS1, ESP1)、(SS2, ESP2)**，分别是"要进入 0、1、2 号特权级时该用哪个栈"。规则是这样的：只要发生**从外层特权级向内层**的转移（典型：用户态 ring 3 被中断打断、要进 ring 0 执行内核），CPU 绝不能沿用外层的栈——不受信任、空间和内容都不受控、旧现场还得有个地方压。于是硬件在压栈之前先查 TSS：目标是 ring 0 就取 **SS0:ESP0** 换上，用新栈压旧 SS:ESP 和 EFLAGS/CS/EIP。所以你的每一次系统调用、每一次硬件中断进内核，落脚的内核栈地址**既不在 IDT 里也不在 GDT 里，就存在 TSS 的 ESP0 字段里**——这是它每天都在干的活。

为什么备三对、现代系统却只用一对：架构有 4 个特权级，从外向内落脚就有 0、1、2 三种目标（ring 3 是最外层，只有出发、没有"落进 ring 3 要换栈"的场景），格式于是配满三对。历史上 OS/2 真用过 ring 2 跑部分驱动，ESP2 不是纯摆设；但 Windows、Linux 只用 ring 0 和 ring 3，**ESP1/ESP2 终身闲置（填 0）**——和 GDT 里那些空格子同理：格式比用法活得久。

ESP0 怎么保证永远指着"当前线程"的内核栈：**每次线程切换，SwapContext 亲手改写它**。WRK 实证（`KE/I386/CTXSWAP.ASM:594-595`）：取本 CPU 的 TSS 地址，把新线程的内核栈顶（ThInitialStack）写进 TssEsp0 字段。于是两条进门路径共用这块随切换刷新的牌子：走 IDT 门的（中断、int 指令），CPU 自己读 ESP0 换栈；走 SYSENTER 的，硬件不读 TSS（只认 MSR 里每 CPU 固定的中转栈），由入口代码 KiFastCallEntry **以软件方式读 TSS.ESP0** 完成二次跳板——补记五里那句"按 TSS 里的 ESP0 跳板"，读的就是这个字段。注意 TR 一辈子不变（每 CPU 固定一块 TSS），变的只是 ESP0 的内容——又是"位置固定、内容随切换改写"的老设计。

64 位的 TSS 变了样：寄存器现场区整个删掉（长模式彻底放弃硬件任务切换）；栈字段升级为 64 位的 **RSP0/RSP1/RSP2**（分工照旧，1、2 继续闲置；硬件中断发生特权级转换时 CPU 仍靠 RSP0 换栈）；新增 **IST1–IST7**（中断栈表）七个专用栈指针，给 NMI、双重错误这类绝不能共用普通栈的场合——i386 时代靠 DF、NMI 两个独立 TSS（见 GDT 实表）绕的弯子，64 位直接内建进 TSS 本体了。

### 3. RFLAGS：是 EFLAGS 的 64 位容器，低 32 位原封不动

你的猜测对，补一个精确版：**FLAGS（8086，16 位）→ EFLAGS（386，32 位）→ RFLAGS（x86-64，64 位）**，和 AX→EAX→RAX 是同一条加宽路线。RFLAGS 的**低 32 位与 EFLAGS 一一对应、每个位的含义完全不变；高 32 位全部保留未用**——不是新添了一套 64 位标志，而是老寄存器被装进更大的容器，上半截空着。

里面的住户分三类：① **状态标志**（运算结果）：CF 进位、ZF 零、SF 符号、OF 溢出等，算术指令写、条件跳转读；② **DF** 方向标志，管串操作往哪个方向走；③ **系统标志**：IF（中断允许——清零时可屏蔽中断一律不应答）、TF（单步，调试器靠它）、IOPL、AC 等。IA32_FMASK 关心的正是第三类：SYSCALL 进门后最初几条指令是全系统最脆弱的时刻——栈还没换（RSP 还指着用户栈）、本 CPU 账本还没就位，此刻若 IF=1 让设备中断打进来，硬件会把现场往用户栈上压，直接灾难；若 TF=1，单步陷阱会插进内核入口流程。所以 FMASK 是一张"进门清单位"清单：清单里点到的位（Windows 点了 IF、TF 等），CPU 在进门的同一拍顺手清零，等入口代码站稳了再自己开回来。返回时则从 R11 恢复——正是 SYSCALL 进门时把原 RFLAGS 存进 R11 的那一笔（见补记五），两件事在这里接上。顺带一提：陷阱帧里压着的那份"EFLAGS"，到了 64 位就是 RFLAGS 的低 32 位，字段名还沿用老名字——压栈五件的样貌在 64 位基本没变，只是成对地换了名字（EIP→RIP、ESP→RSP、EFLAGS→RFLAGS）。

## 追问补记八：用户复述"键盘中断→ISR→DPC→唤醒→切换"全链的核对与四处磨精确（2026-10-31）

用户复述的骨架全对：用户代码运行中 → 键盘中断 → ISR 升至 DIRQL、读走扫描码、排 DPC → 退出路上 IRQL 降到 DISPATCH 时排空 DPC、DPC 执行唤醒 → 本应返回被中断处之前，调度介入把 CPU 交给被唤醒线程。需磨精确的四处：

1. **IRQL 不是 ISR 升的**：中断分发代码在调用 ISR *之前*就把 IRQL 升到该设备的 DIRQL，ISR 一出生已在高位；ISR 返回后也是分发/退出代码负责往下降。
2. **"拷贝设备缓冲区"的准确动作**：ISR 用读端口指令把扫描码从键盘控制器的数据寄存器里*读走*——读走本身就是给硬件销账，不读，控制器会一直举着中断请求不放。
3. **DPC 排空的位置与触发**：不是降到 DISPATCH 后"顺便"排，而是 IRQL 往下降的路上经过 DISPATCH 这一层时，因排 DPC 时已留下一笔"挂起的调度请求"，被 KiDispatchInterrupt 截住先排空 DPC 队列——被中断线程在此之前不会恢复运行。排空发生在下降的半路上，不是终点之后。
4. **切换的决策点与条件**：排空后没有"调度器"这个外人介入，是 KiDispatchInterrupt 顺手查本 CPU 账本：若唤醒动作已把 NextThread 填好，就在 DISPATCH_LEVEL 就地换栈（经 KiSwapContext）；没填就继续降 IRQL、iret 回到被中断处。且立即切换有前提——**被唤醒线程必须比被中断的线程更该跑（优先级更高）**；否则唤醒只完成登记，被中断线程先回去继续跑，切换等下一个时机（它时间片耗尽或阻塞时）。附带：被唤醒线程接管后，先在内核里从当初阻塞的等待点继续往外退、把那次读调用收尾，才经系统调用出口回到用户态，不是从用户代码里凭空冒出来。

## 追问补记九：既然有 TR 记着 TSS，为什么 GDT 里还要有一项 TSS 描述符？（2026-10-31）

**先纠一个小误会：TR 里存的不是 TSS 的地址，而是一个选择子加一份描述符缓存——和 FS 是同一个物种。**装载指令 LTR 的操作数就是一个选择子：CPU 拿它去 GDT 里查到那一格 TSS 描述符，做类型/存在性校验，把基址、界限、属性整份抄进 TR 的隐藏缓存，并把描述符里的"忙"位置上。所以因果是反的：**不是"有了 TR 还多余记一格描述符"，而是"描述符本来就住在 GDT 里，TR 只是把本 CPU 当前用的那一格抄了一份在手边"**。没有 GDT 里那一格，LTR 无从装起——缓存不能取代主记录，正如 FS 的存在从不让 GDT 里的 PCR/TEB 描述符变得多余（同一课的原样重演）。

**描述符里也不止有地址**：还有界限（CPU 读 ESP0 等字段时要做越界检查）、类型与"忙"位、存在位、DPL。若 TR 直接存一个裸地址，这套元信息和检查便无处安放。TSS 属于"系统段"，与代码段、数据段、LDT 共用描述符这一种管理机制，是 386 架构的统一设计。

**历史本相**：硬件任务切换年代，GDT 里的 TSS 描述符是主角——每个任务一格，任务门（IDT/GDT 里的门描述符）指着它们，CPU 靠它们在任务间跳转；现代"每 CPU 一块 TSS、TR 装一次"的用法只是它的退化形态。

**活证据（i386 Windows）**：GDT 实表里的 KGDT_DF_TSS、KGDT_NMI_TSS 两格为什么必须存在——双重错误（#DF）与 NMI 在 32 位 Windows 经 IDT 里的**任务门**送达：事件发生时 CPU 执行一次硬件任务切换，把这两格之一装进 TR，在预设备好的独立栈与现场上跑处理程序。若 GDT 里没有这两格，CPU 在最危急的时刻找不到落脚点。64 位取消了任务门，这两格的职能被 TSS 内部的 IST 字段接管（补记七），于是 64 位 GDT 里只剩主 TSS 一格描述符——且它需要装下 64 位基址，是 16 字节、占相邻两格宽的胖描述符。

**闭环细节**：CPU 缓存的是"表在哪"（描述符），不是"表的内容"——每次中断进门要换栈时，ESP0 的值都是现从 TSS 本体内存里读的。所以 SwapContext 只管改内存里的 ESP0 字段就立即生效，用不着重装 TR（补记七那条链的最后一环）。

## 追问补记十：ISR 返回后，"逐级降 IRQL"到底是谁在做？降到哪一级为止？（2026-10-31）

**先纠正补记八定稿里的一处措辞不严**："ISR 退出收尾"不准确——**ISR 什么收尾都不做**，它只向调用者返回一个"处理了/没处理"的布尔值就离场。升、降、EOI、恢复现场，全是包着它的脚手架干的，分工如下（WRK i386 实证）：

- 进门：每个中断对象有一段生成的**分发模板**代码，先建陷阱帧，再由 KiInterruptDispatch（`KE/I386/INTSUP.ASM`）调 HAL 的 **HalBeginSystemInterrupt(该中断的 DIRQL, 向量, &OldIrql)**——HAL 把 TPR 抬到 DIRQL，并把**中断发生前那一刻的 IRQL** 写回栈上的一个格子里存好。
- 干活：分发代码沿中断对象的 ISR 链逐个调用 ISR（共享中断可能不止一个）。
- 出门：模板尾部的 **INTERRUPT_EXIT 宏**（`KE/I386/KIMACRO.INC`）栈上就摆着两个参数——"previous irql"与"要发 EOI 的向量"；它先 cli，再调 **HalEndSystemInterrupt(OldIrql, 向量)**：HAL 在这一个函数里做完两件事——**发 EOI + 把 TPR 写回 OldIrql**；随后跳 **Kei386EoiHelper**（`KE/I386/TRAP.ASM:1771`）检查回用户态时有无待投递的用户 APC，最后 EXIT_ALL、iretd。

**降到哪一级**：就是进门时存下的那个 OldIrql，一步不差。中断打在普通线程代码上，就是 PASSIVE_LEVEL；打在正跑 DPC 的 DISPATCH_LEVEL 代码上，就只降回 DISPATCH_LEVEL；打在 APC 处理中，就降回 APC_LEVEL。中断处理是严格的栈纪律：垫多高、还原多高，绝不自作主张降到底。

**"逐级"二字的真相**，单看这一次降，TPR 其实是**一次写回**（一个值直达 OldIrql），不是一格一格爬楼梯。但"逐级"的观感有两重真实来源：① **嵌套**——更高优先级的 ISR 可以中途打断低的，每层各存各的 OldIrql，退出时按栈一层层还原，看起来就是逐级下降；② **下降途中的检查点**——i386 的 DPC/APC 是"软件中断"，没有真向量，靠本 CPU 账本里的请求标志模拟（`CLOCKINT.ASM:435` 等处可见对 PbDpcInterruptRequested 的检查）：IRQL 的下降一旦越过 DISPATCH 这条线且标志已置位，执行流先被 KiDispatchInterrupt 接走（它就运行在 DISPATCH_LEVEL，排空 DPC、必要时换线程），办完再继续下降；EoiHelper 在回用户态前对 APC 做同样的检查。所以行为上确实是"逐级降、逐级办事"，只是楼梯不在 TPR 的写动作里，而在下降路径的检查点和嵌套的栈帧里。前提同样重要：若 OldIrql 本来就 ≥ DISPATCH_LEVEL，本次退出不排 DPC——被中断的那段高 IRQL 代码还没降下来，DPC 只能等它自己降。

## 追问补记十一：排空 DPC 时就地换了线程，没执行 iretd 就跑去执行新线程，不乱吗？（2026-10-31）

**不乱。关键在于：iretd 不是被"跳过"了，而是被"推迟"了，推迟的凭证就压在被换出线程自己的内核栈上，跟人走。**

把切换的物理动作看清就没有神秘感了。线程切换（SwapContext）的本质是换栈：把当前内核栈指针存进旧线程的对象、把新线程的内核栈指针装进来、最后一条 ret 落进新线程那条**冻结着的调用链**里继续。对 CPU 而言，不存在"谁的退出路径没走完"这种全局状态——只有栈。被中断线程那半截没走完的退出路径（KiDispatchInterrupt 的尾巴、EoiHelper 的检查、EXIT_ALL、以及压在栈底的那份陷阱帧），原封不动冻在它自己的内核栈上，一个字节都不丢。

于是时序是这样的：换出时，它停在"退出路径走到一半"的状态；将来它被再次选中换回，SwapContext 先"返回"进它自己的调用链，它把剩下的几步走完，最后执行 EXIT_ALL → **用它自己那份陷阱帧执行属于它的那次 iretd**，回到它自己的用户代码。每个线程回用户态用的永远是自己栈底的陷阱帧，不存在串门。两个线程完全可以同时"卡在各自退出路径的中途"（一个冻着、一个在跑），因为全部状态都在各自的栈里，CPU 寄存器只是过客。

这件事能成立的前提，正是"内核栈必须每线程一本"（见本系列此前答疑）：若全 CPU 共用一张内核栈，半截调用链无处冻结，"退出路上换人"根本做不到。几个配套细节：旧线程是被抢占的，会被放回就绪队列同优先级队首、保留剩余时间片，不会丢；EOI 在此之前已由退出宏开头的 HalEndSystemInterrupt 发过，不会因换线程漏发；新线程接管后也不是从用户代码冒出来，而是先在内核里沿自己的调用链把当初阻塞的那次调用退完，再走它自己的出口。

一句话：**iretd 不是 CPU 的全局仪式，而是每个线程各自回家时要走的门；换线程只是把"走门"推迟到它下次被换回来时补走，门票（陷阱帧）一直揣在它自己兜里。**

## 追问补记十二：建陷阱帧时不怕又来中断吗？TPR 为什么不排在第一步？（2026-10-31）

**担心多虑了：进门那一拍，中断已经被硬件关好了——关它的不是软件，是"门"本身。** 设备中断在 IDT 里走的是**中断门**，它和陷阱门的根本区别就在这里：CPU 经中断门跳转时，压完 EFLAGS/CS/EIP 后，顺手把当前 EFLAGS 里的 **IF 清零**再跳进处理代码。所以模板的第一条指令开始执行时，可屏蔽中断已经是关着的，建帧全程不存在被打断的窗口。ENTER_INTERRUPT 宏的头注释明说它"不改变 IF"（`KE/I386/KIMACRO.INC`）——它理直气壮地继承门的保护，自己什么都不用做。

**TPR 抬升在实际顺序里排第三**：建帧（ENTER_INTERRUPT）→ KiInterruptDispatch 调 HalBeginSystemInterrupt 抬 TPR 并存档 OldIrql → 调 ISR。它不能排第一，两条原因：① **没有手可用**——CPU 刚进来时全部寄存器装的都是被中断代码的值，必须先把它们存进帧里腾出寄存器，才谈得上拿寄存器去算、去写 TPR，存现场天然是第一动作；② **不需要它护卫开头**——序幕的安全由 IF=0 覆盖，TPR 管的是稳态下"哪些中断许进"的策略，不是头几条指令的保镖。APIC 还有第二重保险：递送中断时它已置下"处理中"位，处理器当时的有效优先级取 TPR 与处理中类二者的高者，同类及更低的中断在硬件层根本递不进来；且中断只在指令边界被响应，不存在半条指令被塞进来的情形。

**这个实现走得更远**：WRK i386 的分发路径里根本没有 sti——**建帧、分发、ISR 全程 IF=0**，ISR 不会被任何可屏蔽中断打断；高优先级的来者停在 APIC 的待处理位图里，等本次退出 iretd 恢复被中断代码的 EFLAGS（IF 回到 1）后，于下一个指令边界立即递送。**借此纠正补记十的一处不准确**：我说"更高优先级的 ISR 可以中途打断低级 ISR"，在这套实现里不成立。"逐级/层叠"的真实来源是：中断可以打断线程、APC、DPC 这些低 IRQL 的**软件上下文**，每打断一层存一层 OldIrql——层叠的是软件上下文，不是 ISR 套 ISR。

**建帧期间还能进来的只有不走可屏蔽通道的几位**：NMI（不可屏蔽，正因如此 i386 给它备了任务门加独立 TSS，整套换栈换上下文，不依赖这半截帧）；同步异常（如往内核栈守卫页压帧触发的缺页——那是内核栈扩容的设计内路径）；#MC 等。它们各有专门安排，不与普通中断共用这条序幕。

**对照组**：系统调用路径恰恰相反——帧建完、FS 换成 PCR 之后，入口代码会主动 sti 把中断打开，因为系统调用可能跑很久甚至阻塞，不能关着中断办长活；而设备中断路径全程关着办短活。同一种建帧动作，两种 IF 策略，差别来自活的性质。

## 追问补记十三：IF 和 TPR 是两道独立的闸——为什么退出宏还要 cli？抬 TPR 等于开中断吗？（2026-10-31）

**先把两道闸分清，后面两个问题自动解开：**

- **IF（EFLAGS 里的中断允许位）是总闸**：为 0 时，一切可屏蔽中断都递不进来，与优先级无关；为 1 时才谈得上递送。
- **TPR（本地 APIC 的任务优先级寄存器）是门槛**：它只在 IF=1 时有意义，规定"优先级类高于我这条横杆的中断才许递送"。**抬 TPR 是把横杆抬高、放行范围变小**，方向与"开"正好相反；它从头到尾不碰 IF。

所以"抬 TPR 相当于开中断吗"——**不等于，而且方向反了**。高级中断能进来，从来不是因为 TPR 抬升放行了它们，而是因为它们在横杆之上、本来就不归这根横杆管；横杆的作用是把它们以下的挡住。并且在 WRK i386 这条设备中断路径上，IF 全程为 0，抬 TPR 当场一个中断也放不进来。那为什么还要抬？三条理由：① IRQL 是操作系统自己的状态，TPR 是它的硬件编码——调度、锁规则、其他 CPU 的判断都读这个状态，必须与实际"忙的程度"保持一致；② EOI 一旦清掉 APIC 的"处理中"位，此后若出现 IF=1 的窗口（退出路径上就有），单靠 TPR 独自撑住"我还在 DIRQL 忙着"这道防线；③ 抬 IRQL 这个抽象动作在 PIC 型 HAL 里还要顺带改写 8259 的屏蔽字（HAL 内部实现，不在 WRK 树内），语义必须在两种控制器上一致。存档 OldIrql 也在这一步完成，供退出时精确还原。

**退出宏为什么还要 cli——在设备中断这条路径上，它确实是多余的一下，但多余得有道理：**

1. **宏是共享的，它不敢假设**。INTERRUPT_EXIT 与 EXIT_ALL 这一套退出机器不止服务硬件中断：异常走的是**陷阱门**，进门时**不**清 IF——一个在 IF=1 状态下发生的缺页，其退出路径到达这套宏时 IF 是开着的。EXIT_ALL 的注释把契约写死了："所有调用者必须保证到达这里时中断已关闭"。与其让每个调用方各自证明，不如宏在入口自己 cli 一下，把契约变成自带保证。一条指令的成本，买的是所有路径的统一不变量。
2. **它真正看守的危险窗口在 TPR 降下之后**。退出顺序是：cli → HalEndSystemInterrupt（发 EOI + **把 TPR 写回 OldIrql**）→ EoiHelper 检查 → EXIT_ALL 拆帧 → iretd。TPR 一写回低位，优先级门槛就重新打开了，此时唯一还拦着待处理中断的就剩 IF；而拆帧过程（重算 ESP、逐个 pop 段寄存器）中途的栈是不一致的半成品状态，这时若放一个中断进来在上面建帧，就是灾难。cli 保证从结单、降 TPR、查 APC 到拆完帧的整段拆除工作一气呵成；最后 iretd 在一条指令内**原子地**同时恢复原 EFLAGS（IF 回到中断前的值）和原 EIP/CS——中断重新被允许的瞬间，受中断的代码上下文已经完整复位，不留一丝缝。

一句话：**入口的关中断是门给的（针对这一条路径），退出宏的 cli 是退出机器给自己立的规矩（针对全部路径）——前者是事实，后者是契约。**

## 追问补记十四：全程复核版——用户态被键盘中断打断的完整时间线（含每一步的 IF 与 TPR 状态）（2026-10-31）

以下每一步均以本轮逐行复核的 WRK 源码或硬件架构事实为据；HAL 本体不在 WRK 树内，涉及 HAL 内部的步骤按其与内核的接口契约陈述并明确标注，不臆测其代码。

**阶段 0 · 平时**：用户代码运行，CPL 3，**IF=1**，IRQL=PASSIVE（TPR 在最低档）。本线程的内核栈空闲待命，TSS.ESP0 已由上次切换时的 SwapContext 指向它。

**阶段 1 · 硬件敲门（纯硬件）**：按键使 8042 控制器备好扫描码并发出 IRQ；本地 APIC 的待处理位（IRR）置位。CPU 在指令边界核对：IF=1 且该向量优先级类高于当前处理器优先级 → 接受，IRR 位清、"处理中"（ISR）位置位。随后硬件一气呵成：按 TSS.ESP0 换到本线程内核栈 → 压 SS、ESP、EFLAGS、CS、EIP（压入的 EFLAGS 是原样存档，IF 仍为 1）→ 因 IDT 里是**中断门**，把活的 EFLAGS 的 IF、TF 清零 → 按门中地址跳入内核分发模板，CPL=0。**自此 IF=0。**

**阶段 2 · 建帧（ENTER_INTERRUPT，`KE/I386/KIMACRO.INC`，IF=0 全程）**：压非易失寄存器、补齐帧体、存 EAX/ECX/EDX、存 FS/DS/ES/GS 并把 FS 换成 PCR 段、异常链换头；模板另给帧补一个占位错误码字段，使中断帧与异常帧格式统一。宏头注释明言它不改变 IF。

**阶段 3 · 分发抬级（KiChainedDispatch，`KE/I386/INTSUP.ASM`，IF=0）**：调 **HalBeginSystemInterrupt(DIRQL, 向量, &OldIrql)**——HAL 把 TPR 抬到 DIRQL 门槛、把旧 IRQL（PASSIVE）写回栈格存档；若它返回 0，则是伪中断，走**不发 EOI** 的专门出口散场（本例不走）。TPR 抬升不碰 IF：横杆立好，总闸仍关。

**阶段 4 · ISR 干活（IF=0，INTSUP.ASM 通篇无 sti，已逐行核）**：分发沿中断对象链调用 ISR；调用前若该对象的 SynchronizeIrql 更高，先抬到同步级并拿中断自旋锁，返回后降回（INTSUP.ASM 中 LowerIrql 处实证）。键盘 ISR：读 0x60 端口取走扫描码（给设备结账）、存入驱动缓冲区、排 DPC——DPC 入本 CPU 队列且本 CPU 账本的 DpcInterruptRequested 标志被置位（`KE/DPCOBJ.C` 实证）、请求经 HalRequestSoftwareInterrupt 向 HAL 登记（`KE/I386/CLOCKINT.ASM`、`CTXSWAP.ASM` 均以 IMPORT 引用它）——然后返回 TRUE。

**阶段 5 · 结单与还原（INTERRUPT_EXIT 宏，IF=0）**：cli（契约性，本路空转）→ **HalEndSystemInterrupt(OldIrql, 向量)**：HAL 写 APIC 的 EOI 寄存器（"处理中"位清除，控制器结单）并把 TPR 写回 PASSIVE 档。顺序钉死：**先 EOI、先降 TPR，人还没走**。其后跳入的 Kei386EoiHelper 入口契约明言"interrupts are disabled"（`KE/I386/TRAP.ASM`），IF 仍为 0。

**阶段 6 · DPC 投递与排空（IF 在此打开一次）**：IRQL 已低于 DISPATCH 且请求标志在位，挂起的调度软件中断被投递——**投递动作由 HAL 在其降级环节按请求标志完成（HAL 本体不在树内，此步按契约陈述；内核侧可见的实体是 KiDispatchInterrupt，WRK 内核自身没有任何调用点，它是供 HAL 调用的导出函数）**。KiDispatchInterrupt（`KE/I386/CTXSWAP.ASM:168`，自述"entered as the result of a software interrupt generated at DISPATCH_LEVEL"）：先 cli 站稳 → ESP 换到本 CPU 的 DPC 栈 → IRQL 抬回 DISPATCH_LEVEL → **sti，IF=1**（CTXSWAP.ASM:242 实证）→ 排空 DPC 队列。排空期间靠 TPR 在 DISPATCH 的横杆挡住同级及以下，更高级的设备中断可正常打断 DPC（以 OldIrql=DISPATCH 另走一遍全流程）。键盘 DPC 在此执行：翻译、字符入队、满足等待中的读请求——等键线程被摘下等待链、放上就绪队列，并因优先级更高被填进本 CPU 的 NextThread。

**阶段 7 · 换人（若 NextThread 已定，IF=0 下完成）**：KiDispatchInterrupt 排空后查账本，经 KiSwapContext → SwapContext 换栈：存旧线程内核 ESP、装新线程 ESP、按需换 CR3、改写 TSS.ESP0 与 TEB 描述符基址，ret 落进被唤醒线程冻结的调用链。被中断线程连同它没走完的退出路径（还剩 APC 检查、EXIT_ALL、iretd）冻在自己内核栈上、排回就绪队列队首——它的 iretd 是推迟，不是取消（补记十一）。

**阶段 8 · 各自回家（IF 在 iretd 那一拍才真正重开）**：被唤醒线程先在内核退完那次读调用，再走自己的 KiServiceExit（cli → 查它自己的用户 APC → EXIT_ALL → iretd），iretd 原子地恢复它自己的 EFLAGS（IF=1）与 EIP/CS，回到用户代码时字符已在手。被中断线程等将来被换回时，续走阶段 6–8 属于它的那份，再 iretd 回到被打断的那条指令。

**两个检查点的相对次序**：下降途中先办 DISPATCH 级的事（DPC)，再办 APC 级的事（EoiHelper 的 DISPATCH_USER_APC 检查）——下楼先过 DISPATCH 层。APC 检查本身有个会打开中断的细节（补记十三未展开）：若确有用户 APC 待投递，该宏会抬到 APC_LEVEL 后 **sti** 调 KiDeliverApc、事后 LowerIrql 再 cli 收回并复查（`KE/I386/TRAP.ASM:865` 宏定义实证）；本例无待投递用户 APC，不触发。

**IF 总账**：用户态 1 → 中断门清 0 → 建帧/分发/ISR/结单全程 0 → DPC 排空期间 1（TPR 横杆值班）→ 换栈 0 → iretd 原子恢复 1。
**TPR 总账**：PASSIVE → DIRQL（Begin）→ PASSIVE（End 还原）→ DISPATCH（排空期间）→ 随接管线程的上下文而定。

**对补记十的一处精确化**（非推翻，是把执行者钉准）：下降途中 DPC 被"接走"的投递者是 HAL（在其降级环节按请求标志投递），被投递到的实体是 KiDispatchInterrupt；此前补记只写了"被 KiDispatchInterrupt 接走"，语义无误、主语未明，此处补正。

## 追问补记十六：阶段 5 把 TPR 写回 PASSIVE，是固定的吗？（2026-10-31）

**不是固定的。写回的值是进入时存档的 OldIrql——HalBeginSystemInterrupt 存什么，HalEndSystemInterrupt 一分不少地还什么。** 补记十四里写 PASSIVE，只因为那个场景里被打断的是用户代码，而用户态代码永远运行在 PASSIVE_LEVEL，这是场景的属性、不是机制的常量。INTERRUPT_EXIT 宏的栈上参数写得明明白白：栈顶就是 "previous irql"，退出时原样奉还。

换个被打断的对象，写回值随之而变，后果也不同：

| 被键盘中断打断的上下文 | 存档的 OldIrql | 阶段 5 写回 | 对阶段 6 的影响 |
|---|---|---|---|
| 用户代码 / 普通内核线程代码 | PASSIVE | PASSIVE | 低于 DISPATCH，DPC 软件中断正常投递（补记十四走的就是这条） |
| 正在投递 APC 的代码 | APC_LEVEL | APC_LEVEL | 同上，水位够低，DPC 照常投递 |
| 正在运行的 DPC | DISPATCH_LEVEL | DISPATCH_LEVEL | **不投递**——水位从未降到 DISPATCH 以下；新排的 DPC 躺在队列里，由正在跑的那个排空循环（KiRetireDpcList 循环到队列空为止）顺手带走 |
| 持有自旋锁、已自行抬 IRQL 到某 DIRQL 的线程代码（IF 开着时被打断） | 那个 DIRQL | 那个 DIRQL | 不投递，等该代码自己降下来再说 |

为什么机制必须"存什么还什么"、不许图省事一律降到 PASSIVE：IRQL 是被中断上下文的**财产和防线**——它当时敢持有那把锁、敢假设"低于我的中断进不来"，全靠这个水位撑着。退出路径若自作主张降过头，等于在人家活没干完时先把防线拆了（与补记十"中断退出不越级办事"同理）。HalBegin/HalEnd 这一对函数的全部意义就是这份对称性：一个负责存档，一个负责原样奉还，中间 ISR 干了什么、排了什么 DPC，都不改变奉还的数值。
