> 整理自 2026-10-31 对话问答。PatchGuard 是嵌在 ntoskrnl 里的一套"巡查 + 自毁"机制：定期核对关键内核代码与数据结构，发现篡改即主动蓝屏。本文讲它的设计哲学、组织结构、保护清单、检查的生命周期与自我保护，并交代它与驱动签名、HVCI 的分工。配套的《PatchGuard 攻防史》按时间线整理了历代绕过与微软的逐版本反制。

---

> 诚实边界先行：微软从未公开发布 PatchGuard 的实现文档。以下内部细节来自公开逆向研究（2005 年 Skywing 在 Uninformed 期刊的首度分析、Satoshi Tanda 等人的跨版本持续追踪）在各 Windows 版本上的成果；具体结构（上下文字段、触发器组合）随版本显著变化。本文讲的是**跨版本稳定的架构与机制**，不声称对当前最新版本字段级准确。蓝屏参数表则直接引自微软官方 bugcheck 文档与多份转储分析的一致口径。

## 术语速览

- **PatchGuard**：微软的正式名称是 **Kernel Patch Protection（KPP，内核补丁保护）**。它不是一个驱动、不是一个服务，而是嵌在 ntoskrnl 内核本体里的一套"巡查+自毁"机制：定期核对一批关键内核代码与数据结构是否被改动，发现篡改就主动蓝屏。
- **挂钩（hooking）**：把某张分发表里的函数指针改指到自己的代码，或在目标函数开头插入跳转，让执行流先经过自己。32 位时代的杀毒软件与 rootkit 共同的主力手法。
- **SSDT（System Service Descriptor Table，系统服务描述符表）**：系统调用的分发总表（WRK 第 7、8 批讲过，其影子表还含 win32k 的一半）。
- **DKOM（Direct Kernel Object Manipulation，直接内核对象操纵）**：不改代码、只改内核数据对象本身的攻击，如把进程从活动进程链表上摘链以隐藏进程。
- **校验和（checksum）**：对一段数据按固定算法算出的指纹值；内容改一个字节，指纹就变。PatchGuard 用它判断"这段东西还是不是原样"。
- **上下文（PatchGuard context）**：研究者对那块集中存放 PatchGuard 全部状态（保护清单、期望校验值、触发器安排）的内核数据结构的称呼；它被加密存放。
- **触发载体（trigger）**：负责"到点叫醒检查例程"的宿主机制——定时器 DPC、系统工作线程、APC 等本不相干的内核设施被 PatchGuard 借来当闹钟。
- **BugCheck（蓝屏停机）**：内核自认无法安全继续运行时主动触发的停机，带一个停机码说明死因；PatchGuard 用的停机码是 **0x109 CRITICAL_STRUCTURE_CORRUPTION**。

## 一、它为什么存在：威胁模型与历史

**要防的事**：在 32 位时代，改内核是家常便饭——rootkit 改 SSDT 劫持系统调用、改 IDT 劫持中断、在内核函数开头打内联补丁；杀毒软件用**同样的手法**搞行为监控。后果有二：恶意软件借此隐形；大量"合法挂钩"写得参差不齐，成为 Windows 蓝屏与不稳定的主要来源之一。微软的判断是：内核的完整性一旦允许任意第三方改写，安全和稳定两个目标同时失守。

**为什么只有 64 位**：PatchGuard 随 Windows x64（2005 年，XP x64 / Server 2003 SP1 世代）诞生，**只部署在 64 位（x86-64 与后来的 ARM64），32 位永远没有**。不是技术做不到，而是生态账算不过来：x86 上存量安全软件全靠挂钩吃饭，强行部署等于砸掉整个生态；x64 是新平台、没有历史包袱，微软借换代立规矩——**新平台的第一天就把"不许改内核"写进地基**。与之配套的是 64 位强制驱动签名（管"谁能进内核"，见《Windows 驱动签名与验签》）——签名管准入，PatchGuard 管进来之后的行为。

**定位要说准**：微软自己明确说过 PatchGuard **不是安全边界**。已经进了内核的代码与管理员本来就在信任圈内；它的作用是**绊线与制动**——让"偷偷改内核"这件事从免费变成高成本、高风险，同时把不守规矩的改动以蓝屏的形式暴露出来。它的对手与其说是顶级攻击者，不如说是"整个生态的随意性"。

**为什么反应是蓝屏这么极端**：检查发现篡改时，内核完整性已经不可信——此时任何"修复"动作都运行在被污染的环境里，都可能正中攻击者下怀。唯一可信的反应是立即停机。**Fail-closed（失效即关闭）**，不留商量。

## 二、总设计哲学（三条，理解了它们细节自然长出来）

1. **检测而非预防**。它不拦着你改（拦不住，也不打算拦），它定期回来对账，改过就翻脸。所以它的一切设计都在围绕"对账如何不被预料、不被绕过、不被先下手拆掉"。
2. **没有固定据点**。没有名为 PatchGuard 的驱动、线程或定时器。它的状态藏在一块加密的上下文里，它的闹钟寄生在多个不相干的内核机制上，它的检查时机是随机化的。设计目标：让"找出并拆掉它"比"老实不改内核"更难。
3. **检查者与被检查者互相校验**。保护清单里包含 PatchGuard 自己的上下文与关键数据——想先拆哨兵，拆的动作本身就在哨兵的看护范围内。

## 三、组织结构

**初始化**：系统启动早期，内核初始化流程中有一段 PatchGuard 的布防动作（研究者从符号与逆向中确认其存在，微软不公开）：在内核非分页池中分配上下文，逐项登记保护对象，为每个对象算好**期望校验和**，把校验值与关键指针**加密（XOR 滚动密钥一类的方式，具体算法随版本变）**后存入上下文，再把第一批触发器散布出去。

**触发载体（公开研究确认用过的）**：

- **内核定时器（KTIMER）到期后的 DPC**——挂在系统定时器机制上，到期时以 DPC 形式跑检查；
- **系统工作线程的延迟工作项**——排进 System 进程的工作队列，由现成的工作线程捎带执行；
- **APC**——排进某个线程的 APC 队列，搭那趟线程的便车。

三类载体**并用且轮换**，间隔**随机化**（公开观察为数分钟量级、每次不同）。这是第 2 条哲学的落地：摘掉一个定时器没用，其他闹钟还在；想守株待兔摸清检查规律，随机间隔让你守不到。

**检查例程**：就是 ntoskrnl 里的一组内部例程，不导出符号、无公开入口，每版本位置与形态都变。检查逻辑的大致形态见下一节的生命周期。

## 四、保护清单：从蓝屏参数反推官方看护范围

微软不公布清单，但有个硬证据：**0x109 的第 4 个参数（Arg4）就是"被篡改区域的类型"代码表**（Arg1、Arg2 是校验值，Arg3 是与类型相关的附加信息，常为出事结构的地址）。这张表等于官方自曝了看护范围（以下为文档与多份转储一致的条目，编号即 Arg4 值）：

- **代码类**：0x01 函数或 .pdata 被改（内联挂钩的靶心）；0x0A 系统服务函数被改；0x0D / 0x0E 导入表被改；0x102 win32k.sys 被改；另有会话空间的一组同类项（0x0B / 0x0C）。
- **分发与门面结构**：0x02 某处理器的 **IDT**；0x03 某处理器的 **GDT**；0x09 IVT；0x07 **关键 MSR 被改**（这一条看护的正是 LSTAR 等系统调用入口——把 syscall 入口改指到别处当场翻脸）。
- **数据结构类**：0x04 / 0x05 / 0x1A 三种**进程链表损坏**（DKOM 摘链隐藏进程的检测就在这里）；0x08 对象类型被改；0x0F **Ps Win32 callout 被改**（正是 WRK 第 8 批那张 16 指针的 Win32 回调表）；0x1D 执行回调对象被改；0x06 / 0x10 调试例程与调试切换例程被改；0x11 IRP 分配器被改；0x00 通用数据区兜底。

从这张表能读出两个结论：其一，看护范围**远不止 SSDT 与代码段**——进程链表、回调表这些纯数据结构都在内，说明微软很清楚 DKOM 这条路；其二，清单**随版本在长**（编号排到 0x102 说明后来还把 win32k 整体纳入），它是个活名单，不是一次性工程。

## 五、一次检查的生命周期（机制主干）

1. **闹钟响**：某个载体（定时器 DPC / 工作项 / APC）被调度执行，控制流进入检查例程。注意此时执行流是"借"来的——和 DPC 借被中断线程的流同理，没有专职的 PatchGuard 线程存在。
2. **解开上下文**：例程先定位上下文，把里面的关键字段解密开。上下文的位置与密钥安排刻意不固定。
3. **先查自己**：先校验上下文与检查机制自身的关键数据是否完好——这一笔不过，后面都不用查了，直接按篡改论处。
4. **逐项对账**：对清单里每个对象重新计算校验和（代码段、表、结构各有其覆盖范围），与存档的期望值逐一比对。
5. **两种结局**：
   - **全部相符**：重新布防——给各载体换上新的随机间隔、必要时轮换载体，悄然散场，不留日志、不留痕迹（正常情况下系统永远不会告诉你它刚查过一轮）。
   - **任一不符**：`KeBugCheckEx(0x109, …)`，Arg4 填上对应的类型代码，当场蓝屏。没有警告、没有隔离、没有"尝试恢复"——fail-closed（失效即关闭）的字面执行。

## 六、它怎么保护自己

- **藏**：上下文加密存放、关键指针编码、检查例程无导出符号、整体形态随版本大改；微软零文档——不透明本身就是一层设计（与代码签名的"明规则"互补：一个靠公开规则准入，一个靠不可测性看护）。
- **散**：状态只有一份，但触发点有多个、分布在不相干的子系统里，拆一处不等于拆全部。
- **互相看**：自己的上下文与数据在自己的清单里（第五节第 3 步），先拆哨兵的动作会被哨兵的同伴发现——只要还有一个载体活着。
- **注意它的先天弱点**（这是理解下一节的钥匙）：检查代码跑在它所要保护的同一个内核里，与被检查者同级。同级别对抗中，防守方靠的是不透明与随机性争取成本优势，而不是靠权限隔离——这决定了它注定是一场猫鼠游戏，也解释了微软后来为什么要把防线下沉到 hypervisor（第七节）。

## 七、与相邻机制的分工

| 机制 | 管什么阶段 | 手段 | 性质 |
|---|---|---|---|
| 驱动签名 / CI（代码完整性） | **加载时**：谁能进内核 | 证书链与目录文件验签 | 明规则、准入制 |
| **PatchGuard** | **运行时**：进来之后不许改什么 | 随机巡查关键代码与结构、发现篡改即蓝屏 | 暗巡查、检测制 |
| HVCI / VBS（Win10 起） | **运行时**：想改也改不动 | hypervisor 把内核代码页设为不可写不可改，页表权限在虚拟化层强制 | 硬隔离、预防制 |

HVCI 可以看作 PatchGuard 思想的接班与硬化：同样是守护内核代码完整性，一个靠"巡查后同归于尽"，一个靠"把代码页焊死在保险柜里"。在开了 VBS 的系统上，PatchGuard 的相对重要性下降，但它并未消失——数据结构那部分看护（进程链表、回调表）仍由它承担。

## 八、局限性与公开已知的对抗类别（概念层）

- **时间窗**：检测是周期性的，篡改发生与下次检查之间存在窗口。"改完即恢复"（hit-and-run：在检查间隙改、用完立刻改回去）是对这一类周期检测的通用反制思路。
- **定位与摘除**：历代研究者（2005 年 Skywing 首度公开分析并给出绕过、其后 Uninformed 系列论文、2010 年代 Satoshi Tanda 对各 Windows 版本的持续追踪）的主战场，就是定位上下文、识别并摘除触发载体。微软则以每版本大改实现、调整触发组合来重置这场竞赛——这是它"每版本都不一样"的根本原因。
- **清单之外的数据面**：清单再长也是有限名单，名单之外的内核数据不在看护之列；纯数据攻击若能避开清单条目，PatchGuard 无感。
- **信任根**：如同第六节所说，它在被保护者内部运行；更低层（hypervisor、固件）的攻击者不在其视野内。
- **误伤与摩擦**：内核调试器在运行时下普通断点（改写代码字节写入 int 3）会触发 0x109——官方蓝屏文档列的三大成因之一就是它（另两因是驱动篡改与硬件内存损坏）；2006 年前后，安全厂商曾与微软就 PatchGuard 公开争论，因为它把 AV 们赖以工作的挂钩技术一并封死，微软的回应是推动厂商改用官方回调与过滤框架——今天的 minifilter、WFP、各类注册回调，生态位正是那场争论的产物。

## 九、对驱动安全审计的落点

PatchGuard 的存在改变了攻击面的地形（与《Windows 驱动签名与验签》的结论闭环）：在默认 x64 配置下，"加载驱动后改内核结构"这条经典路线成本被抬得极高，于是真实世界的重心转移到三处——**找一个合法签名但暴露了读写原语的驱动（BYOVD）借刀杀人**（微软为此单独维护漏洞驱动拉黑名单，而不是指望 PatchGuard 兜底）；**打清单外的数据面**；**在检查窗口内动手脚**。审计一个驱动时最要命的问题始终不变：它的 IOCTL 有没有把任意内核读写能力交到低权限调用者手里——只要这扇门开着，PatchGuard 的校验值与触发器本身也在射程之内，再好的巡查也防不住有人先拆了巡查。
