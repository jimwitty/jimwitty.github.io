## Abstract / 摘要

2006 年底，暴雪部署了版本检查（version check）与客户端软件认证系统的首个重大更新，该系统用于验证使用二进制游戏客户端协议连接到 Battle.net 的客户端的真实性。这套系统自初代《暗黑破坏神》（Diablo）发布后不久、Battle.net 公开上线以来就一直在使用。新的认证模块——Lockdown 模块（暴雪新版版本检查/客户端认证模块，负责在登录时验证客户端是否为正版暴雪游戏软件）——引入了多种机制，旨在抬高在登录 Battle.net 时伪造游戏客户端的门槛。此外，新认证模块还引入了对内存中客户端二进制文件的运行时完整性检查（run-time integrity checks：在程序运行期间对内存中的代码映像做校验比对，以发现被改动的代码）。这旨在简单地检测许多客户端修改（常被称为 "hacks"，即作弊/篡改手法），这类修改通过在内存中给游戏代码打补丁来改变游戏行为。Lockdown 认证模块还引入了一些反调试（anti-debugging：使调试器难以附加、跟踪和分析目标模块的技术）手段，旨在增加逆向工程该模块的难度。此外，还引入了若干检查，旨在使攻击者难以简单地从一个未经授权的、非暴雪游戏进程的上下文中加载并运行暴雪的 Lockdown 模块。毕竟，如果攻击者可以简单地在自己的进程中加载并运行 Lockdown 模块，那么伪造游戏客户端登录过程、或让改过的游戏客户端成功登录 Battle.net，就变得极其容易。然而，与任何保护机制一样，新的 Lockdown 模块并非没有缺陷，本文将详细讨论其中的一些缺陷。

## 1) Introduction / 1）引言

Lockdown 模块是若干方案的一部分，这些方案试图使非"正版"暴雪游戏客户端难以连接到 Battle.net。在本文中，作者把经过修改/被 "hack" 的暴雪游戏客户端，以及第三方客户端软件——称为 "emubots"（模拟客户端程序）——都视为非正版暴雪游戏的 Battle.net 客户端的例子。Battle.net 协议还包含若干其他方案（例如一种专有机制，用于向 Battle.net 出示有效的 CD-Key 供其检查；以及用于账户登录的 SRP 密码交换协议的一种非标准衍生版本），这些方案由于晦涩且无文档记载，使得外人要成功地把非正版客户端登录到 Battle.net 并非易事。

在 Lockdown 模块推出之前，另一套系统占据着它的位置，承担验证客户端软件版本的角色。先前的系统对重放攻击有抵抗力（需要注意：服务器维护的挑战/响应值池相对较小，因此在观察大量成功登录尝试之后，使用重放攻击仍是可能的），其原理是使用一条由服务器动态下发的校验和公式（实际上就是一个挑战）。这条公式随后由 Lockdown 模块的前任——即 "ver" 模块（亦称 "ix86ver" 模块）——来解释，并用于对若干关键游戏客户端二进制文件生成单向哈希。所得到的结果响应随后被发回游戏服务器进行验证，响应无效将导致客户端被拒绝接入 Battle.net。

虽然 "ver" 模块对某些类型的非正版客户端（例如那些在磁盘上修改暴雪游戏二进制文件的客户端）具有一定的内在抵抗力，但它对在内存中修改暴雪游戏客户端的做法几乎无能为力。此外，几乎没有什么能阻止攻击者创建自己的客户端软件（一个 "emubot"），实现 "ver" 模块的校验和方案——既可以直接调用 "ver"，也可以使用第三方逆向工程实现的 "ver" 模块算法。需要注意的是，对于第三方软件直接调用 "ver" 模块，存在一道基本的防护："ver" 系列模块被设计为始终对调用方进程的映像（由 Win32 API `GetModuleFileNameA` 返回）执行版本检查哈希的一部分。这对第三方程序构成了一个小小的麻烦。然而，要绕过这道防护，只需挂钩（hook）`GetModuleFileNameA` 并伪造返回给 "ver" 模块的结果即可。

鉴于现有 "ver" 模块的能力，Lockdown 模块在确保只有正版暴雪客户端软件才能作为游戏客户端登录 Battle.net 这一方向上迈出了一大步。就暴雪而言，Lockdown 模块在许多方面都是首创：它所发布的代码会主动尝试挫败通过调试器进行的分析（并主动尝试以非平凡的机制抵抗在外来进程中被调用）。

然而，尽管 Lockdown 模块投入了大量工作，它已证明或许没有原先期望的那样有效（作者无法陈述 Lockdown 模块确切的期望目标，但可以假定，"被攻破前的存活时间" 超过数天是 Lockdown 模块的一个目标）。本文讨论嵌入 Lockdown 模块及相关认证系统的各种主要保护系统、针对它们的潜在攻击，以及暴雪可以在未来发布的新版版本检查/认证模块中采取的技术反制措施。

Lockdown 模块的开发者所面临的部分问题，与该模块运行环境的约束有关。作者推导出该模块目前面临的以下约束：

1. 认证系统的服务器部分很可能是静态的，不会实时生成挑战/响应值。相反，可能的值的池似乎是预先生成并配置在服务器上的。
2. 该模块需要在所有暴雪游戏支持的所有操作系统上工作，范围涵盖从 Windows 9x 到 Windows Vista x64。注意，对于不同的架构（例如 Mac OS），有使用不同于 Windows 架构的系统的相应规定。
3. 该模块需要在所有暴雪 Battle.net 游戏的所有版本上工作，包括以前的版本。这是因为该模块在 Battle.net 的软件版本控制系统中起着不可或缺的作用，因此在旧客户端能够升级之前，就会被用在旧客户端上。
4. 合法用户不应看到高比例的误报，并且不希望误报导致对合法用户采取自动化的永久性处置（例如封停账户）。

顺带一提，作者认为，版本检查与认证系统并非意在作为 Battle.net 的复制保护系统，因为它并不阻止正版暴雪游戏软件的额外副本在 Battle.net 上被使用。（译注：原文此处 "discourge" 为 discourage 之笔误，照译。）本质上，版本检查与认证系统是一个旨在确保只有正版暴雪游戏软件的副本才能登录 Battle.net 的系统。Battle.net 上的复制保护措施通过 CD-Key 功能提供，服务器要求用户拥有一个有效（且唯一）的 CD-Key（针对适用的产品）。

## 2) Protection Schemes of the Lockdown Module / 2）Lockdown 模块的保护方案

与旧的 "ver" 模块形成鲜明对比的是，Lockdown 模块包含若干主动防御机制，旨在显著增强该模块抵抗攻击的能力（包括分析攻击，以及被诱骗向不受信任的进程提供对挑战的"良好"响应）。

Lockdown 模块中的保护方案可以分为几类：

1. 挫败对 Lockdown 模块本身及其实现的秘密算法之分析的机制（反调试/反逆向工程）。
2. 挫败在敌对进程中成功使用 Lockdown 为 Battle.net 的挑战生成"良好"响应的机制（反 emubot，并且推及反 hack，其中 "反 hack" 指对抗对原本正版的暴雪游戏客户端所做的修改）。
3. 挫败对正试图登录 Battle.net 的原本正版的暴雪游戏客户端进行修改的机制（反 hack）。

此外，Lockdown 模块还负责实现 "ver" 模块原始功能的合理摹本；也就是说，提供一种权威地验证正版暴雪游戏客户端版本的方法，用于软件版本控制（例如向连接到 Battle.net 的正版暴雪游戏客户端的旧版本部署正确的软件更新/补丁）。

沿着这一思路，Lockdown 模块及相关认证系统中存在以下保护方案：

### 2.1) Clearing the Processor Debug Registers / 2.1）清除处理器调试寄存器

x86 家族处理器包含一组专为协助程序调试而设计的特殊寄存器（调试寄存器，debug registers：x86 处理器中用于设置硬件断点的寄存器组 DR0–DR7）。这些寄存器允许用户使处理器在某个特定内存位置被访问时停下来——无论是作为指令取指、数据读取还是数据写入。这一调试设施允许用户（调试器）设置最多四个不同的虚拟地址，在以特定方式被引用时陷住执行。利用这些调试寄存器在特定位置设置陷阱，有时被称为设置"硬件断点"（hardware breakpoint），因为利用的是处理器专用的调试支持（硬件内建）。（译注：原文 "hardware breakpoint" 一语前缺失起始引号，照译。）

由于这些调试寄存器对任何试图分析或逆向工程 Lockdown 模块的人显然很有用，该模块主动尝试禁用这一调试辅助手段：在执行 Lockdown 模块版本检查调用 `CheckRevision` 的线程的上下文中，显式地将关键调试寄存器的内容清零。在调用 Lockdown 模块的 `CheckRevision` 例程之后，所有必需的调试寄存器都会立即被清除。

这一保护机制构成一种反调试方案。

### 2.2) Memory Checksum Performed on the Lockdown Module / 2.2）对 Lockdown 模块执行的内存校验和

与前任的行为相反，Lockdown 模块对若干关键游戏可执行文件在内存中（而非磁盘上）实施校验和。除了对某些游戏可执行文件做校验和之外，Lockdown 模块还把自身包括在要做校验和的模块列表中。这带来了几个直接的好处：

1. 试图在 Lockdown 模块内部的例程上设置常规软件断点，会扭曲操作的结果，从而挫败逆向工程的尝试。这是因为，所谓的软件断点是通过把目标位置的指令打补丁为一条特殊指令（通常是 `int 3`）来实现的，该指令使处理器中断进入调试器。对内存中模块可执行代码的更改会导致校验和被扭曲，因为被纳入校验和的是 `int 3` 操作码而非原始操作码。
2. 试图绕过 Lockdown 模块中其他保护机制的做法变得更加困难，因为一个不受信任的进程若试图通过把某些其他保护机制打补丁去除、来使 Lockdown 模块产生正确的结果，那么仅仅是在内存中更改 Lockdown 代码这一行为本身，就会无意中改变校验和操作的最终结果。内存校验和保护这方面的成功，与 Lockdown 模块也尝试禁用硬件断点这一事实相关。这两个保护机制因此以一种强有力的方式相互补充，使得天真地破坏其中一个保护方案的尝试通常会被另一个方案检测到。实际上，其结果是一种初步的软件保护"纵深防御"（defense in depth）方法，这是大多数相对成功的保护方案的标志。
3. 把版本检查模块本身包括进校验和输出的结果中，这在版本检查与客户端认证系统中是全新的，因此对试图在自己的代码中重新实现 Lockdown 算法的人构成了额外一道意想不到的"减速带"。

这一保护机制同时具有反调试、反 hack 和反 emubot 系统的特点。

### 2.3) Hardcoding of Module Base Addresses / 2.3）模块基地址的硬编码

如前所述，Lockdown 模块现在对游戏可执行文件在内存中（而非磁盘上）实施校验和。利用这一变化，Lockdown 模块可以把主进程可执行文件的基地址硬编码为默认地址 0x00400000。这样做是安全的，因为没有任何暴雪游戏可执行文件包含基址重定位信息，因此其基地址永远不会从这个地址改变。

借助硬编码这个地址，不受信任的进程要成功调用 Lockdown 模块变得更加困难。除非程序员特别机敏，否则他或她可能不会注意到，Lockdown 模块实际上并没有对所期望的暴雪游戏的主可执行文件进行校验和，而是对不受信任进程的主可执行文件进行校验和（Microsoft 链接器程序生成的可执行文件的默认地址，与暴雪游戏客户端主可执行文件所用的 0x00400000 是同一个值）。

虽然可以在链接时更改程序的基地址——第三方进程可以这样做，试图使所期望的暴雪主可执行文件有可能被映射到 0x00400000 地址——但在 Windows NT 下要做到这一点很困难。这是因为 0x00400000 地址在地址空间中位置很低，而内核内存管理器的默认行为是从地址空间底部开始为内存分配寻找新地址。这意味着在几乎所有情况下，一个全新的 Win32 进程已经会有一个与 Lockdown 模块为暴雪游戏主可执行文件所需的地址范围相重叠的分配（以作者的经验，通常是与 CSRSS 通信所用的共享节之一），而该游戏正是要为其计算挑战响应的。虽然可以改变 Windows NT 内存管理器的这一行为，使分配从地址空间顶部开始并向下搜索，但这不是默认配置，也是一个相对不为人知的内核选项。所有用户都需要重新配置以改变默认的分配搜索偏好，才能使不受信任的进程通常成功映射所期望的暴雪游戏可执行文件，这一事实使得这种方法对潜在的攻击者来说相对痛苦。

Lockdown 模块还确保 Win32 API `GetModuleHandleA(0)` 的返回值对应于 0x00400000，表明就加载器而言，主进程映像的基址位于 0x00400000。对游戏主可执行模块的基地址的这一限制有一个不幸的副作用：它将无法利用 Windows Vista 的 ASLR（地址空间布局随机化）攻击面削减能力，从而对暴雪游戏抵抗某些类别的、可能影响用户安全性的利用的能力产生负面影响。

这一保护机制主要被视为一种反 emubot 方案，因为它旨在防止不受信任的进程成功调用 Lockdown 模块。（译注：原文此处及 2.4 节末的 "succcessfully" 为 successfully 之笔误，照译。）

### 2.4) Video Memory Checksum / 2.4）显存校验和

Lockdown 模块引入的版本检查算法的另一个先前不存在的组成部分，是对调用 Lockdown 模块的进程的显存（video memory）做校验和。在暴雪游戏调用该模块的时点，被校验和的那部分显存应当对应于暴雪游戏登录界面上 "Battle.net" 横幅的一部分。Lockdown 模块目前仅针对所谓的 "legacy"（传统）游戏客户端实现，即使用 Battle.snp 和 Storm 多人游戏网络提供程序（Storm Network Provider）系统的客户端。这包括从《暗黑破坏神 I》到《星际争霸》和《魔兽争霸 II: BNE》的所有支持 Battle.net 的暴雪游戏。未来的游戏，例如《暗黑破坏神 II》，不受 Lockdown 模块支持。

这对潜在攻击者构成了又一道非平凡的挑战。虽然要做校验和的显存内容是静态的，但 Lockdown 模块获取显存指针的方式，是通过对若干 Storm 内部例程（`SDrawSelectGdiSurface`、`SDrawLockSurface` 和 `SDrawUnlockSurface`）的混淆调用，这些例程依赖暴雪游戏在启动期间初始化的相当数量的内部状态。这使得在一个不受信任的进程中——如果它没有费尽周折去初始化 Storm 图形子系统、并把适当的数据绘制到 Storm 视频表面上——使用这些 Storm 内部例程不太可能简单地"开箱即用"。

这一保护机制主要被视为一种反 emubot 方案，因为它旨在防止不受信任的进程成功调用 Lockdown 模块。

### 2.5) Multiple Flavors of the Lockdown Module / 2.5）Lockdown 模块的多种风味

最初的 "ver" 模块方案开创了一个系统：版本检查模块有多个可下载的"风味"（flavors，即同一模块的多个变体版本）供客户端使用。Battle.net 服务器向客户端发送一个元组（版本检查模块文件名、校验和公式及初始化参数、版本检查模块时间戳），用于对最新版本的版本检查模块进行版本管理（并在必要时下载）。这一机制提供了一种可能性：Battle.net 服务器可以支持版本检查模块的多个"风味"，分发给客户端，以增加任何寻求重新实现版本检查与认证系统的人所需的工作量。

最初的 "ver" 模块及相关认证方案实际上确实使用了这种多 "ver" 模块的方案，而 Lockdown 方案在这一趋势上进一步扩展。在最初的系统中，有 8 个可能的模块可供选择；相比之下，Lockdown 系统将其扩展到一组 20 个可能性。然而，两个系统中的版本检查模块仍然彼此非常相似。在两个系统中，每个模块都有自己唯一的密钥（"ver" 系统中是一个 32 位值，Lockdown 系统中是一个 64 位值），用于影响版本检查校验和的结果（需要注意的是，在 Lockdown 系统中，实际的 Lockdown 模块本身本质上是第二个"密钥"，因为对该模块增加的校验和代表对最终校验和结果的额外调整，并随每个 Lockdown 模块而变化）。这唯一的差异被每个模块风味的其他细微、表面性的改动所掩盖；例如，模块基地址的获取方式存在细微差异，还有其他表面性差异，例如代码在函数之间移动、或函数在最终二进制文件中被重新排列，以挫败对两个 Lockdown 模块做简单的 "diff"（差异比较）便能揭示所述两个模块之间功能差异的企图。

这一保护机制或许最适合归类为反分析方案，因为它试图为任何试图逆向工程整个认证系统的人制造更多工作。

### 2.6) Authenticity Check Performed on Lockdown Module Caller / 2.6）对 Lockdown 模块调用方执行的真实性检查

Lockdown 模块引入的另一项新的保护方案，是对该模块的导出函数 `CheckRevision` 例程的调用方真实性的初步检查。具体来说，该模块试图确定对 `CheckRevision` 例程的调用的返回地址是否指向 Battle.snp 模块内的某个代码位置。如果对 `CheckRevision` 调用的返回指针不在期望范围之内，那么校验和计算中会被故意引入一个错误，最终导致 Lockdown 模块返回的结果失效。

## 3) Attacks (and Counter-Attacks) on the Lockdown System / 3）对 Lockdown 系统的攻击（及反制）

尽管 Lockdown 模块引入了若干新的防御机制，试图挫败潜在的攻击者，但这些系统远非万无一失。一个想要在非正版客户端的上下文中通过版本与认证检查、以登录 Battle.net 的潜在攻击者，有许多方法可以攻击（或颠覆）这些防御系统。此外，也有各种不同的方法，可以在版本检查与认证系统的未来更新中挫败这些提出的攻击。

### 3.1) Interception of SetThreadContext / 3.1）拦截 SetThreadContext

如前所述，Lockdown 模块试图禁用处理器的整套调试寄存器，以使在逆向工程或分析 Lockdown 模块的过程中难以利用所谓的硬件断点。然而，目前这一方案相对容易被破坏。

有几种可能的攻击可以使用：

1. 挂钩 `SetThreadContext` API 并阻止禁用调试寄存器的尝试（编程式）。
2. 对 Lockdown 模块中 `SetThreadContext` 的导入地址表（IAT，Import Address Table）条目打补丁，使其指向一个什么都不做的自定义例程（编程式）。
3. 对 Lockdown 模块的指令代码打补丁，使其从一开始就不调用 `SetThreadContext`（编程式）。然而，由于内存校验和保护方案，这种方法被认为通常站不住脚。
4. 在 `kernel32!SetThreadContext` 上设置条件断点，在调用后重新应用硬件断点状态，或者干脆改变执行流使其立即返回（调试器式）。

根据攻击者是想通过硬件断点以编程方式改变 Lockdown 模块的行为，还是只是想在调试器中不受干扰地观察该模块的行为，有几种可用的选择。

建议的反制措施包括如下技术：

1. 验证调试寄存器是否真的被清除了。然而，这也可以被简单地打补丁去除。更微妙的做法是把若干调试寄存器的值包括进校验和计算中，但这对攻击者来说也会相当明显，因为调试寄存器不能从用户模式直接访问，需要调用 Get/SetThreadContext，或底层的 NtGet/SetContextThread 系统调用。
2. 在 Lockdown 模块内的不同位置加入禁用调试寄存器使用的额外调用。为了最有效，这些调用需要内联并使用不同的手段来设置调试寄存器状态。例如，一处可以使用直接导入，另一处可以使用 `GetProcAddress` 动态导入，第三处可以手动遍历 kernel32 的导出地址表（EAT，Export Address Table）以找到 `SetThreadContext` 的地址，第四处可以调用 ntdll 中的 `NtSetContextThread`，第五处可以反汇编组成 `NtSetContextThread` 的操作码，确定系统调用序号，并直接进行系统调用（例如通过 `int 2e`）。这里的目标是增加额外的工作，并从寻求禁用反调试功能的攻击者的角度消除"单点故障"。注意，直接系统调用的方法需要额外的工作才能在 Wow64 下运行（例如运行原生 Windows x64 的 x64 计算机）。
3. 验证对应于 kernel32 的所有 IAT 条目是否真的都指向内存中的同一个模块。然而这样做有风险，因为在某些情况下（例如当 Microsoft 应用程序兼容性层模块在使用时），这些 API 可能被合法地绕道（detour）。

### 3.2) Use of Hardware Breakpoints / 3.2）硬件断点的使用

假设攻击者能够破坏反调试保护方案，那么他或她就可以自由地巧妙利用硬件断点来禁用其他保护系统（例如模块基地址的硬编码、CheckRevision 调用方真实性检查等等），方法是在选定的代码位置设置执行取指断点。然后，攻击者可以在断点命中时简单地更改执行上下文，以绕过其他保护机制。例如，攻击者可以在 Lockdown 模块内部、为主进程映像硬编码的基地址上设置一个读取断点，并相应地更改该基地址。攻击者还必须对 `GetModuleHandleA` 打补丁才能完成这个示例攻击。

针对基于硬件断点的攻击，建议的反制措施包括：

1. 验证向量化异常处理程序（vectored exception handler）链，它可能被用来在硬件断点命中时拦截 STATUS_SINGLE_STEP 异常（译注：原文作 "STATUSSINGLESTEP"，应为状态码 STATUS_SINGLE_STEP，照译加注）。然而这样做有风险，因为存在"外来"向量化异常处理程序的合法理由。
2. 干脆阻止调试器附加到进程的检查。这不被认为是一个可行的解决方案，因为调试器附加到进程有许多合法理由，其中许多可能对最终用户完全不可见（例如性能分析器、崩溃控制与报告系统，以及其他类型的安全软件）。试图阻止调试器还可能阻止 Windows 错误报告（Windows Error Reporting）或预配置的 JIT 调试器在游戏崩溃事件中的正常运行，这取决于所使用的实现。检测调试器的方法包括调用 `IsDebuggerPresent`、`NtQueryInformationProcess(...ProcessDebugPort..)`、对 `NtCurrentPeb()->BeingDebugged` 的检查，等等。（译注：原文 "soforth" 为 so forth 之笔误，照译；原文他处同类笔误如 "eachother" 等不再逐一标注。）
3. 在整个校验和实现的执行过程中复制检查（也许以略微改变的形式）。重要的是，这种复制要尽可能内联，以消除攻击者可用来短路保护方案的单点故障。
4. 如前所述，强化反调试机制。

### 3.3) Main Process Image Module Base Address Restriction / 3.3）主进程映像模块基地址限制

一个想在不受信任进程中执行 Lockdown 模块的攻击者，需要绕过对主进程映像基地址的限制。最可能的方法是组合攻击：攻击者使用一组硬件断点之类的东西来改变模块基地址的硬编码限制，并对 `GetModuleHandleA` API 使用导入表或代码补丁式的挂钩，以打败对主可执行映像模块基地址的第二重检查。

另一种方法是简单地把主可执行映像作为进程创建、将其挂起，然后在该进程中创建一个新线程，或者接管初始线程的控制权来执行 Lockdown 模块。这使潜在的攻击者不必对模块中的检查打补丁，因为该模块目前没有针对这种情况实现的防御。

为了强化这一保护机制，可以采取以下方法：

1. 手动遍历已加载模块列表（并检查 PEB，即进程环境块 Process Environment Block），以验证主进程映像真的位于 0x00400000。对这些机制逐一检查会给攻击者制造额外的工作，尽管它们每一个都可能被攻破。
2. 验证游戏在一定程度上已经初始化了自己。这会使"以挂起方式创建游戏进程"的方法更困难。它也会在其他方面使攻击者更难以在不受信任的进程中使用 Lockdown 模块，而不诱使该模块相信它正在一个已初始化的游戏进程中运行。确定游戏如何初始化的范围超出了本文的讨论，不过可以采用与目前基于 Storm 显存校验和的方法类似的做法（尽管要有更多的"冗余"，或者对合法游戏进程附加一整套要求矩阵）。

### 3.4) Minor Functional Differences Between Lockdown Module Flavors / 3.4）Lockdown 模块各风味之间的细微功能差异

目前，攻击者需要实现 Lockdown 模块的所有风味，才能确保成功连接到 Battle.net。然而，即使现在有 20 种可能性，由于不同 Lockdown 风味之间的功能差异很小，这仍然不困难。更甚者，找到构成每个 Lockdown 风味之间唯一功能差异的"魔法"常量是极其容易的。

在作者的测试中，两个模式匹配加一个 200 行的小型 C 程序，就足以以完全自动化的方式、编程式地识别出代表每个 Lockdown 风味模块之间功能差异的所有魔法常量。事实上，作者敢打赌：实现全部 20 种不同风味的 Lockdown 模块所花的时间，比构思并实现一个初步的模式匹配系统来自动发现全套 20 个 Lockdown 模块风味中全部 20 个魔法常量所花的时间还要多。显然，从投入保护方案的努力与攻击它的难度之比来看，这是不可取的。

为了解决这些弱点，可以实施以下步骤：

1. 在 Lockdown 风味之间实现真正的、重大的功能差异。与其使用在每个风味之间不同的单一常量值（可能是一个 "" 预处理器常量）（译注：原文此处仅作空引号 ""，疑似漏排了宏名，照译），不如实现其他真正的功能差异。否则，即使模块风味之间有许多不同的"非功能性"差异，一个模式匹配系统也能在人类攻击者发现了至少一个模块风味的常量之后，迅速为每个模块定位出不同的常量。
2. 避免使用可以快速替换的常量作为风味间功能差异的"实质"。虽然这些从开发角度来看很方便，但从攻击者角度来看也很方便。（译注：原文此处 "betwene" 为 between 之笔误，照译。）如果从开发角度多花一点时间，攻击者就可被迫对每个模块分别进行真正的分析，以确定实际的功能差异，从而大大增加攻击者打败这一保护方案所需的时间。

### 3.5) Spoofed Return Address for CheckRevision Calls / 3.5）对 CheckRevision 调用伪造返回地址

由于 x86 架构的工作方式，伪造一个过程调用的返回地址指针极其容易。所要做的只是把伪造的返回地址压到栈上，然后立即执行一条到目标过程的直接跳转（而不是标准的调用）。

因此，在运行时绕过这一保护机制相当容易。只需在内存中 Battle.snp 模块的代码空间中搜索一个 `ret` 操作码，并使用前面描述的技术，借助伪造的返回地址简单地把调用从 Battle.snp "弹跳"过去。对 Lockdown 模块来说，这个调用看起来将源自 Battle.snp 的上下文，但实际上这个调用会立即从 Battle.snp 返回到不受信任进程中真正的调用方那里。

为了反制这一点，可以尝试以下做法：

1. 验证两层深的返回地址，尽管由于 x86 调用约定的性质（至少 stdcall 和 fastcall 这两种是暴雪代码经常使用的），不能保证返回地址之后四字节处是一个特别有意义的值。
2. 验证返回地址并不直接指向 `ret`、`jmp`、`call` 或类似指令，假定当前的 Battle.snp 变体在其对该模块的调用中不使用此类模式。不过，这只会略微提高攻击者的门槛；他或她只需要通过 Battle.snp 中一个更具体的位置来中转调用，例如正常调用 Lockdown 模块时实际使用的位置。

### 3.6) Limited Pool of Challenge/Response Tuples / 3.6）挑战/响应元组的有限池

目前，Battle.net 服务器包含的版本检查与认证系统可能的挑战/响应对的池相当有限。观察表明，大多数产品有一个大约一千个值的池可以发送给客户端。这一点过去曾被用来对付 Battle.net，其反制是把若干 Battle.net 产品的可能值增加到 20000 个。然而，即使有 20000 个可能的值，随着时间的推移捕获大量登录尝试并建立一个可能值的查找表仍然是可能的。这对攻击者来说是一个有吸引力的选择，因为他或她只需在一段时间内进行被动分析，就能构建一个能以相当高的成功率登录 Battle.net 的数据库。鉴于版本检查值池的更新相对不频繁（通常每个补丁一次），这被认为是攻击者绕过版本检查与认证系统的一种相当可行的方法。

然而，暴雪可以很容易地解决这一限制，例如通过实施以下一项或多项建议：

1. 定期轮换可能版本检查值的集合，以确保挑战/响应对的数据库会很快过期并需要重建。结合一个大的可能值池，这种方法将大大降低这种攻击的实用性。不幸的是，作者怀疑，在当前的 Battle.net 服务器实现中，每次要轮换这些池时，都需要暴雪方面的人工干预。
2. 在每个 Battle.net 服务器上实现运行时动态生成池值。这将要求服务器能够访问所需的客户端二进制文件，但预计这不会是一个重大挑战（特别是因为作者怀疑 Battle.net 已经由 Windows 驱动，这将允许现有的 Lockdown 模块代码在清理和重新打包后也在服务器上使用）。这可以实现为一个每隔一段时间就"搅拌"一次的可能值池；新的挑战/响应值不一定需要在每次登录尝试时生成（而且这样做在任何情况下都会带来不希望的性能影响）。

## 4) Conclusion / 4）结论

尽管 Lockdown 模块及相关认证系统在暴雪持续打击非正版 Battle.net 客户端软件的战斗中代表了一个重大突破，但在版本检查与认证系统的未来发布中，仍有许多改进可以做出，这些改进将符合版本检查系统所受的约束，并且仍然会对试图使用非正版客户端伪造 Battle.net 登录的对手构成重大挑战。作者鼓励暴雪考虑并实施与本文所述类似的增强措施，特别是相互重叠、相互补充的保护措施（例如调试寄存器清除和内存校验和方案）。

在改进 Lockdown 系统方面，作者想强调以下原则对于创建一个既难以被攻破、又从开发和部署角度仍然可行且可用的系统来说特别重要：

- 关于模块内各种保护机制的纵深防御是必须的。保护系统需要被设计成相互补充、相互强化，使得攻击者必须打败多层保护方案，任何一次重大攻击才能成功到构成对该系统的攻破。

- 旨在挫败逆向工程或防止关键算法被轻易复制的对策，需要根据对手可能采取的"攻击"（或复制、重新实现等等）一个受"守卫"（或其他重要的）算法或代码段的方法来看待。例如，攻击者可以通过把汇编代码整段复制到另一个模块中，或者加载一个"正宗"模块并直接调用其内部函数（或内部函数的中间部分）以绕过"上游"的保护检查，从而减轻重新实现某个感兴趣的算法或函数的部分工作的负担。沿着这一思路，明智的做法（译注：原文此处 "advisible" 为 advisable 之笔误，照译）是把保护检查与执行实际有用工作的代码在一定程度上交错起来，使得对对手来说，绕过完全"前置"进行的保护检查不那么轻而易举（如果检查代码被整个跳过，其余的秘密算法或函数就会相对"脆弱"）。

- 旨在为对手制造"时间陷阱"（time sinks）的对策需要精心设计，使其不易被绕过。例如，在当前的 Lockdown 模块实现中，有二十种风味的 Lockdown 模块；然而，在这个实现中，对手发现（在很大程度上以编程方式）这些差异是极其容易的，这使这个"时间陷阱"非常无效，因为对手攻破它所需的时间很可能远少于最初的开发者创建它所需的时间。

- 依赖外部导入 API 的措施，通常相对容易被攻击者快速定位和禁用（例如，Lockdown 模块禁用调试寄存器断点的方法，对对手来说会立即显而易见——如果他们对 Win32 API 有哪怕一点点熟悉的话，而这必须假定他们熟悉）。在某些情况下（例如调试寄存器断点清除代码），这是不可避免的；但在其他情况下（例如模块基地址的验证），同样的效果可能通过使用不那么明显的方法来实现（例如，通过定位 PEB 以及当前线程 TEB 中的反向链接指针所指向的加载器数据结构，手动遍历已加载的模块列表）。作者鼓励其他防御措施的开发者尽可能减少对容易被注意到的外部 API 的依赖（当然，要与对可在所有支持平台上执行的、可维护代码的需求相平衡）。（译注：原文 "easily-noticible" 为 easily-noticeable 之笔误，照译。）在某些情况下，例如 Storm 符号的手动解析，当前系统在避免容易被检测到的外部 API 使用方面确实做得相当不错。

总而言之，Lockdown 系统在守卫 Battle.net、防止未经授权的客户端方面代表了向前迈出的一大步。即便如此，在该系统潜在的未来修订中仍有很大的改进空间。作者希望，通过对当前 Lockdown 模块的长处和弱点的全面核算（并就如何修复当前实现中某些较弱机制提出尖锐的建议），本文可能对未来防御系统的强化有所裨益。
